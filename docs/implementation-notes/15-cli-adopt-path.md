# #15 CLI: Adopt path

Questions that came up while building the Adopt path of `iidp app create`, the options considered, and the answer chosen for each. `docs/design.md`'s "The wizard" (question 2's "Adopt asks for the repository", question 3's "skipped when the repository already has a Dockerfile") and `docs/implementation-notes/11-cli-create-path.md`, `13-cli-capabilities.md` and `14-cli-wizard.md`'s Adopt hooks were the starting point.

## The flag: `--repo <owner>/<name> | <https URL>`, not a positional argument

The ticket names the flag; logged here as instructed. `--repo` accepts either shorthand (`owner/name`) or a GitHub URL (`https://github.com/owner/name`, with or without a trailing `.git` or slash), parsed by `parseRepoFlag` in `internal/cli/app.go` with no network access — consistent with every other flag `createOptions.plan` validates before anything is cloned. A positional argument was rejected: `app create` already takes `cobra.NoArgs`, and every other identifying value in this command (`--name`, `--image`, `--domain`) is a flag; a lone positional would be the only exception.

## The Application name defaults to the repository name; `--name` is not required for Adopt

`checkRequiredFlags` and `createOptions.plan` both special-case `pathAdopt`: `--repo` is required, `--name` is not (it defaults to `--repo`'s parsed name), matching the ticket's "defaults to the repository name; `--name` overrides". `platformrepo.ValidateName` still runs on whichever name is used, so a repository whose own name is not a valid Application name (uppercase, too long, containing `_` or `.`) is refused with the same message Create's `--name` validation gives — `--name` is how a developer works around that.

## Kind: never asked interactively; required as a flag, resolved from detection otherwise — recorded per the ticket's explicit ask

**The question the ticket asks to log:** how the CLI decides Kind when a Dockerfile exists, since it cannot tell a Static site image from a Web service one from the Dockerfile alone.

**Choice, per the ticket's own recommendation:** `--kind` is required, with a message, whenever detection cannot resolve it — a Dockerfile already exists, or no known framework was detected (the Other case). `apprepo.ResolveKind(explicit string, det Detection) (string, error)` is the single place this is decided: an explicit `--kind` always wins outright (no "must not be set" refusal the way Create has for a framework that derives one — Adopt's detection is a best guess about someone else's repository, not a chosen template, so overriding it should never be an error); left empty, it is derived from `det.Framework.Kind()` when a framework was detected, and refused otherwise. `internal/cli/wizard.go`'s Kind/framework block (the `TODO(#15)` this ticket replaces) now skips itself entirely for Adopt — no question is asked, matching the ticket's "the Kind and framework questions are skipped" — and relies on this same refusal surfacing once the repository is actually read, either during the interactive summary's preview clone or, non-interactively, inside `Adopter.Adopt` itself.

**Why this, over asking Kind interactively once a Dockerfile is found:** the wizard would need to clone the repository mid-question to know whether to ask, which is possible (the summary already does an extra clone, see below) but adds a real branch to the question flow for a case — an Application with a hand-written Dockerfile the CLI cannot classify — that is uncommon enough that a clear flag-driven refusal, logged once, is simpler for both the implementation and a developer reading `--help`.

## Detecting the framework: `package.json`'s dependencies *and* devDependencies

`docs/design.md`'s wording ("Next.js from `next` in `package.json` dependencies, Vite React from `vite` plus `react`") reads as the `dependencies` object specifically, matching Create's own generated templates — except Create's own `vite-react` template (`internal/templates/vite-react/package.json`) keeps `vite` in `devDependencies` and only `react`/`react-dom` in `dependencies`, the shape the real `create-vite` scaffolding tool also produces. Detecting only `dependencies` would misclassify Create's own output if it were ever adopted. `apprepo.detectFramework` checks both objects for `next` and for `vite`/`react` independently, falling back to Other (including when there is no `package.json` at all) exactly as Create's own framework enum already allows nothing else.

## Only the Dockerfile and `.dockerignore` are rendered, not the whole template

`templates.RenderDockerfile(framework, data, dir)` is new: it writes exactly `Dockerfile` and `.dockerignore` from the chosen framework's embedded files, reusing the same `text/template` rendering `Render` (Create's whole-template writer) already does per file, rather than walking the framework's directory and filtering. `templates.DeployWorkflowPath` (renamed from the package-private `deployWorkflowPath`) and a new `templates.RenderDeployWorkflow(data) []byte` expose the one shared workflow file the same way, so Adopt never touches `package.json`, source files, `.gitignore` or the template's own README — files that would collide with or shadow whatever the real repository already has.

## The deploy workflow is added only when the path is entirely absent — never compared for "identical enough to skip"

The ticket's own wording allows either: "`.github/workflows/deploy.yaml` always unless an identical one exists". Read literally, that leaves open what happens when a *different* one already exists. Chosen: `apprepo.Detection.HasDeployWorkflow` is a plain existence check (`os.Stat`), and `Adopter.Adopt` writes the file if and only if it is absent — an existing workflow, whether byte-identical to what Adopt would generate or not, is left alone, the same "never modify what already exists" rule the ticket states explicitly for the Dockerfile. This was chosen over an identical/different distinction (write only when different, or refuse when different) because the ticket's other acceptance criterion — "nothing else in the repository is ... modified" — is unconditional, and re-writing a file that already exists is a modification even when the new content happens to match. Re-running Adopt against a repository that already has `deploy.yaml` (from an earlier successful Adopt, or written by hand) therefore never touches it again; if the repository has neither a `Dockerfile` nor needs a workflow, `Adopter.Adopt` refuses with `ErrNothingToAdd` rather than opening an empty pull request.

## One `Adopter`, not the `Creator` pattern's exact shape

`internal/apprepo/adopt.go` adds `Adopter` (`Client`, `Auth`, matching `Creator`'s fields) with two methods: `Preview` (read the repository, clone it, detect — no writes, no branch, no PR) and `Adopt` (the same reads, plus refusal checks, the actual clone, writing, committing, pushing and opening the pull request). `Detection` (Dockerfile/framework/deploy-workflow/migration) and `AdoptPreview`/`AdoptRequest`/`AdoptResult` are named with an `Adopt` prefix because `apprepo.Creator` already owns the bare names `Result`/`Application`; `ResolveKind` and `Detection.Files()` are exported standalone functions so both the CLI's interactive preview and `Adopter.Adopt` itself compute the same "what Kind, what files" answers from one piece of logic, never two copies that could disagree.

## The wizard previews with one extra clone, then Adopt clones again for real — the same trade-off `PreviewApplication` already made

`docs/implementation-notes/14-cli-wizard.md` settled this for the Platform repository: showing real data in the summary needs a read, but declining must leave no lasting side effect, and "no lasting side effect" was interpreted there as "no commit pushed, no GitHub repository created" rather than "no temporary clone ever made". The same reasoning applies here: `runAppCreate`'s interactive-and-not-`--yes` branch calls `Adopter.Preview` (a read-only GitHub API check plus a throwaway clone, removed before it returns) to resolve Kind, list the files the pull request will add, and refuse early if push access is missing or `iidp/adopt` already exists — all before the summary is printed or anything is confirmed. Once confirmed, `Adopter.Adopt` clones the same repository again to actually write, commit, branch, push and open the pull request. This costs one extra clone per interactive Adopt run (skipped entirely with `--yes`, exactly like `PreviewApplication`), which is cheap: Adopt's clone is shallow, single-branch, and of a repository size dominated by source code the clone doesn't need to keep around either way.

## The wizard's live migration-command suggestion is not populated for Adopt — a documented gap, not a silent one

The migration command question (`askMigrationCommand` → `suggestMigrationCommand` → `resolveMigrationDir`) decides what directory to look in from the plan alone, with no network access, exactly like every other `plan()`-time computation: for Create it renders a scratch copy of the template, for the legacy bare path and for Adopt it falls back to the current working directory when it has a `package.json`. For Adopt that fallback is only useful by coincidence — the developer happens to be running `iidp` from inside a checkout of the very repository being adopted, which is a plausible enough real-world habit to leave the fallback in place rather than special-case it away, but it will not generally find what a real clone would. Wiring the live suggestion to a real clone would mean acquiring a GitHub token and cloning mid-wizard, before question 2's own repository answer has even been through `plan()`'s validation — a bigger seam change than this gap justifies. What is not a gap: the actual value written to `postgres.migrationCommand` is always correct, because `detectMigrationCommand`'s real detection (for a flag-driven run) and `Adopter.Adopt`'s own detection (against the true clone, whenever `--migration-command` was not explicitly set) are what is authoritative — the wizard's live suggestion is cosmetic, shown before the developer decides, not a source of truth for what gets written. A developer who wants the wizard to show the real suggestion for Adopt can run from within a checkout of the target repository, or skip the wizard and use `--postgres` with no `--migration-command` directly.

## Branch name: `iidp/adopt`, checked and refused via the GitHub API, not a local git check

Named for the Platform (`apprepo.AdoptBranch`), matching the ticket's "a branch named for the Platform" and the exact string logged here: `iidp/adopt`. Every Adopt run against a given repository targets the same branch, so a second run before the first pull request is merged or closed is refused rather than silently opening a second, competing one. The existence check is `github.Client.BranchExists` (`GET /repos/{owner}/{name}/branches/{branch}`, 200 vs 404), run before any clone: it is the same shape `RepositoryExists` already uses for the Create path (`internal/implementation-notes/11-cli-create-path.md`'s `*statusError`/`IsNotFound`), and checking through the API rather than after a clone means the refusal costs nothing but one HTTP request when the branch is already there.

## Permission: `permissions.push` from `GET /repos/{owner}/{name}`, refused with `ErrNoPushAccess`

The ticket's "the developer's permission from `permissions.push` must be true, otherwise a clear refusal" is read literally: `github.Client.GetRepository` decodes the `permissions.push` GitHub already includes in an authenticated repository read (no separate collaborator-permission endpoint call needed), and `Adopter.Adopt`/`Preview` refuse before cloning anything when it is false. This is a point-in-time check like every other permission or existence check in this codebase (`docs/implementation-notes/11-cli-create-path.md`'s "Ordering" section): a permission revoked between the check and the push still fails, just later and with git's own error instead of this one.

## Testing: a real bare Application repository per fixture, the fake GitHub server's `clone_url` pointing at it

Per the ticket's explicit testing seam: `internal/cli/app_create_test.go` gains `seedApplicationRepository(t, defaultBranch, files)`, the same init-bare/clone/seed/push shape `newPlatformRepository` already uses for the Platform repository fixture, returning both the bare directory (so a test can push a branch to it directly, simulating one already present) and its `file://` clone URL. `fakeGitHub` (`app_create_create_test.go`) gains: `seedAdoptRepository` (registers a seeded repository as existing, with push access, at a given owner/name), `denyPush`/`markPrivate`, and three new endpoint handlers layered into the existing `/repos/` prefix route — `GET .../branches/{branch}` (answered by literally checking the bare repository's refs with `git show-ref`, so a branch the CLI actually pushed becomes observably present with no separate bookkeeping) and `POST .../pulls` (recorded as a `fakePullRequest`, returned with a fake `html_url`). `GET /repos/{owner}/{name}` itself now returns `default_branch`, `clone_url`, `private` and `permissions.push`, fields the pre-existing Create-path tests never decoded but which Adopt's `GetRepository` needs.

`internal/cli/app_create_adopt_test.go` covers: Next.js and Vite React detected from a Dockerfile-less repository's `package.json` (dependencies and devDependencies), no known framework requiring `--kind` and producing the Other stub, an existing Dockerfile never modified and requiring `--kind`, no push access refused, an already-existing `iidp/adopt` branch refused, the personal-account (non-org owner) secret-and-variable note in both stdout and the pull request body, migration tooling (a `prisma/schema.prisma` in the seeded repository) detected with `--postgres` and no `--migration-command`, the Application name defaulting to the repository name and `--name` overriding it, `--repo` accepting a URL, `--repo` requiring `--path adopt` and vice versa, every other Capability flag (`--postgres`, `--staging`, `--size`) applying the same way Create's do, and the wizard asking for the repository while never asking Kind or Framework. `assertOnlyAddedFiles` diffs the pushed branch against the default branch with `git diff --name-status`, asserting every changed path has status `A` (added) and that the set matches exactly what the ticket says the pull request should contain — the acceptance criterion "assert that in tests by diffing the pushed branch against the default branch", implemented literally.

## What the review changed

A two-axis review (repository standards, then issue #15's acceptance criteria) was run before the pull request. Fixed: a flag-driven (non-interactive) `--postgres` run against a repository whose Kind resolves to Static site (an existing Dockerfile Kind override, or a detected framework) used to open the pull request and push the branch *before* checking that combination, so a refusal after the fact left a real, open pull request behind with no explanation — `AdoptRequest` now carries `Postgres bool`, and `Adopter.Adopt` checks it immediately after resolving Kind, before any file is written, branch created, commit made or push attempted, matching the interactive summary's own preview-based early refusal; `TestAppAdoptRefusesPostgresOnAStaticSiteBeforeOpeningAPullRequest` asserts no pull request is opened. The three near-identical copies of the Postgres/Static-site refusal (`createOptions.plan`, the interactive summary, and the old post-`Adopt`-call check) became one `checkPostgresKind(postgres bool, kind string) error`, called from `plan` and the summary; `Adopter.Adopt`'s own copy stays separate since it lives in a different package and is the one that must run after Kind is actually resolved from a real clone. `github.Repository.Private`/`AdoptPreview.Private` (read from the API but never used for any refusal or printed anywhere) were removed as dead plumbing, along with the test fixture's matching `markPrivate` helper. `runWizard` no longer takes an unused `Dependencies` parameter it never read (added, then not needed once the migration-command gap below was accepted as a documented limitation instead of built out). `internal/apprepo.Creator`'s `ErrRepositoryExists` message, which used to point at "Adopt (not available yet, see issue #15)", now names the actual `--path adopt --repo` invocation. `TestAppAdoptCapabilitiesApplyTheSameAsCreate` gained a `--domain` case (prod only, staging still empty), the one Capability flag combination the original test left unexercised for Adopt.

## What was not built

A `--yes`-equivalent dry run that shows the pull request's diff without opening it was not asked for and was not added; `Adopter.Preview` exists for the wizard's own use, not as a new user-facing flag. Rebasing or updating an already-open `iidp/adopt` pull request (rather than refusing) is left for a future ticket if repeated Adopt runs against the same repository turn out to be a real workflow — the ticket's own text ("If the branch already exists remotely, refuse with a message") settles this one.
