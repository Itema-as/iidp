# #131 A Preview Environment's sync always ends

Found during the Phase 2 rollout (#96, step 11), on Itema-as/hello#2. The preview's migration Pod was Unschedulable (`Insufficient cpu`, fixed by #130), so its sync waited on the migration hook. Closing the pull request started the deletion, and `hello-pr-2` showed `Activity: Leaving`, but nothing was deleted while the sync ran. Deleting the migration Job didn't help: the sync failed, retried and made a new Job. Only `argocd app terminate-op argocd/hello-pr-2 --core` let ArgoCD finish the deletion.

## What ArgoCD does

Checked on 2026-09-29 against ArgoCD **v3.5.3**, the appVersion of the argo-cd chart `bootstrap/versions.yaml` pins, and Kubernetes **v1.36.4**, the k3s release `infra/platform/variables.tf` pins. Read at the tags:

- **Deletion waits for the operation.** The application controller's operation worker either processes the running operation or finalizes the deletion, never both: `if app.Operation != nil { processRequestedAppOperation } else if app.DeletionTimestamp != nil { finalizeApplicationDeletion }` ([`controller/appcontroller.go` L1134](https://github.com/argoproj/argo-cd/blob/v3.5.3/controller/appcontroller.go#L1134)). `operation` is cleared only when the operation's phase is completed ([L1678](https://github.com/argoproj/argo-cd/blob/v3.5.3/controller/appcontroller.go#L1678)). So a deleted Application whose sync never completes is never deleted.
- **Retries happen inside the same operation.** When a sync fails and `retryCount < limit || limit < 0`, the controller sets the phase back to `Running` and appends "Retrying attempt #N" to the message ([L1620](https://github.com/argoproj/argo-cd/blob/v3.5.3/controller/appcontroller.go#L1620)). The operation is not completed, so `operation` stays set. With `limit: -1` it is never completed while the sync keeps failing, whatever fails. The documented meaning of the field is the same: "number of failed sync attempt retries; unlimited number of attempts if less than 0" ([`docs/operator-manual/application.yaml` L254](https://github.com/argoproj/argo-cd/blob/v3.5.3/docs/operator-manual/application.yaml#L254)). Nothing checks the deletion timestamp before a retry, so a retry runs the hook again during a deletion. That is the new Job seen on hello#2.
- **A Job whose Pod never starts never fails.** ArgoCD's Job health is Progressing until the Job has a `Complete`, `Failed` or `Suspended` condition ([`gitops-engine/pkg/health/health_job.go` L54](https://github.com/argoproj/argo-cd/blob/v3.5.3/gitops-engine/pkg/health/health_job.go#L54)). A Progressing hook is a `Running` task ([`gitops-engine/pkg/sync/sync_context.go` L362](https://github.com/argoproj/argo-cd/blob/v3.5.3/gitops-engine/pkg/sync/sync_context.go#L362)), and while any hook is running the sync waits ([L578](https://github.com/argoproj/argo-cd/blob/v3.5.3/gitops-engine/pkg/sync/sync_context.go#L578)). A Pending Pod adds no failure to `backoffLimit`, so the Job never gets `Failed`, the sync never fails, and a retry limit is never reached.
- **No sync timeout.** The controller's `--sync-timeout` defaults to 0, "no timeout" ([`cmd/argocd-application-controller/commands/argocd_application_controller.go` L280](https://github.com/argoproj/argo-cd/blob/v3.5.3/cmd/argocd-application-controller/commands/argocd_application_controller.go#L280)), and the bootstrap does not set it.
- **A new push starts a fresh sync.** Once a failed operation has completed, automated sync skips a new attempt only if the spec's sources equal the last sync's ([`alreadyAttemptedSync`, L2492](https://github.com/argoproj/argo-cd/blob/v3.5.3/controller/appcontroller.go#L2492)). A push to the pull request changes the preview's `valuesObject.image.tag`, so its sources differ and a new sync starts. While an operation is still running, auto-sync is skipped ([L2322](https://github.com/argoproj/argo-cd/blob/v3.5.3/controller/appcontroller.go#L2322)).
- **`activeDeadlineSeconds` counts Pending time.** The Job controller sets `status.startTime` the first time it syncs a Job that is not suspended, before any Pod is scheduled ([`pkg/controller/job/job_controller.go` L1051](https://github.com/kubernetes/kubernetes/blob/v1.36.4/pkg/controller/job/job_controller.go#L1051)). The deadline is measured from `startTime` ([L1717](https://github.com/kubernetes/kubernetes/blob/v1.36.4/pkg/controller/job/job_controller.go#L1717)), and when it passes the Job fails with reason `DeadlineExceeded` ([L1091](https://github.com/kubernetes/kubernetes/blob/v1.36.4/pkg/controller/job/job_controller.go#L1091)). ArgoCD then sees it Degraded, the hook fails, and the sync fails.

[argoproj/argo-cd#29100](https://github.com/argoproj/argo-cd/issues/29100), which the issue points to, is about `PreDelete` hooks being deleted before they run (`39-final-backup-predelete-hook.md`). It is not this bug: a preview has `postgres.backups: false` and so no `PreDelete` hook, and `finalizeApplicationDeletion`, where that race lives, is not reached at all while an operation runs.

So each fix alone is not enough. With only a deadline, the failed hook is retried without limit and the operation stays `Running`. With only a retry limit, a Pending hook Pod never fails, so there is nothing to retry and the operation stays `Running`.

## The choices

- **The migration Job gets `activeDeadlineSeconds: 1800`, in every Environment.** Chosen by the maintainer. 30 minutes is the same bound as `postgres.finalBackupTimeout`. A preview's first sync can start before the pull request's image has been built (the generator and the build run at the same time), and its migration Pod waits in `ImagePullBackOff` until the image is there. 30 minutes leaves room for that, and for any migration of the databases on the Platform today. Staging and prod get it too: their sync also blocks their deletion, and a migration that can't start there otherwise leaves the Environment `Syncing` until someone looks.
- **Not a value.** Options: a `postgres.migrationTimeout` next to `finalBackupTimeout`, or a fixed number. Chose the fixed number: no Application has needed a longer migration, and the chart avoids knobs nobody asked for. `finalBackupTimeout` is a value because a large database's backup can take a long time. A migration that takes longer than 30 minutes would need more than a longer deadline, since it holds up the rollout for that long. If one appears, the value is a small change.
- **Preview Environments retry 3 times (`render.PreviewRetryLimit`).** Chosen by the maintainer. Options: no retry (`limit: 0`), a few, or unlimited as before. A few retries still carry a preview over a passing failure (an apply refused while a webhook is starting, say), which `limit: 0` would leave failed until the next push. Staging and prod keep `limit: -1`. They have no other way to pick up a fix: a fix committed to the Platform repository reaches them through the retrying sync (#75, `retry.refresh`). A preview doesn't need that, because a push to the pull request changes the Application and starts a fresh sync.
- **The retry keeps staging's backoff and `refresh: true`.** Only the limit differs.

## Consequences

- In the worst case, a preview whose migration Pod never starts is deleted about **two hours** after its pull request closes: four attempts of 30 minutes each, plus 10 s, 20 s and 40 s of backoff. That is bounded, and needs nobody with cluster access. A shorter bound would need a lower limit or a shorter deadline for previews only. Neither is worth a preview-only value yet.
- A preview whose sync failed four times stays failed until the next push to its pull request. Previously it retried every 3 minutes for ever. Its ArgoCD Application shows the failure (`SyncError`, "Failed last sync attempt").
- A staging or prod Environment whose migration Pod can't start now fails its sync after 30 minutes and retries, instead of staying `Syncing`. Each retry makes a new Job (`BeforeHookCreation`), so the Pending Pod is replaced every half hour until the node has room.
- **Not covered: a database that never becomes healthy.** The sync waits for every object of a wave to be healthy before the next wave, not only for hooks ([`sync_context.go` L578](https://github.com/argoproj/argo-cd/blob/v3.5.3/gitops-engine/pkg/sync/sync_context.go#L578), `multiStep`). A `Cluster` in wave -2 whose instance Pod is Unschedulable should stay in a phase ArgoCD's health check calls Progressing (`Setting up primary`, [`resource_customizations/postgresql.cnpg.io/Cluster/health.lua`](https://github.com/argoproj/argo-cd/blob/v3.5.3/resource_customizations/postgresql.cnpg.io/Cluster/health.lua); not reproduced), and nothing gives it a deadline, so that sync would also never end and the preview would not be deleted. On hello#2 the database did start; only the migration Pod did not. `argocd app terminate-op` is still the way out of that case. Not changed here; it would need its own issue.
- Environments get the deadline when their `application.yaml` names a chart version with this change. The preview ApplicationSet has its own copy of the chart version, and the CLI rewrites it only when a command changes staging's `application.yaml`. So an existing ApplicationSet keeps `limit: -1` and its old chart version until someone edits it or the CLI rewrites it.

## Proof

- `internal/render/previews_test.go`: `TestPreviewRetriesALimitedNumberOfTimesWhereStagingRetriesForEver` asserts that the preview ApplicationSet's retry limit is `PreviewRetryLimit`, a finite number, with refresh, and that the staging Application it copies still has `limit: -1`. `ExamplePreviewApplicationSet` shows `limit: 3`.
- `chart/application/postgres_test.go`: `TestEveryMigrationJobHasADeadline` asserts `activeDeadlineSeconds: 1800` on the migration Job of every fixture that renders one, a preview's included.
- `test/e2e/fixtures/platform-repo/applications/notes/previews/applicationset.yaml` has `limit: 3`; `TestFixturePreviewsAreTheCLIsApplicationSet` keeps it equal to what the CLI writes.
- Not reproduced on a cluster. The kind test does not make a hook Pod Unschedulable.
