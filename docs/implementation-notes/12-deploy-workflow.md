# #12 Deploy workflow and CI write-back subcommand

Questions that came up while building `.github/workflows/deploy.yaml`, `iidp ci set-image` and the GitHub App installation-token flow that authenticates it, the options considered, and the answer chosen for each. Sources (the GitHub REST API's App-authentication endpoints, `docker/build-push-action`, `docker/login-action`, `docker/setup-buildx-action`, `docker buildx imagetools`) were checked with Context7 on 2026-09-21.

## How `iidp ci set-image` reads `platform.yaml` before it has any credential

**Question.** The subcommand is told to mint its GitHub App installation token "from the app id and installation id in `platform.yaml`", but `platform.yaml` lives in the Platform repository, and reading it normally means cloning that repository with a credential — the very thing minting the token is supposed to produce. Something has to break the circularity.

**Choice.** `platformrepo.LoadRemoteConfig` clones `main` with no credential at all (`git.Auth{}`) purely to read `platform.yaml`, before anything else happens. This is safe, not a shortcut: `platform.yaml` carries no secret by design — `agePublicKey` is a *public* key (`docs/platform-repository.md` already says so for `iidp secret set`), and `baseDomain`, `chartVersion`, `cloudflareZone`, `backupsBucket` and now `githubApp.id`/`githubApp.installationId` are Platform-wide configuration, not credentials. Once `githubApp.id` is known, the JWT is signed, the installation token is minted, and *that* token is what `platformrepo.Writer.SetImageTag` uses for the real clone-edit-commit-push cycle (a second, authenticated clone — a little wasteful, but it keeps `SetImageTag` identical in shape to `CreateApplication`/`SetSecrets`, and a shallow anonymous clone of one small YAML file is cheap next to the file/image work CI already does).

**Consequence, and the objection considered.** A review pass raised exactly the right question: every other command that touches the Platform repository (`app create`, `secret set`) requires a `gh auth login` token and refuses with "not logged in to GitHub" if it is missing — doesn't that mean the Platform repository is assumed private, and won't the anonymous clone here simply fail in production? It's a fair reading, but it conflates two different requirements. Those other commands need a token because they need to *push* (the write is what requires write access; a public repository still enforces that). Nothing in `docs/design.md`, `docs/platform-repository.md` or any ADR states the Platform repository's *read* access is restricted, and its secrets are SOPS-encrypted specifically so that exposure of the repository's contents is not a security incident (`ADR-0002`, `docs/platform-repository.md`'s "Secrets"). Requiring anonymous read access is therefore a real but acceptable operational requirement, not a latent bug — it is now stated plainly in `docs/platform-repository.md` ("How the deploy workflow writes back") and `LoadRemoteConfig`'s own error message names it explicitly rather than surfacing as an opaque clone failure. If a future decision makes the Platform repository private, `githubApp.id`/`githubApp.installationId` would need another source — the org Actions variable `IIDP_DEPLOY_APP_ID` already exists per `docs/implementation-notes/05-bootstrap-wizard.md` and is the natural fallback for the id half, though nothing today provides the installation id the same way. Reopen this if the Platform repository's visibility changes.

## Where the app id and installation id actually live

`docs/implementation-notes/05-bootstrap-wizard.md` records the wizard writing both an org Actions secret (`IIDP_DEPLOY_APP_PRIVATE_KEY`) and an org Actions variable (`IIDP_DEPLOY_APP_ID`), anticipating that "ticket #12's deploy workflow reads" the variable directly. This ticket instead reads the app id (and the installation id, which the wizard note does not mention a variable for) from `platform.yaml`'s new `githubApp` block, per the issue's own instructions. `IIDP_DEPLOY_APP_ID` is left as it is — an unused-by-this-ticket convenience the wizard already provides — rather than removed; a future change could make the two consistent (drop one source) if that turns out to matter.

## The JWT: standard library only, GitHub's documented claims

Confirmed via Context7 (`/websites/github_en_rest`, "generate a JSON Web Token (JWT) for a GitHub App" and "create an installation access token"): `POST /app/installations/{installation_id}/access_tokens`, authenticated with `Authorization: Bearer <JWT>` where the JWT is RS256-signed, `iss` the App's id, `iat` recommended 60 seconds in the past (clock drift tolerance) and `exp` at most 10 minutes ahead. `internal/githubapp.SignJWT` implements this with `crypto/rsa`, `crypto/sha256`, `encoding/base64` and `encoding/json` only, matching the ticket's "no JWT dependency" and this repository's existing minimal-dependency posture (`docs/implementation-notes/16-cli-secret-set.md` made the same call for SOPS). `internal/github.Client.CreateInstallationToken` reuses the existing client's `do` method: since `Client.Token` is sent as `Authorization: Bearer <Token>` already, setting `Token` to the JWT for this one call is enough — no new HTTP plumbing needed.

## Environment resolution: inside `platformrepo.Writer.SetImageTag`, not the CLI layer

`auto` must be decided "from the Platform repository, never the workflow" (the issue's own words). `platformrepo.Writer.attemptSetImageTag` resolves it after cloning, by checking whether `applications/<app>/staging/` exists in that same clone — the same clone that goes on to write the tag, so there is no window for the Application's shape to change between the decision and the write within one attempt. `internal/cli/ci.go` never sees "auto" become "staging" or "prod" itself; it only reports back `Result.Environment`, the same way `Result.Address`/`Result.StagingAddress` already report facts decided inside `platformrepo`.

## Commit message: the resolved Environment, not the literal `auto`

`Deploy <app> <environment> <tag>` uses whichever of `prod`/`staging` was actually written, not the literal string a caller passed. A Platform repository's git log is its audit trail (`ADR-0002`); logging "auto" there would makes every reader re-derive what actually happened.

## `render.SetImageTag`: the same node-level editing `iidp secret set` uses

`internal/render/edit.go` already has `AddSecretName` and `AddKustomizeSource`, both decode-edit-reencode on a `yaml.Node` tree so comments and untouched keys survive (`docs/implementation-notes/16-cli-secret-set.md`). `SetImageTag` follows the same shape: find `image.tag`'s scalar node and mutate its `Value` in place, forcing `Tag: "!!str"` and clearing `Style` so a numeric-looking tag (a version like `20260921`, though unlikely for this project's tags) is never re-encoded as a YAML number. It reports `changed bool` like its siblings, though nothing currently uses that to skip a commit (unlike `iidp secret set`, `ci set-image` always has something to write: a different tag every time it runs).

## Installing `iidp` inside the generated workflow

The workflow needs `iidp` itself to run `ci set-image`. Chosen: `gh release download` (preinstalled on GitHub-hosted runners), authenticated with `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}` (a valid token is enough to call the API at the authenticated rate limit, even for a different, public repository), against a fixed pattern `iidp_*_linux_amd64.tar.gz` (`.goreleaser.yaml`'s `name_template`). The version to pin to is `internal/version.Version` at template-generation time, with `dev` (a `go build` with no `-ldflags`, i.e. this ticket's own dev builds and anyone building the CLI from source) mapped to `latest` (`gh release download` with no tag argument): `apprepo.Creator.Create` resolves this once (`templateIidpVersion`) and both the workflow template and the CLI's closing output ("The deploy workflow ... is pinned to iidp `<version>`") use the same resolved string, so the two can never disagree. The release repository is `platform.CLIRepository` (`Org + "/iidp"`), a new constant next to `platform.Repository`, so it changes in the one place the org constant does.

## The GitHub Actions `${{ }}` / Go `text/template` `{{ }}` collision

**Question.** Every other file `internal/templates` renders goes through `text/template` (`{{.Name}}` etc.). A GitHub Actions workflow is full of its own `${{ github.sha }}`-style expressions, which use the identical `{{`/`}}` delimiters `text/template` parses by default. Parsing `deploy.yaml` as a Go template would either fail outright (`github.sha` is not a template action) or, worse, silently misinterpret pieces of it.

**Choice.** `.github/workflows/*.yaml` files are detected by path (`templates.workflowPath`, a small regexp) and rendered by plain `strings.Replacer` substitution instead of `text/template`: four tokens (`__IIDP_APP_NAME__`, `__IIDP_OWNER__`, `__IIDP_VERSION__`, `__IIDP_CLI_REPO__`) stand in for the values `text/template` would otherwise have filled in. This keeps every other embedded file (READMEs, `package.json`, Dockerfiles) on the existing, more flexible `text/template` path unchanged, and keeps the one file that cannot use it simple and readable as plain YAML with obviously-not-shell-not-YAML placeholder tokens, rather than escaping every `${{ }}` in the workflow as `{{"{{"}}` noise.

## One `deploy-workflow.yaml`, not one per framework

The workflow is identical for every framework: it builds whatever `Dockerfile` the template shipped and never branches on which framework generated it. An earlier pass duplicated it into `internal/templates/{nextjs,vite-react,other}/.github/workflows/deploy.yaml`, matching how each framework directory is a self-contained embedded root — but unlike the READMEs and Dockerfiles, which genuinely differ per framework, three identical 129-line copies would drift the next time only one got edited (a review flagged this as Duplicated Code). Chosen instead: one file, `internal/templates/deploy-workflow.yaml`, embedded on its own (`//go:embed deploy-workflow.yaml`) and written by `Render` after the per-framework walk, for every framework, at `.github/workflows/deploy.yaml`. `TestDeployWorkflowIsIdenticalAcrossFrameworks` locks in that the three renders produce byte-identical output (modulo nothing — `Data` carries no per-framework field), which is the property this change is for.

## The `promote` job needs no `actions/checkout`

A review pass noted the `promote` job (the `v*`-tag path) had an `actions/checkout` step, copied from `build`'s shape, even though `docker buildx imagetools create` and the `iidp ci set-image` install step touch nothing in the Application repository's working tree — only the registry and GitHub's API. Removed; `build` keeps its checkout because `docker/build-push-action`'s `context: .` needs the repository's files. `TestDeployWorkflowIsRenderedForEveryFramework` asserts `jobs.promote.steps` has no `actions/checkout` step, so it cannot silently come back.

## Action versions, pinned to a major, checked live

Confirmed via Context7 against `docker/build-push-action`'s own README and `docker/docs`' GitHub Actions guides: `actions/checkout@v7` (matching this repository's own `release.yaml`, itself newer than the docs' own `@v6` example — both current), `docker/setup-buildx-action@v4`, `docker/login-action@v4`, `docker/build-push-action@v7`. `docker buildx imagetools create --tag <new> <existing>` is documented (`docker/docs`, "Copy multi-platform images between registries") as the no-rebuild retag command; the promote job uses it exactly that way, retagging the SHA image (built on `main`, before the tag existed) as the tag's version.

## Tag ref parsing: `${GITHUB_REF_NAME#v}`, matching the release workflow's own idiom

The promote job strips a `v*` tag's leading `v` with the same shell pattern `.github/workflows/release.yaml`'s `chart` job already uses (`version="${GITHUB_REF_NAME#v}"`), rather than introducing a different technique. `docs/platform-repository.md` documents the result: `image.tag` on `prod` after a tag push is the version without its `v` (tag `v1.2.3` writes `1.2.3`), the same convention `internal/version.Version` and `chartVersion` already use.

## `on.push.branches`/`on.push.tags`, and the YAML 1.1 `on:` boolean gotcha

Checked directly (a scratch `gopkg.in/yaml.v3` decode of `on:\n  push:\n ...` into `map[string]any`): the library resolves the plain scalar key `on` as the string `"on"`, not the YAML 1.1 boolean `true` some other parsers (PyYAML, older Ruby YAML) infamously produce for GitHub Actions workflows. The workflow-validity test asserts `on.push.branches[0]` and `on.push.tags[0]` directly by string key with no workaround needed.

## GHCR package visibility

GHCR packages a workflow pushes are private by default. The chart's `Deployment` pulls `image.repository:image.tag` with no `imagePullSecrets` today (`chart/application/templates/deployment.yaml`), so a private package needs either pull credentials added to the Environment's namespace (a chart change, out of scope here) or the package made public. **Recommendation: make the package public**, for now, the simplest of the two and consistent with this being an internal Platform where the image itself (unlike the Platform repository's secrets) is not sensitive. Where: the package's GitHub page (`https://github.com/orgs/<org>/packages/container/<name>` for an org, `https://github.com/users/<user>/packages/container/<name>` for a personal account) → Package settings → Danger Zone → Change visibility. Documented in `README.md` and every template's `README.md`; a chart change to support `imagePullSecrets` is a natural follow-up if a private registry is ever preferred.

## The personal-owner secret note

`IIDP_DEPLOY_APP_PRIVATE_KEY` is created as an org Actions secret with visibility `all` (`docs/implementation-notes/05-bootstrap-wizard.md`), so every org repository receives it automatically; a repository under a developer's personal account (`--owner user`) does not, and the deploy workflow's write-back step will fail there until someone adds a repository-level secret of the same name by hand. `runAppCreate` prints this, gated on `!ownerIsOrg`, right after listing the Application repository's files — the one addition the ticket's "closing-output line" instruction calls for in `internal/cli/app.go`.

## Testing seams

`iidp ci set-image` is driven through the CLI seam (`cli.Run`/`cli.RunWith`) like every other command, against the same local bare Platform repository fixture `app_create_test.go` already established, extended with `platform.yaml`'s new `githubApp` block. The installation-token endpoint is faked with a small `httptest.Server` that verifies the incoming JWT's RS256 signature against a freshly generated test key pair and its `iss` claim, using nothing but the standard library — the same verification a real GitHub would perform, run against `iidp`'s own signer.

**Proving the minted token reaches the git push.** The ticket allows two approaches: asserting through "the existing credential seam", or through a fake server's `Authorization` header on a repository read. The second was not chosen: with git-based clone/commit/push (required by "the same retry-on-moved-main logic as `app create`", which is specifically about `git.ErrPushRejected`, a non-fast-forward push rejection with no GitHub-REST-API equivalent), the Platform repository fixture is a local bare repository over `file://`, and `docs/implementation-notes/10-cli-platform-repository.md` already notes that "for `file://` remotes (the tests) the helper is configured and never consulted" — there is no `Authorization` header to observe. Making one observable would mean standing up a smart git HTTP server (`git http-backend` via `net/http/cgi`, checking Basic Auth before delegating) purely to assert one credential value, which is a lot of fragile machinery for this one fact. Chosen instead: `Dependencies.CIAuthObserved func(token string)`, a small test-only hook in the same spirit as the pre-existing `Dependencies.BeforePush`, called with the token right before it becomes the `git.Auth` used for the clone-edit-commit-push cycle. A test sets the fake server to return a known token and asserts `CIAuthObserved` received exactly it, then separately confirms the whole command still succeeds and writes the expected tag — proving both halves (the right token was minted, and the operation completed using whatever credential it was given) without needing an HTTP-authenticated git remote.

**Leaf-level tests outside the CLI seam.** Two deviate from this repository's established "no package gets its own `_test.go`; the seam is the CLI" convention (`docs/implementation-notes/11-cli-create-path.md`): `internal/githubapp/jwt_test.go` (verifying `SignJWT`'s output against a real RSA public key and exercising `PrivateKeyFromEnv`'s two sources) and `internal/templates/deploy_workflow_test.go` (parsing the rendered `deploy.yaml` for each framework with `yaml.v3` and asserting its triggers, image reference and both `set-image` invocations, per the ticket's explicit "test that the generated workflow is valid YAML" acceptance criterion). Both are pure functions of their own package's inputs and outputs — signing a JWT needs no GitHub or git faking to verify meaningfully, and neither does checking a template's rendered shape — so testing them directly, the way `internal/render`'s `Example` tests already do for the two pre-existing documents, needs no additional seam and is more direct than routing the same assertions through `cli.Run` and a fake GitHub server that would otherwise be exercised for reasons unrelated to what is being checked.

## What was not built

The org Actions variable `IIDP_DEPLOY_APP_ID` remains an unused, wizard-provided convenience (see "Where the app id and installation id actually live" above); a chart change to support `imagePullSecrets` for a private GHCR package is left to a future ticket if the visibility recommendation above is ever revisited.
