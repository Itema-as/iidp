# #18 Itema login Capability

Questions that came up while adding the Itema login Capability, and the answer chosen for each. oauth2-proxy's current documentation was checked with context7 (`/websites/oauth2-proxy_github_io_oauth2-proxy`) on 2026-09-21/22 for its Microsoft Entra ID provider, cookie/whitelist domains, the Traefik integration and the Helm chart's `values.yaml`; the chart itself (`oauth2-proxy/manifests`, release `oauth2-proxy-10.7.0`) was downloaded and its templates read directly where the docs pages left a question open.

## Chart and versions

`oauth2-proxy/manifests` at `https://oauth2-proxy.github.io/manifests`, chart `10.7.0` (appVersion `7.15.3`, oauth2-proxy's own release), the newest entry in the chart repository's `index.yaml` on 2026-09-21. Pinned in `bootstrap/versions.yaml` next to the other components, the same way and for the same reason.

## Provider: `entra-id`, not `oidc` or the legacy `azure`

The current docs (`configuration/providers/ms_entra_id`) name `entra-id` a dedicated, fully OIDC-compliant provider for Microsoft Entra ID, distinct from the older `azure` provider (which still exists but is documented as the legacy path) and from the generic `oidc` provider (which works, but `entra-id` adds Entra-specific options like `entra_id_allowed_tenants` and federated-workload-identity auth that the generic provider does not). Chosen: `entra-id`, single-tenant, with the issuer URL `https://login.microsoftonline.com/<tenant-id>/v2.0` the docs' "Configure Single-tenant App" example uses.

## Where the Entra values live, and why alphaConfig instead of the classic flags

**Question.** The Secret `oauth2-proxy/oauth2-proxy-entra` carries `clientID`, `clientSecret` and `tenant` (plus a generated `cookieSecret`). The `entra-id` provider's issuer URL has to be built from the tenant id (`https://login.microsoftonline.com/<tenant>/v2.0`); Helm cannot see inside a SOPS-encrypted Secret to build that string at render time, and the classic `--oidc-issuer-url` flag takes only a literal value.

**Choice.** oauth2-proxy's own alpha configuration schema (`alphaConfig.enabled: true`, checked against `configuration/alpha-config` and the chart's own `_helpers.tpl`), with the provider defined in `configData.providers[0]` rather than through `config.clientID`/`config.clientSecret`/the classic flags. Three chart `extraEnv` entries (`ENTRA_CLIENT_ID`, `ENTRA_CLIENT_SECRET`, `ENTRA_TENANT`, chosen names, sourced via `secretKeyRef` from the Secret) are referenced as `${ENTRA_CLIENT_ID}` etc. inside `oidcConfig.issuerURL` and the provider's `clientID`/`clientSecret` fields. This is a documented oauth2-proxy feature, not a Helm trick: the docs' "Use environment variables in YAML configuration" example shows exactly `clientSecret: ${CLIENT_SECRET}` inside `configData` for "securely inject[ing] sensitive data"; the chart's `oauth2-proxy.alpha-config` helper confirms it never runs `configData` through Helm's own `tpl` (only chart-level `annotations`/`configFile` get that), so the `${VAR}` tokens reach oauth2-proxy's own config loader untouched, which expands them against the container's environment when it reads `oauth2_proxy.yml`. `proxyVarsAsSecrets: false` turns off the chart's own classic Secret-and-env mechanism for `client-id`/`client-secret`/`cookie-secret` (which expects fixed kebab-case Secret keys this component does not use, and which alpha config bypasses anyway: with `alphaConfig.enabled`, the chart's Deployment sets `--alpha-config=...` instead of `--client-id=...`/`--client-secret=...`).

`OAUTH2_PROXY_COOKIE_SECRET` is the one classic env var kept: the cookie-signing key is not part of the alpha "providers" schema (it is a session/cookie setting, unaffected by `alphaConfig`), so it is set directly from the Secret's `cookieSecret` key via the same `extraEnv` mechanism, no `${VAR}` expansion needed since the whole value is used as-is.

## `email_domains: "*"`, logged: any account of the tenant may sign in

Chosen: left at the chart's own default (`config.emailDomains: ["*"]`, which the chart writes into a minimal auto-generated legacy config file that coexists with the alpha config — confirmed in `templates/deployment.yaml`: the Deployment always appends both `--alpha-config=...` and `--config=...` when alpha is enabled, and the helper comments describe the latter, in that case, as "a minimal legacy config (no upstreams)" carrying only `email_domains`). This is not a second, narrower filter beyond the tenant: the single-tenant issuer URL is what actually restricts sign-in to Itema's Entra tenant, so `email_domains: "*"` correctly means "any account of that tenant", not "any account anywhere".

## Cookie scope: `cookie_domains`/`whitelist_domains` the Platform base domain

`extraArgs.cookie-domain` and `extraArgs.whitelist-domain` (the current CLI flag names; the docs' `cookie_domains`/`whitelist_domains` are the config-file spelling of the same setting) are both set to `.<baseDomain>`, so the cookie oauth2-proxy issues after a successful sign-in is valid for every Environment's host under the Platform base domain — the "sign in once, reach everything protected" requirement — and the redirect-back allowlist (`whitelist-domain`) covers the same set, needed because `/oauth2/start`'s `rd` parameter and `/oauth2/sign_out`'s redirect both check against it. `redirect-url` is `https://auth.<baseDomain>/oauth2/callback`, matching exactly what the bootstrap wizard's Entra app registration already used (`docs/implementation-notes/05-bootstrap-wizard.md`), so the existing registration works unchanged.

## reverse-proxy mode and the header the Application receives

`--reverse-proxy` (trust `X-Forwarded-*` from Traefik) and `--set-xauthrequest` (add `X-Auth-Request-User`/`-Email`/`-Preferred-Username`/`-Groups` to oauth2-proxy's response) are both set. The Application receives the signed-in user's email in `X-Auth-Request-Email`, one of the `authResponseHeaders` the `itema-login` Middleware copies onto the request Traefik forwards once oauth2-proxy answers.

## The Traefik pattern: `/oauth2/auth` plus an `errors` middleware, not the root address

**Superseded by #77/#78.** This shape never redirected: the `errors` middleware's 302 carries no `Location`, so browsers rendered the sign-in page on the Application's host. ForwardAuth now points at the root address with `skip-provider-button`; the 403 described below was the sign-in page, not the static upstream. See [`77-login-redirect.md`](77-login-redirect.md).

**Question.** The acceptance criteria ask for a Traefik `Middleware` of kind `forwardAuth` pointing at `/oauth2/auth`, plus the `/oauth2/start?rd=...` (or equivalent) redirect for unauthenticated requests. Current oauth2-proxy documentation (`configuration/integrations/traefik`) shows two shapes: (a) one `forwardAuth` middleware pointed at oauth2-proxy's bare address (`https://oauth.example.com/`, not a specific path), used for routes that should "redirect all unauthenticated to oauth2 signin", relying on Traefik forwarding a redirect response from the auth server straight to the client instead of erroring; (b) two middlewares — `forwardAuth` against `/oauth2/auth` (which answers 401/403 with no redirect) chained with an `errors` middleware that rewrites that into a redirect to `/oauth2/sign_in?rd={url}`.

**First choice, and why it was reverted.** Shape (a) was tried first, on the assumption that the chart's Ingress can only ever name one middleware. It renders and the Application reaches Healthy, but a real kind run (`KIND_EXPERIMENTAL_PROVIDER=podman go test -tags e2e ./test/e2e/... -run TestBootstrap`) showed the acceptance criterion actually fails with it: an unauthenticated request to the protected fixture host came back `403 Forbidden`, not a redirect, with this component's alpha-config `static: true` upstream — the docs' root-address example most likely assumes a real (non-static) upstream behind oauth2-proxy, which is not this component's situation (nothing is ever actually proxied through oauth2-proxy; Traefik reaches the protected Application's own Service directly, so the upstream oauth2-proxy itself proxies to is a placeholder either way).

**Choice.** Shape (b). Traefik's `router.middlewares` annotation is in fact a comma-separated list (confirmed by rendering it as `oauth2-proxy-itema-login-errors@kubernetescrd,oauth2-proxy-itema-login-auth@kubernetescrd` and observing Traefik apply both), so the chart's Ingress names two Middlewares, not one: `itema-login-auth` (`forwardAuth` against `/oauth2/auth`, `authResponseHeaders` unchanged) and `itema-login-errors` (`errors`, `status: ["401-403"]`, `query: /oauth2/sign_in?rd={url}`, pointed at the oauth2-proxy Service). This is the documented, better-tested contract (`/oauth2/auth`'s 401/403 is exactly what the Nginx `auth_request`/`error_page` and Caddy `@error status 401` patterns the same docs describe are built around, and the docs call the 401-then-redirect shape "superior to returning a 403 status code, as browsers do not automatically follow redirects on 403 responses"), and it is what the local kind run in the pull request body confirms: `shop.app.example.test` (unprotected) still 200, `shop-staging.app.example.test` (protected) redirects.

## Why the Middleware is a second source on the `oauth2-proxy` Application, not a separate top-level one

The ticket asks for "a new component Application `oauth2-proxy`" (singular). ArgoCD's multi-source Applications, already used by `platform-components.yaml` (this repository's `bootstrap` chart plus the Platform repository's `platform.yaml` as a values ref) and by `platform-tls` (a small local chart at a pinned revision), are the established pattern for "one more thing this repository owns, alongside a chart from elsewhere". The Middleware needs no templating (fixed name, namespace, and service address), so it is a plain manifest, `bootstrap/components/oauth2-proxy-login/middleware.yaml`, referenced as the Application's second source (`repoURL`/`targetRevision` from `.Values.bootstrap.repoURL`/`targetRevision`, the same fields `platform-tls` already threads through from `platform.yaml`) — no mini chart needed since there is nothing to parameterise.

## kind: `oauth2Proxy.skipOIDCDiscovery`, a fixture-only `platform.yaml` field

**Question.** oauth2-proxy validates its OIDC issuer at startup by fetching the discovery document; kind has no route to `login.microsoftonline.com`, and the fixture's Entra tenant is a dummy GUID regardless. Without a working pod, Traefik's `forwardAuth` would answer with a 5xx instead of the redirect the acceptance criterion asks `TestBootstrap` to assert, which the ticket explicitly says to avoid ("prefer a running proxy").

**Options considered.** A tiny in-cluster stub serving `/.well-known/openid-configuration` and a JWKS endpoint (a second test-harness component, in the spirit of the git server built for #4, but real engineering weight for a startup check this test never exercises past the first redirect); accepting Synced-but-not-Healthy for `oauth2-proxy` in kind (rejected outright by the ticket's own wording); `--skip-oidc-discovery` (`oidcConfig.skipDiscovery` in alpha config) with manually supplied, unreachable `.invalid` endpoints (RFC 2606, the same convention `objectStorageEndpoint: https://objectstorage.invalid` already uses in this fixture for "guaranteed never to resolve, fails fast").

**Choice.** The third option, gated by a new `platform.yaml` field, `oauth2Proxy.skipOIDCDiscovery` (bootstrap-only, default `false`, documented in `bootstrap/README.md` and `bootstrap/values.yaml`), set `true` only in the fixture Platform repository — the same shape as `acme.server` already being pointed at Let's Encrypt staging there. A real Platform leaves it `false` and gets normal OIDC discovery against Entra ID, which does need a reachable issuer and does need this flag off. `skipDiscovery: true` plus three `https://oauth2-proxy-entra.invalid/...` endpoints are added to the rendered alpha config only when the field is set; they are never actually requested by `TestBootstrap`, which only proves the unauthenticated redirect to `/oauth2/start`, not a completed sign-in.

Three mistakes surfaced only by actually running the pod in kind, not by reading the docs alone, and are recorded here so they are not repeated.

1. `--set-xauthrequest` (the classic flag `oauth2-proxy.yaml` originally used to add the `X-Auth-Request-*` response headers) crash-loops the container once `alphaConfig.enabled` is set ("unknown flag: --set-xauthrequest"): the current alpha-config docs say so directly ("Using Alpha Configuration > How to inject custom headers": "legacy flags such as pass-user-headers and set-xauthrequest are incompatible and should be removed"); `injectResponseHeaders` in `configData` is the alpha equivalent, with the `values: - claimSource: {claim: ...}` nesting the docs' "Migrate Header Injections" page says became required in v7.14.0, older than the appVersion this chart installs.
2. `loginURL`/`redeemURL` are not `oidcConfig` fields the way `jwksURL` is: the alpha config loader rejects them there ("'providers[0].oidcConfig' has invalid keys: loginURL, redeemURL"), confirming the "Providers > Provider" reference's own description of "specific endpoint URLs for authentication, token redemption" as fields of the outer `Provider`, not `OIDCOptions`; they moved up one level, sibling to `oidcConfig` and `clientID`.
3. `cookie_secret` is validated by its raw string length, not its decoded length: a 44-character base64 encoding of 32 random bytes (`head -c32 /dev/urandom | base64`, what both the fixture and the wizard generated at first) was refused with "cookie_secret must be 16, 24, or 32 bytes to create an AES cipher, but is 44 bytes" — the value is read verbatim from the Secret's `stringData` key with no base64 decoding step, unlike the chart's own `openssl rand -base64 32 | head -c 32 | base64` suggestion, which is a recipe for a Kubernetes `data:` field (which Kubernetes itself decodes) and not for the raw value a `stringData` key or an env var carries. Both the wizard and the fixture now generate a 32-character (32-byte) string directly, filtered to `[A-Za-z0-9]` so it is also valid YAML and shell content with no escaping.

`oauth2-proxy` came up Healthy in kind only after all three fixes.

## Which Environment is protected in the fixture, and why not a third Application

**Question.** The ticket offers either a third, Environment-less Application `intranet` with `login.enabled: true`, or `login.enabled` on `shop-staging`.

**Choice.** `shop-staging`. Adding a third Application would need its own `applications/<name>/<environment>/{application.yaml,values.yaml}` (matched by `bootstrap/applications.yaml`'s existing glob, so no bootstrap change), but proves nothing `shop-staging` does not already prove more cheaply: `login.enabled` is an ordinary Capability toggle on a values file exactly like any Environment's, and `shop-staging` already exercises Postgres, its own address and its own migration Job, so turning login on there costs one more key in an existing fixture file instead of a new directory tree, a new namespace, and new dummy image/Postgres/backups wiring to keep it Healthy. `TestBootstrap` now asserts the split the ticket asks for directly: `shop.app.example.test` (prod, unprotected) still answers 200; `shop-staging.app.example.test` (staging, protected) gets a redirect. This also means the two Environments of one real Application can, in practice, differ on Itema login — the CLI does not force it identically onto both (`--login` covers "every Environment the Application already has" only for the run it is given on, `docs/implementation-notes/18-itema-login.md`'s own CLI section below), which this fixture happens to demonstrate rather than needing a second, purpose-built example.

## CLI: where `--login` is validated, and what it writes

Chosen: the same shape as every other Capability since #13/#17. `render.Environment` gains a `Login bool` field, written into every Environment via `render.Values`'s new `login: {enabled: false}` block (written in full, even off, the same convention `postgres`/`domains` already follow — #13's notes). `platformrepo.Application.Login` and `platformrepo.Capabilities.Login` carry it from the CLI down to `writeEnvironment` (`app create`, into every Environment being created) and `applyCapabilitiesToEnvironment` (`add-capability`, into every Environment the Application already has, prod and staging alike — unlike `Domains`, which is prod-only, `Login` is not gated by `environment == "prod"`, since one oauth2-proxy cookie for the base domain is meant to cover both). A new `render.EnableLogin` node-editing helper (`internal/render/edit.go`, the same shape as `EnablePostgres`/`SetSize`) sets `login.enabled: true` in place, preserving comments and unrelated keys, and `render.CopyValuesForStaging` needs no change: it never touches the `login` key, so a prod values.yaml with login already on carries it over to a freshly added staging Environment for free.

Refusal ("--login cannot be combined with --domain") is checked in three places, mirroring `--postgres`'s Static-site refusal: `createOptions.plan` (flag-only, before anything is cloned, for `app create`), `runAppAddCapability` (flag-only, before anything is cloned, for `--login --domain` given together on one `add-capability` call), and `platformrepo.Writer.attemptCreate`/`attemptAddCapabilities` (after the clone, the only place that can see whether a custom domain is *already* on `prod` — the same trade-off #13 documents for the Postgres bucket/endpoint check: a failure here is reported after the token/clone step, with a clear message, and nothing is written).

## The wizard's question 7, finally asked

`itemaLoginQuestion` (`internal/cli/wizard.go`) now asks "Itema login?" with the `[no]` default `docs/design.md` specifies, skipped entirely (asking nothing, printing nothing) when `len(opts.domains) > 0` — the wizard does not ask a question whose answer `plan()` would then refuse, the same reasoning already applied to Adopt stopping the wizard immediately (`docs/implementation-notes/14-cli-wizard.md`). The answer is written with `f.Set("login", ...)`, so it flows through `plan()` exactly like every other question. The summary screen (`printSummary`) and the closing output (`printCreated`, `printAddCapabilityResult`) both report it.

## Testing

Chart: `chart/application/login_test.go`, the same fixture-and-`render()` pattern as `domains_test.go`/`postgres_test.go` — the middleware annotation present only on the Platform-address Ingress when `login.enabled` (`login-enabled.yaml`), absent by default (`prod-small.yaml`), the refusal with a custom domain (`refuse-login-with-domain.yaml`, following the `refuse-*` convention), and kubeconform on the enabled fixture. Wizard: `TestAppCreateWizardFullRunAnsweringEveryQuestion` (asked, with the rest of the scripted answers each gaining one more blank line) plus the "flags pre-answer questions" and "defaults taken by empty answers" tests already covering every other question, now covering this one too — no dedicated "skipped when a domain was given" test was added beyond the CLI-seam refusal tests above, since the wizard's own skip condition (`len(opts.domains) > 0`) is a one-line guard with no state of its own to exercise separately from the flag-driven refusal it defers to. Bootstrap: `bootstrap/bootstrap_test.go`'s `TestOauth2ProxyPointsAtThePinnedChartAndPlatformValues` (both sources, the chart version pin, `cookie-domain`/`whitelist-domain`/`redirect-url`, the ingress host, `provider: entra-id`) and the updated `TestRendersOneApplicationPerComponent` list. End-to-end: `test/e2e/harness.go` gains `Cluster.CheckRedirect` (the same polling shape as `CheckHTTP200`, but expecting a 3xx and treating a 5xx as "not up yet, keep polling" rather than a hard failure, so a slow-starting oauth2-proxy pod does not flake the assertion); `TestBootstrap` waits for the new `oauth2-proxy` Application to reach Healthy alongside the other nine components, and `testFixtureApplication` asserts `shop-staging` (protected) redirects while `shop-prod` (unprotected) still answers 200.
