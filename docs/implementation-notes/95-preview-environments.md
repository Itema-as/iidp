# #95 Preview Environments from an ArgoCD ApplicationSet

This note records the choices made while building Preview Environments as [ADR-0006](../adr/0006-preview-environments-from-an-argocd-applicationset.md) designed them: `--previews` writes one ApplicationSet per Application, `applications/<name>/previews/applicationset.yaml`, whose Pull Request generator gives every open pull request labelled `preview` an Environment `<name>-pr-<number>`. The contract is in [`docs/platform-repository.md`](../platform-repository.md#applicationsnamepreviewsapplicationsetyaml-preview-environments), the developer's side in the README's "Preview Environments", the chart's in [`chart/application/README.md`](../../chart/application/README.md), the Platform's in [`bootstrap/README.md`](../../bootstrap/README.md#preview-environments).

## Sources

Checked on 2026-09-26 against ArgoCD **v3.5.3**, the appVersion of the argo-cd chart `bootstrap/versions.yaml` pins (10.9.2, `helm show chart`). Read at the tag in `argoproj/argo-cd`:

- `docs/operator-manual/applicationset/Generators-Pull-Request.md`: the GitHub fields (`owner`, `repo`, `api` "if using GitHub Enterprise", `appSecretName` "a Secret name containing a GitHub App secret in repo-creds format", `labels` "filter the PRs to those containing all of the labels listed"), `requeueAfterSeconds` (default 30 minutes), the template parameters (`number`, `branch`, `branch_slug`, `head_sha`, `head_short_sha` 8 characters or fewer, `head_short_sha_7`, `labels` for Go templates only, `author`), and the lifecycle: "Application will be removed when a Pull Request no longer meets the specified criteria".
- `applicationset/generators/pull_request.go`: the parameters exactly as above, `number` as a decimal string; `GetRequeueAfter` returns `requeueAfterSeconds` when set; `selectServiceProvider` refuses when SCM providers are disabled and checks `api` against `--allowed-scm-providers`; with `appSecretName` it builds `NewGithubAppService` from `GitHubApps.GetAuthSecret`.
- `util/github_app/repos.go` and `util/db/repository_secrets.go`: `GetAuthSecret` is `GetRepoCredsBySecretName`, which reads the Secret **by name** from the settings manager's Secret informer in the `argocd` namespace (`util/settings/settings.go`: every Secret there except cluster Secrets, `argocd.argoproj.io/secret-type!=cluster`) and parses the repo-creds keys `githubAppID`, `githubAppInstallationID`, `githubAppPrivateKey`, `githubAppEnterpriseBaseUrl`. No label is required.
- `applicationset/services/internal/github_app/client.go`: `ghinstallation.New(transport, id, installationId, key)`; with an `api` URL the installation transport's `BaseURL` is that URL and the client is `github.NewClient(...).WithEnterpriseURLs(url, url)`. So the token request goes to `<api>/app/installations/<id>/access_tokens` and the list to `<api>/repos/<owner>/<repo>/pulls` (go-github appends `/api/v3/` to an enterprise URL that does not end in it).
- `applicationset/services/pull_request/github.go`: `PullRequests.List` with GitHub's default state, open, 100 per page, following `NextPage`; the label filter is applied client-side; it dereferences `number`, `title`, `head.ref`, `base.ref`, `head.sha` and `user.login` of every pull request.
- `applicationset/utils/utils.go` (`deeplyReplace`): with Go templates every string of the template is rendered, map keys too, and a `runtime.RawExtension` such as `helm.valuesObject` is decoded, rendered string by string and re-encoded. So `{{.head_sha}}` inside `valuesObject` works, and stays a JSON string whatever its digits.
- `cmd/argocd-applicationset-controller/commands/applicationset_controller.go`: `--enable-scm-providers` defaults to true, `--allowed-scm-providers` to empty ("all"), `--policy` to empty, which is `sync` (create, update and delete).
- `docs/user-guide/helm.md`: "Order of precedence is `parameters > valuesObject > values > valueFiles`".
- `docs/user-guide/sync-options.md`, "Namespace Metadata": `managedNamespaceMetadata` needs `CreateNamespace=true`; "The generated namespace is normally not tracked with Argo CD. You can use `managedNamespaceMetadata` to set a tracking annotation on the generated namespace ... Once a namespace is owned by Argo CD, it will be managed by ArgoCD, including the possibility to delete it", with the example `argocd.argoproj.io/tracking-id: 'your-application-name:/Namespace:/your-namespace-name'`. `controller/state.go` adds the managed namespace to the comparison's targets when it carries tracking, so it is neither OutOfSync nor pruned (`isManagedNamespace`); `util/argo/resource_tracking.go` builds and parses the id as `<app>:<group>/<kind>:<namespace>/<name>`, and the default tracking method in 3.x is the annotation.
- `docs/operator-manual/applicationset/Application-Deletion.md`: the controller adds the resources finalizer to generated Applications unless `preserveResourcesOnDeletion`, and deleting the ApplicationSet deletes its Applications by owner reference.
- `docs/user-guide/directory.md`: `include` takes `{a,b}` for several patterns.
- `resource_customizations/argoproj.io/ApplicationSet/health.lua`: an ApplicationSet is Degraded on `ErrorOccurred` and Healthy on `ResourcesUpToDate`, which is what `bootstrap/applications.yaml`'s health shows.
- The argo-cd chart 10.9.2's values and `helm template` output: the ApplicationSet controller runs by default (`applicationSet.replicas: 1`, `resources: {}`), its Role can get, list and watch Secrets in `argocd`, and `argocd-cmd-params-cm` sets none of the `applicationsetcontroller.*` SCM keys.

Context7 was not used for ArgoCD: its tag's source was read directly instead, which is where the details above live (the appSecretName lookup is not in the docs at all).

## The App credential: the Secret cloud-init already writes

`appSecretName: platform-repo-github-app`. It is ArgoCD's repository Secret for the Platform repository, written by cloud-init (#41), and it holds the App's id, installation id and key under the repo-creds key names. The docs call for "a GitHub App secret in repo-creds format"; the source shows it is read by name, with no `repo-creds` label needed, so the existing Secret is the credential and nothing new is written. A second Secret labelled `repo-creds` was the alternative. It would be a second copy of the key to rotate (`infra/README.md`, "Rotating the Platform repository credential"), and the rotation reaches the generator as it is, since the settings manager's informer sees the Secret change.

The App needs **Pull requests: Read-only** (#93, done on the live App) and must be installed on the Application repositories. The live installation is on all of Itema-as's repositories. The bootstrap wizard told a new Platform to install it on the Platform repository only; it now says All repositories, since the CLI creates Application repositories later and an installation on selected repositories would miss them. That widens what the App's key can write (Contents: write on every repository, not one), which is the live Platform's situation already. The narrower alternative, selected repositories with each Application repository with previews added by an org owner, is documented in `infra/README.md` as a possibility, not the default.

## The generator: owner and name from the binding

`owner` and `repo` are `repository.yaml`'s `repository` (the name when the binding was written). The generator cannot take a repository id. `--previews` is refused without a binding: `app create` without `--path` has none (refused in the flag checks, before anything is written, naming `--path create` or `--path adopt`), and `add-capability` reads `repository.yaml` and refuses without a complete one, naming `iidp app bind`.

**After a rename.** GitHub answers API requests for a repository's old name with a 301 to the repository's new location ("Resources in the REST API", redirects; read, not tried), and Go's HTTP client follows it for a GET, keeping the Authorization header on the same host. So previews keep working after a rename, until another repository is created under the old name; from then on the generator lists that repository's pull requests. Those previews would run `ghcr.io/itema-as/<app>:<their head SHA>`, which does not exist, so nothing of the other repository runs, but the old Application's previews stop. `iidp app bind` after a rename refreshes `repository.yaml` and does not rewrite the ApplicationSet; running `iidp app add-capability` for another Capability does not either, unless it changes staging's `application.yaml`. Rewriting it from `bind` is a small follow-up if renames happen; it was left out as not asked for.

## The template: staging's Application

The template is built from staging's `application.yaml` as it is in the Platform repository, not from `platform.yaml`: its sources are copied, so

- the chart is at the version staging is pinned to ("the Application's pinned chart version"), and a hand bump of staging's pin, as the rollouts do, is not undone by the preview;
- staging's `values.yaml` is the only value file, and `$values` resolves against the Platform repository source copied with it;
- once staging has a `sops/` source, previews get it: staging's Secrets, decrypted by KSOPS the same way, applied into the preview's namespace. The Secrets keep staging's names (`<app>-staging-<key>`), which is what staging's `values.yaml` lists under `secrets`, so the chart's `envFrom` finds them.

The CLI adds the `sops/` source to staging's `application.yaml` once, when staging gets its first secret (`iidp secret set <app> staging`) or Postgres (`add-capability --postgres`). Any command that changes staging's `application.yaml` rewrites the ApplicationSet in the same commit (`platformrepo.refreshPreviews`); the rewrite is deterministic, so a command that changes nothing about staging commits nothing for previews. Rendering the ApplicationSet with a `sops/` source unconditionally was rejected: ArgoCD fails a source whose path does not exist, and staging has none until its first secret. Having the ApplicationSet not copy the sources but rebuild them from `platform.yaml` was rejected for the pinning reason above. A staging `application.yaml` that is not the shape the CLI writes (no single chart source whose value file is staging's, or no `ref: values` source) is refused rather than guessed at.

The overrides are `helm.valuesObject`, which ArgoCD applies over `valueFiles`: `environment: pr-{{.number}}`, `image.tag: '{{.head_sha}}'`, `size: small`, `domains: []`, `runTasks: false`, `login.enabled: true`, `postgres.backups: false`. Helm merges maps, so `login.groups`, `image.repository`, `postgres.enabled` and `postgres.migrationCommand` stay staging's. `helm.parameters` was the alternative: it cannot set an empty list, and a SHA of digits would need `forceString`.

`goTemplate: true` with `missingkey=error`, so a misspelt parameter fails the ApplicationSet instead of rendering `<no value>`. `head_sha`, not `head_short_sha`: the workflow tags the image with the full SHA, like every other SHA tag on the Platform.

**Labels.** The generated Application carries `iidp.itema.no/application: <app>` and `iidp.itema.no/environment: pr-<number>`, the labels every Environment's ArgoCD Application has; `iidp app status` (#94) finds Environments by them. The ApplicationSet itself carries only `iidp.itema.no/application`.

## The chart

- **`environment: pr-<number>`.** `application.environment` accepts `pr-` followed by a number without leading zeros, so `fullname`, the host and every label follow as they do for staging. The chart now refuses an Environment whose `<name>-<environment>` is over 63 characters: a 55-character name, which the chart allows, with `-pr-12345` would make a Service name and DNS label too long. The CLI's 40-character names leave room for a nine-digit pull request number.
- **`postgres.backups`** (default `true`) is the "no backups" flag the issue asked for, and one flag for all of it, since a preview has no use for any part: `false` renders no `plugins` on the `Cluster` (so no WAL archiving and no sidecar), no `ObjectStore`, no `ScheduledBackup`, and no final Backup hook with its ServiceAccount, Role and RoleBinding. That is how the PreDelete hook is disabled: it is simply not rendered, so ArgoCD has no hook to wait for when the preview is deleted. `platform.backupsBucket` and `objectStorageEndpoint` are no longer required with it off. A separate flag for the final backup was considered; nothing would ever set the two differently.
- `runTasks: false` (#91) and `login.groups` (#92) needed nothing new.

## Deletion: the namespace goes with the preview

The issue asks that closing the pull request removes the preview's namespace and database. ArgoCD deletes an Application's resources through the resources finalizer, but a namespace made by `CreateNamespace=true` is not one of them: every other Environment's namespace stays after `iidp app delete` (the e2e's guardrails test relies on shop-staging's staying). The template therefore puts ArgoCD's tracking annotation on the namespace through `managedNamespaceMetadata`, `argocd.argoproj.io/tracking-id: <app>-pr-{{.number}}:/Namespace:/<app>-pr-{{.number}}`, the way ArgoCD's sync-options documentation gives for a namespace ArgoCD should own. ArgoCD then treats it as the preview's resource, keeps it Synced (it compares it with a namespace built from `managedNamespaceMetadata`) and deletes it with the preview. Deleting the namespace takes the database with it, and there is no hook to wait for.

Rendering a `Namespace` from the chart was the alternative. It would need a value to render it only for previews, the labels written in the chart as well as in the ApplicationSet, and a sync wave before the `sops/` Secrets' -2; and a Namespace in the manifests replaces `managedNamespaceMetadata` (the same documentation). The annotation needs none of that. The documentation calls a hand-set tracking annotation "at the user's own risk" in general because a namespace may be shared; a preview's namespace is its own by construction.

The namespace keeps the labels every Environment's has (#90), with `iidp.itema.no/environment: pr-<number>`, so the admission policies and Pod Security bind to it.

## The ApplicationSet controller and the bootstrap

The controller already ran: the argo-cd chart enables it by default, in cloud-init's render and the `argocd` Application's alike. The bootstrap now sets it explicitly, `replicas: 1`, requests 10m CPU and 64Mi, limit 256Mi memory (the chart sets none). 10m is what the Deploy gate and the backup sidecar were given for the same reason: the node and the kind runner are near their CPU request ceiling. Its memory in kind has not been measured beyond the test passing; watch it for OOM kills.

`bootstrap/applications.yaml` (written by the wizard, carried by the fixture) now includes `{*/*/application.yaml,*/previews/applicationset.yaml}`, so the same app-of-apps applies ApplicationSets. A second root Application in the bootstrap chart would have arrived with the pin bump and needed no edit on the live Platform, but it would need the Platform repository's URL in the bootstrap values and be a second thing watching `applications/`. The live Platform's `applications.yaml` needs the one-line edit at rollout.

## The reusable workflow

A `preview` job in `.github/workflows/application-deploy.yaml`, run only for `pull_request` events whose pull request has the `preview` label, and, for `labeled` events, only when the label added is `preview` (another label changes nothing about the image). It checks out `github.event.pull_request.head.sha` (the default for a `pull_request` event is the merge commit, whose SHA the generator never reports), builds and pushes `ghcr.io/<owner>/<app>:<head SHA>`, and calls nothing: no `iidp`, no `id-token`. The `build` and `promote` jobs' conditions exclude pull requests already (`refs/pull/...` is neither `main` nor a tag). The caller template gains `pull_request: types: [opened, synchronize, reopened, labeled]`. A pull request without the label starts a run whose jobs are all skipped, which GitHub does not bill. The reusable workflow's contract with callers (#74) is unchanged for a caller without the trigger: it never gets pull request events, and has no previews' images.

Not handled: a pull request from a fork, whose `GITHUB_TOKEN` cannot write packages, so its push fails. Application repositories are private and org members push branches, so this is unlikely. The preview waits in `ImagePullBackOff` until the image exists, whether because the build is still running or because it failed.

## CLI

- `--previews` on `app create` needs `--staging` and `--path create` or `--path adopt`; the refusals come from the flag checks, before anything is created, with "previews use staging's secrets; add --staging first" and "... bound to none: give --path create or --path adopt". The Writer checks both again.
- `--previews` on `add-capability` needs a staging Environment, already there or `--staging` in the same run (the ApplicationSet is rendered last, from the new staging's `application.yaml`), and a complete binding. A second `--previews` is refused as already present. The commit subject names the Capability `previews`.
- The wizard asks right after the staging question, only when staging is on and the path is Create or Adopt (without a path the answer could only be refused). The summary and the closing output print `https://<name>-pr-<number>.<baseDomain>`.
- `app delete` removes the ApplicationSet in the same commit, and says so. Staging's `values.yaml` and `sops/` stay, as for every Environment, which the previews still render from while ArgoCD deletes them.
- `platform.yaml` gains `githubAPI`, read by the CLI and written as the generator's `api` when set. It exists for GitHub Enterprise and for the kind fixture, where it points at the fake GitHub.

Not guarded: an Application named `<app>-pr-<n>` would have the same prod address as `<app>`'s preview `<n>`. The same was already true of an Application named `<app>-staging` and `<app>`'s staging.

## What the rollout (#96) has to do

1. Release, then bump the bootstrap pin (the controller's resources) and `chartVersion` in `platform.yaml`.
2. In the Platform repository, change `bootstrap/applications.yaml`'s `include` to `'{*/*/application.yaml,*/previews/applicationset.yaml}'`.
3. Check the `iidp-deploy` installation covers the Application repositories that get previews (the live one is on all repositories) and has `pull_requests: read` (#93).
4. For `hello`: bump staging's chart version in `applications/hello/staging/application.yaml` to the release (an older chart refuses `environment: pr-<n>`), then `iidp app add-capability hello --previews`.
5. Add the `pull_request` trigger to `hello`'s `.github/workflows/deploy.yaml` (README, "Preview Environments"), and to `iprofil`'s if it gets staging and previews later.
6. Label a pull request on `hello` `preview`: within 3 minutes `hello-pr-<n>` appears, runs the head SHA's image once the workflow has pushed it, and redirects to sign-in; unlabel or close it and `hello-pr-<n>` and its namespace go.
