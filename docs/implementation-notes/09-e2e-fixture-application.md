# #9 Platform end-to-end: fixture Application in kind

Questions that came up while giving the fixture Platform repository an Application with staging and prod Environments, and extending the kind end-to-end test to prove the whole Platform path. ArgoCD sources were checked with context7 on 2026-09-21.

## The gap: nothing reads `applications/`

The bootstrap's root Application (`platform`) syncs only `bootstrap/` of the Platform repository, non-recursively (#4's notes, "How platform.yaml reaches the bootstrap"). `docs/platform-repository.md` describes `applications/<name>/<environment>/application.yaml` as what the CLI writes, but nothing made ArgoCD notice it.

**Options.**

1. Recurse the root Application into the whole Platform repository. Rejected: it would also try to apply `platform.yaml`, `.sops.yaml` and anything else at the root as plain manifests, and the two-files-only contract (#4) would have to be redefined.
2. An `ApplicationSet` with a git directory generator (`applications/*/*`), templating one Application per match. The generator syntax is closer to a glob over directories than over files, so it would need one more piece to filter down to Environments that actually carry an `application.yaml`; and it needs the ApplicationSet controller (installed as part of ArgoCD's core manifests, so no new component to bootstrap) and its own CRD, RBAC and reconcile loop for a case this repository never needs across clusters or many unrelated repositories.
3. A third file `bootstrap/applications.yaml`, a plain ArgoCD Application with a directory source on the Platform repository itself: `path: applications`, `directory: {recurse: true, include: '*/*/application.yaml'}`. Confirmed against the current Argo CD documentation (`user-guide/directory`): `include` is a glob matched against paths under `path`, and `recurse: true` is required for it to look inside subdirectories at all.

**Choice.** Option 3, `bootstrap/applications.yaml`. It is one more file of the same kind the Platform repository already carries by hand (`platform-components.yaml`, `platform-secrets.yaml`), needs no new component, and the include glob matches the CLI's layout exactly: `applications/<name>/<environment>/application.yaml`, nothing else in each Environment's directory (`values.yaml` alongside it is not itself a manifest, so it must not match). Every Environment's Application becomes a child of it, the same app-of-apps shape one level up. Documented in `bootstrap/README.md` and `docs/platform-repository.md`; the fixture Platform repository (`test/e2e/fixtures/platform-repo/bootstrap/applications.yaml`) carries it, and the end-to-end test proves it.

## The `default` AppProject needs nothing added

The ticket asked to verify what the `default` project must permit: both of an Environment's sources (the chart repository and the Platform repository) and any destination namespace. Checked with context7 against the current Argo CD documentation (`user-guide/projects`, "The Default Project"): the `default` project, created automatically by ArgoCD's own install manifest, starts fully permissive (`sourceRepos: ['*']`, every destination, every resource kind) and nothing in `bootstrap/` narrows it. So `bootstrap/applications.yaml` and every Environment's Application, using `project: default`, already have everything they need; no `AppProject` was added.

## The fixture Application

One Application, `shop`, with `prod` and `staging` Environments under `applications/shop/<environment>/{application.yaml,values.yaml}`, in exactly the shape `docs/platform-repository.md` describes with one deviation, documented there and in the files themselves:

**Chart source.** kind has no GHCR. The harness already serves this repository in-cluster (`iidp.git`, for the bootstrap); the fixture's `application.yaml` points its first source at the same repository, `path: chart/application`, instead of the OCI reference, keeping the second source (`ref: values`, `$values/applications/shop/<environment>/values.yaml`) identical to what the CLI writes. `TestBootstrap` now serves `chart/` from `iidp.git` alongside `bootstrap/` for this reason. An in-cluster OCI registry (`helm push` to a registry Pod) was the alternative; rejected as more moving parts for the same proof, since ArgoCD's multi-source Helm-from-git path is already exercised by the bootstrap itself.

**Image.** The chart runs the same image for the Deployment and the migration Job (`chart/application/templates/migration-job.yaml`), so it has to both answer HTTP 200 on `/` and provide a shell the migration command runs with `sh -c`. `nginx:1.27-alpine` (`docker.io/library/nginx`): a real, public, multi-arch tag; nginx answers 200 on `/` with its default page; being Alpine-based, it carries busybox, which provides `sh`, `nc` and `wget` without adding anything to the image. `traefik/whoami`, the ticket's other suggestion, was tried and rejected: it is a single static binary on `scratch` with no shell, so `sh -c "<migrationCommand>"` cannot even start.

**Migration command.** `test -n "$DATABASE_URL" && nc -z -w 5 <cluster>-db-rw 5432 && echo migrated`, where `<cluster>-db-rw` is the CloudNativePG read-write Service the chart's naming convention produces (`shop-db-rw` for prod, `shop-staging-db-rw` for staging, from `chart/application/README.md`, "Names and addresses" and #7's notes). It fails if `DATABASE_URL` is unset (the Secret the Deployment also reads from was never created) and fails if the database is not accepting connections, which is what "proves DATABASE_URL is set and the database reachable" needs without adding a Postgres client the image does not have. `psql`, the ticket's other suggestion, was rejected for the same reason as needing two different images would be: nginx does not carry it, and adding it (a `postgresql-client` package layered onto the Application's image) would no longer be "trivial".

**Object Storage.** `platform.backupsBucket: iidp-backups` and `platform.objectStorageEndpoint: https://objectstorage.invalid` in both Environments' `values.yaml`, the two values the chart requires with `postgres.enabled` (`chart/application/templates/postgres-objectstore.yaml`). `.invalid` is the DNS TLD RFC 2606 reserves for exactly this (guaranteed never to resolve), so the plugin's calls against it fail fast rather than hanging on a real but wrong host. The Secret the `ObjectStore` references, `backups-credentials` (`platform.backupsCredentialsSecret`'s default), does not exist anywhere in kind; at the time this ticket was implemented, the harness created it by hand with dummy `ACCESS_KEY_ID`/`ACCESS_SECRET_KEY` values in both `shop-prod` and `shop-staging`, ahead of ArgoCD's own `CreateNamespace=true` (`Cluster.CreateNamespace`, `Cluster.CreateBackupsCredentialsSecret` in `test/e2e/harness.go`), so the `Cluster` and `ObjectStore` render against a Secret that exists from their first reconcile.

**Superseded by #42.** The harness no longer creates this Secret by hand: the fixture Application's `sops/` directories now carry a copy of `bootstrap/templates/backups-credentials.enc.yaml`, applied by each Environment's own ArgoCD Application (`Cluster.CreateBackupsCredentialsSecret` and the manual `Cluster.CreateNamespace` calls for `shop-prod`/`shop-staging` are both removed); see [`docs/implementation-notes/42-backups-credentials.md`](42-backups-credentials.md).

**Whether Healthy is still reachable.** It is, without any chart change. ArgoCD 3.5.3 registers a health check only for `postgresql.cnpg.io/Cluster` (#7's notes); `ScheduledBackup` and the `Backup` it creates (`immediate: true` takes one as soon as it exists) have none, and CloudNativePG's own cluster phase reflects instance state, not WAL-archiving or backup success, so continuous archiving and the scheduled backup failing against `objectstorage.invalid` do not turn the Cluster, or the Environment's Application, unhealthy. Observed in a local run (see the pull request body for the tail of its output): both `shop-prod` and `shop-staging` reach Synced and Healthy with the dummy credentials in place.

## Test layout

Extended `TestBootstrap` (`test/e2e/bootstrap_test.go`) rather than adding a second test function: the ticket's own parenthetical allows either, and a second function would either create a second cluster (the fifteen-minute budget does not allow it) or need package-level state to share one, for no benefit over a second wait inside the same test. The added steps are factored into `testFixtureApplication`, called once the nine platform components are Healthy: wait for `applications`, `shop-prod` and `shop-staging` to be Synced and Healthy, then for each Environment assert its migration Job's `.status.succeeded >= 1` (`Cluster.WaitForJobSucceeded`) and HTTP 200 through Traefik with a `Host` header (`Cluster.CheckHTTP200`, HTTPS on the harness's mapped port with certificate verification disabled: kind's Traefik falls back to its own default certificate since no DNS-01 issuer can complete in kind, so there is nothing valid to verify against).

`go test -tags e2e ./test/e2e/... -run TestBootstrap -v -timeout 23m` and the `kind` job's `timeout-minutes: 25` in `.github/workflows/e2e.yaml` are both raised from the bootstrap ticket's 18m/20m to leave room for the fixture Application's CloudNativePG cluster, migration and rollout on top of the nine platform components; the actual run stays well under the fifteen-minute ceiling the ticket sets (see the pull request body).

## What was not touched

`chart/application` needed no change: the migration Job, the `Cluster` and the `ObjectStore` already render exactly what the fixture needs, and Healthy is reachable with dummy Object Storage credentials as recorded above. No `secrets:` were added to either Environment's values file; both the Deployment and the migration Job need only `DATABASE_URL`, which the chart injects.

## CI ran into a real CPU ceiling, and how it was closed

The first CI run failed with the Deployment Pod of one Environment stuck `Pending`; the harness's `DumpDiagnostics` (`test/e2e/harness.go`, extended with a `FailedScheduling` events dump and the node's allocated-resources table for exactly this) named the cause: `0/1 nodes are available: 1 Insufficient cpu`, with `kubectl describe node` showing CPU requests at 1820m of roughly 2000m allocatable (a private repository's hosted runner is 2 vCPU) before that Pod's own 250m could fit. This is real: the nine platform components plus two Postgres-backed Environments (`250m` CNPG `Cluster` and `250m` Deployment each, both fixed, Guaranteed-QoS chart conventions from #7 and the sizes table) add up to within about 70-100m of the runner's ceiling, a margin too thin to rely on. Local runs on this laptop's 6-vCPU, 12 GB podman machine never hit it.

**Choice.** Scale kind's CoreDNS Deployment to one replica right after cluster creation (`Cluster.Create` in `test/e2e/harness.go`), freeing the ~100m CPU and ~70Mi memory kind's default second replica claims: kind stands in for a node the Platform does not need two CoreDNS replicas' worth of DNS capacity for, unlike a real multi-node cluster. This is a kind-only harness adjustment in the same spirit as the NodePort and `ingressendpoint.ip` overrides #4 already makes for Traefik; it touches nothing `chart/application` or `bootstrap/` renders, so it changes nothing about what is being proven. Rejected: lowering `chart/application`'s fixed Postgres or size resource requests, which are Platform-wide conventions calibrated for the real Hetzner node (#7's notes), not for a CI runner sharing its 2 vCPU with the whole control plane; and a second, larger GitHub-hosted runner, not available on a private repository without a paid plan, which is outside this ticket's scope to provision.

After the CoreDNS change, one CI run still failed, but not on CPU (allocated resources showed only 67%): ArgoCD's own self-management sync (`argocd.argoproj.io/sync-options: Replace=true,Force=true`, #4's notes) had not finished after ten minutes, so `platform-secrets` (which needs KSOPS from the completed `argocd` Application) and `platform-tls` (cert-manager not yet healthy) were still waiting too. This is a pre-existing latency the bootstrap ticket's own ten-minute budget already carries, unrelated to this ticket's addition; a retry of the same commit passed in 363s (6 minutes), the tail pasted in the pull request body. It is noted here rather than fixed because widening #4's own wait budget is not this ticket's file to own.
