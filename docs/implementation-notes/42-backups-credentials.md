# #42 Object Storage credentials and endpoint reach every Postgres Environment

Questions that came up while wiring the Platform's Object Storage credentials from the bootstrap wizard through to every Environment's Postgres Capability, and the answer chosen for each. `sops`'s own documentation and behaviour were checked directly (by encrypting and decrypting fixture documents) on 2026-09-22.

## `objectStorageEndpoint` was already almost entirely wired

`internal/platformrepo.Config.ObjectStorageEndpoint`, the chart's `platform.objectStorageEndpoint`, `render.Values`'s `platformValues`, and the fixture Platform repository's `platform.yaml`/`applications/shop/*/values.yaml` were all added by #13, whose notes ("`objectStorageEndpoint` is a new `platform.yaml` field") anticipated this ticket. The one missing piece was the bootstrap wizard itself: nothing in `scripts/bootstrap-wizard.sh` asked for or wrote it. This ticket's CLI-side work is therefore small (`docs/platform-repository.md` and `bootstrap/README.md` already documented the field); the wizard is where the real gap was.

## Deriving `objectStorageEndpoint` from `location`, not asking for it outright

**Question.** The ticket asks for the endpoint to be "derived from the `location` tfvar with an override prompt."

**Where `location` already lives.** `infra/state-bucket/variables.tf` already declares `location` (default `hel1`, validated against `fsn1`/`nbg1`/`hel1`, "keep it in the same location as the node") -- it is where the buckets, `backupsBucket` included, are actually created. The wizard did not ask for it before this ticket: `infra/state-bucket/terraform.tfvars.example` shows it commented out, left at its default unless a Platform admin edits the tfvars file by hand.

**Choice.** `stage_hetzner` now asks for `location` (default: whatever is already in `infra/state-bucket/terraform.tfvars`, or `hel1`), writes it with `tfvar_set` the same as every other tfvar, and then asks for `objectStorageEndpoint` with the derived default `https://<location>.your-objectstorage.com` -- an ordinary `ask` call, so pressing Enter accepts the derivation and typing something else overrides it outright, the "override prompt" the ticket asks for. Both questions live in `stage_hetzner`, next to the Object Storage keys they are collected alongside, rather than in `stage_platform_repo` where `platform.yaml` is actually written: `BACKUPS_BUCKET` already follows this split (asked in `stage_platform_repo`, since it is not a `terraform.tfvars` value at all, only a `platform.yaml` one), but `location`, unlike `backupsBucket`, is a real OpenTofu variable that also has to reach `infra/state-bucket/terraform.tfvars`, so it belongs where every other tfvar-backed question already lives.

## Where the file lives: `bootstrap/backups-credentials.enc.yaml`, not `bootstrap/sops/`

**Question.** Every other Platform secret the wizard writes lives under `bootstrap/sops/`, applied wholesale by `bootstrap/platform-secrets.yaml` into the Platform's own component namespaces (`argocd`, `cert-manager`, `external-dns`, `monitoring`, `oauth2-proxy`). The backups-credentials Secret needs to reach every Postgres-enabled Environment's own namespace instead -- namespaces `bootstrap/platform-secrets.yaml` knows nothing about and must never apply into.

**Choice.** `bootstrap/backups-credentials.enc.yaml`, a sibling of `bootstrap/sops/` rather than a file inside it. Nothing in `bootstrap/` applies it: it is a template the CLI reads and copies, the same way `internal/templates`' framework templates are read and rendered rather than applied anywhere directly. `.sops.yaml`'s creation rules gained a second entry, `path_regex: bootstrap/backups-credentials\.enc\.yaml$`, alongside the existing `bootstrap/sops/.*\.enc\.yaml$` one, both naming the same age key -- `sops --encrypt --in-place` (the wizard's own invocation, no explicit `--age`/`--encrypted-regex` flags, `docs/implementation-notes/05-bootstrap-wizard.md`'s "Secrets on disk") resolves the right rule from the path alone.

## Byte-for-byte copy is safe: confirmed, not assumed

**Question.** The CLI holds no private key (`docs/platform-repository.md`, "Secrets") and could not re-encrypt the file for a new path even if it wanted to. Does SOPS bind a document's MAC to the path it was encrypted for, the way `--filename-override` (`internal/sops.Binary.Encrypt`, #16's notes) might suggest?

**Confirmed directly.** A plaintext Secret was encrypted with `sops --encrypt --filename-override bootstrap/backups-credentials.enc.yaml ...`, then copied unmodified to `applications/shop/prod/sops/backups-credentials.enc.yaml` and decrypted from there with `SOPS_AGE_KEY_FILE` pointed at the fixture private key: it decrypts to the identical plaintext, with no warning or error about the path having changed. `--filename-override` only ever affects which `.sops.yaml` creation rule a stdin-sourced encryption matches (#16's notes) -- it plays no part in the MAC, which covers the document's values, not its metadata. This is asserted directly, not just narrated, in two places: `internal/cli/app_postgres_backups_credentials_test.go` (`assertBackupsCredentialsCopied`, which decrypts the copy at its new `applications/<app>/<environment>/sops/` path) and `test/wizard/run.sh` ("write_backups_credentials decrypts unchanged after being copied to a different path"), both against the real `sops` binary when it is on `PATH`.

## `values.yaml`'s `secrets:` list is left alone

The chart reads this Secret through `platform.backupsCredentialsSecret` (`chart/application/values.yaml`, unchanged since #7), not through `envFrom`/`secrets:` the way a developer's own `iidp secret set` secrets are mounted. `copyBackupsCredentials` (`internal/platformrepo/backups.go`) therefore never calls `render.AddSecretName`: adding it to `secrets:` would mean nothing to the chart and would misdescribe how the Secret actually reaches the Environment.

## Registering the copy: reusing `iidp secret set`'s own machinery

`copyBackupsCredentials` writes the file, then rewrites `kustomization.yaml` and `ksops.yaml` (`render.SopsKustomization`, `render.KsopsGenerator`, from a fresh directory listing, exactly as `platformrepo.Writer.writeSecrets` already does for `iidp secret set`) and calls `render.AddKustomizeSource` to add the Environment's `sops/` directory as a third `application.yaml` source -- the same function `iidp secret set` calls, matched by path and so already idempotent: an Environment that already has another secret set (and so already has this source) gets no duplicate when Postgres is enabled afterwards, and the reverse (Postgres enabled first, then a developer's own secret set later) leaves exactly one source too. This is why no chart change and no new `render` function were needed: the KSOPS layout and the third-source mechanism `docs/platform-repository.md`'s "Secrets" section already describes accept an arbitrary set of `*.enc.yaml` files in the directory, and this file is simply one more.

## Refusal happens before any write, for every path that needs the file

`checkBackupsCredentialsPresent` runs in `Writer.attemptCreate` right after the existing `backupsBucket`/`objectStorageEndpoint` check (`app.Postgres`), and in `Writer.attemptAddCapabilities` for both `caps.Postgres` (enabling Postgres this run) and `caps.Staging && prod.Postgres.Enabled` (adding a new staging Environment when Postgres is already on, which will need the file copied into that new Environment even though `--postgres` itself was not passed this time). Both checks run immediately after `LoadConfig`, before anything is written to the clone, matching the existing `backupsBucket`/`objectStorageEndpoint` check's own placement (#13's notes, "Postgres bucket/endpoint check ... in the same place ... the existing `chartVersion` check already runs"). The error names the file's exact path and points at the bootstrap wizard, the same shape every other "missing prerequisite" error in this codebase takes.

## Which Environments get the file: Postgres's own uniformity rule, reused

#17's notes already established that `add-capability`'s "already present" checks read only `prod`'s state, on the assumption that Postgres (like every other Capability this command manages) is uniform across an Application's Environments by construction. This ticket reuses exactly that assumption to decide which Environments need `backups-credentials.enc.yaml` copied:

- In the loop over `envs` (`prod`, and `staging` if it already exists), the file is copied whenever `caps.Postgres` is being newly enabled in this call -- applying uniformly to every Environment the loop touches, since Postgres is always turned on for all of an Application's existing Environments together.
- When `--staging` adds a brand new Environment, the file is copied there whenever Postgres is enabled at all once this run's edits land (`caps.Postgres || prod.Postgres.Enabled`) -- covering both "Postgres and staging added in the same command" and "staging added later, to an Application that already has Postgres."

An Environment that already had Postgres enabled from an earlier run, and is not otherwise touched by this one, is not re-copied: it already has the file from whichever run turned Postgres on.

## The kind end-to-end fixture: one credentials file, shared by both Environments

**What changed.** `test/e2e/fixtures/platform-repo/bootstrap/backups-credentials.enc.yaml` now carries the harness's real MinIO root credentials (`MinIOAccessKey`/`MinIOSecretKey`, `iidpe2e`/`iidpe2epassword`, unchanged constants from #39), SOPS-encrypted for the fixture age key. Both `applications/shop/prod/sops/` and `applications/shop/staging/sops/` carry an identical byte-for-byte copy of it, each with its own `kustomization.yaml`/`ksops.yaml` and third `application.yaml` source -- exactly what `iidp app create --postgres --staging` would itself produce. `test/e2e/harness.go`'s `CreateBackupsCredentialsSecret` (the dummy pair) and `CreateMinIOBackupsCredentialsSecret` (the real pair) are removed; `TestBootstrap` no longer creates either namespace or Secret by hand, or calls `CreateNamespace` for `shop-prod`/`shop-staging` at all -- ArgoCD's own `CreateNamespace=true` sync option creates them, and the Secret arrives through each Environment's own third source at the same time as the Cluster and ObjectStore that reference it.

**Why the same file for both, even though prod's endpoint stays unreachable.** #9 and #39 left `shop-prod`'s `platform.objectStorageEndpoint` at `https://objectstorage.invalid` (RFC 2606, guaranteed to fail fast) and only pointed `shop-staging` at the harness's real MinIO, because only staging's final-Backup PreDelete hook (#39) needs a backup to genuinely complete; prod's Cluster only needs to reach Healthy, which it does regardless of whether its ObjectStore's credentials are real. Nothing about this ticket changes that split -- `testFixtureApplication`'s and `testDeleteEnvironment`'s existing assertions are exercised unchanged. Giving prod the *same* credentials file as staging, rather than inventing a second, dummy-valued fixture file, is simpler to maintain (one canonical fixture file, referenced from three places: `bootstrap/`, `applications/shop/prod/sops/`, `applications/shop/staging/sops/`) and costs nothing: prod never reaches `objectstorage.invalid` to authenticate with anything, real or dummy, so which credentials it carries is moot. This also matches what a real Platform does -- one `bootstrap/backups-credentials.enc.yaml`, copied unmodified into every Environment regardless of what that Environment's own `objectStorageEndpoint` happens to be.

**Sync-wave timing, unproven but consistent with prior art.** The copied Secret (`render.SecretDocument`, `argocd.argoproj.io/sync-wave: "-2"`, unchanged) lands at the same wave as `postgres-cluster.yaml`/`postgres-objectstore.yaml` (also `-2`, #7's notes), rather than a wave earlier: this is the same relationship `iidp secret set`'s own per-key secrets already have to the migration Job's wave `-1` (one wave *before* the Job, not before the Cluster), and the harness previously avoided the question entirely by creating the Secret ahead of ArgoCD's first reconcile (`CreateBackupsCredentialsSecret`, before `ApplyRootApplication`). Removing that head start means the Secret and the Cluster/ObjectStore that reference it are applied together for the first time in this ticket's design; ArgoCD's automated sync policy (`selfHeal: true`, unlimited retries with backoff, `docs/implementation-notes/04-bootstrap.md`) is relied on to converge if the very first reconcile attempt races the Secret's creation against the ObjectStore's validation. The kind end-to-end run (this ticket's own local run, pasted in the pull request body) reached Healthy for both Environments within the existing ten-minute budget, so this was not observed to be a problem in practice; it is recorded here as a design point worth revisiting only if a future run shows otherwise.

## Testing

CLI seam (`internal/cli/app_postgres_backups_credentials_test.go`): create with `--postgres` (prod only, and with `--staging`), the refusal when the file is missing (naming it and the wizard, nothing written), add-capability `--postgres` on an Application with no secrets and on one that already has another secret set (asserting the pre-existing secret's file and `ksops.yaml` entry both survive, and the `application.yaml` source is not duplicated), and add-capability `--staging` alone when prod already has Postgres. Every test that asserts the copy is byte-for-byte reads the real fixture file directly (`test/e2e/fixtures/platform-repo/bootstrap/backups-credentials.enc.yaml`, `testBackupsCredentialsPath`) rather than a duplicated literal, so the CLI is proven against the exact bytes a real bootstrap wizard run (and the e2e fixture) would carry; the decrypt assertions skip cleanly when `sops` is not on `PATH`, the same convention `docs/implementation-notes/16-cli-secret-set.md` established. `newPlatformRepository` (the shared CLI-seam test helper) now seeds `bootstrap/backups-credentials.enc.yaml` in its one "Seed the Platform repository" commit by default, since most `--postgres` tests need it present; `newPlatformRepositoryWithoutBackupsCredentials` is the explicit opt-out for the tests that assert its absence.

Wizard (`test/wizard/run.sh`): fake-mode assertions that `stage_hetzner` derives `objectStorageEndpoint` from the default location, from a non-default one, and honours an explicit override; that `write_platform_yaml` writes the field; and, gated on `age-keygen`/`sops` being installed (the existing "sops round-trip" section), that `write_backups_credentials` produces a document `sops --decrypt` reproduces with no `namespace` line, that the same document decrypts unchanged after being copied to a different path, and that a second call with unchanged Object Storage keys leaves the existing file untouched (`OBJECT_STORAGE_KEYS_CHANGED=0`).
