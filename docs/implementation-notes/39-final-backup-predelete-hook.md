# #39 Chart: final Postgres backup as an ArgoCD PreDelete hook

Questions that came up while replacing #17's two-commit final-backup design with an ArgoCD `PreDelete` hook the chart itself renders, and the answer chosen for each. ArgoCD's current documentation (`sync-waves.md`, the "stable" branch) was checked with context7 (`/websites/argo-cd_readthedocs_io_en_stable`, "PreDelete hook annotation resource hooks deletion of Application" and "argocd.argoproj.io/hook annotation values PreSync Sync PostSync PreDelete hook-delete-policy") on 2026-09-22.

## PreDelete hooks, confirmed

A resource annotated `argocd.argoproj.io/hook: PreDelete` is created only when the Application itself is deleted, never during an ordinary sync (pruning included): "PreDelete hooks execute exclusively during Application deletion before any application resources are removed." ArgoCD "waits for all PreDelete hooks to reach a Healthy state before proceeding with resource deletion and hook cleanup"; "If a PreDelete hook fails, Application deletion is blocked and enters a DeletionError condition. Deletion can proceed once the hook manifest is fixed in Git or the failing hook resource is manually deleted." This is exactly the guarantee #17's design was missing: the previous two commits (final Backup, then Environment removal) were pushed together and ArgoCD reconciled their effects independently, with no ordering between "the Backup finishes" and "the Environment's Application is noticed deleted." A `PreDelete` hook makes ArgoCD itself the thing that orders them.

`argocd.argoproj.io/hook-delete-policy` applies to hooks generally (`BeforeHookCreation` by default, plus `HookSucceeded` and `HookFailed`), including `PreDelete` ones; nothing in the docs restricts it to `PreSync`/`Sync`/`PostSync`. The bootstrap pins the `argo-cd` chart at 10.9.2 (appVersion v3.5.3, `bootstrap/versions.yaml`), well past the ArgoCD 3.1 release that introduced `PreDelete`/`PostDelete` hooks, so no version gap needed working around.

## Ordering the hook's own RBAC ahead of the Job

**Question.** The Job needs a `ServiceAccount`, `Role` and `RoleBinding` to exist before it can create a `Backup`. Hooks of the same type (here, every object in this file is `PreDelete`) are still ordered by `argocd.argoproj.io/sync-wave` within that phase, the same as `Sync`-phase hooks and regular resources (#7's notes on the migration Job established this for `Sync`; the same "Sync Phases and Waves" documentation describes phases and waves as orthogonal, waves ordering within a phase regardless of which phase it is).

**Choice.** The `ServiceAccount`, `Role` and `RoleBinding` carry `argocd.argoproj.io/sync-wave: "-1"`; the Job carries no wave annotation, leaving it in the default wave `0`. ArgoCD applies wave -1 first, waits for it to be Healthy (a `ServiceAccount`/`Role`/`RoleBinding` are Healthy as soon as they exist -- Kubernetes has no readiness concept for RBAC objects), then wave 0. This is the same two-wave shape `postgres-cluster.yaml`/`postgres-objectstore.yaml` (wave -2) and `migration-job.yaml` (wave -1) already use for "the thing that must exist first" versus "the thing that needs it", just inside the `PreDelete` phase instead of `Sync`.

## `hook-delete-policy`: clean up on success, keep on failure

**Choice.** `BeforeHookCreation,HookSucceeded` on all four objects (`ServiceAccount`, `Role`, `RoleBinding`, Job). `HookSucceeded` removes them once the deletion's `PreDelete` phase succeeds, so a successfully deleted Environment's namespace is not left holding orphaned RBAC and a spent Job. `HookFailed` was deliberately left off: the documentation's own description of a failed hook ("fixed in Git or... manually deleted") assumes the failed hook resource is still there to fix or delete -- an operator needs the failed Job's logs to know why the backup did not complete, the same reasoning #7's notes give for the migration Job keeping a failed run around under `BeforeHookCreation` alone. `BeforeHookCreation` is kept too, belt-and-suspenders: the RBAC's names are stable (`<fullname>-final-backup`, not per-attempt), so a second deletion attempt after a first one's hook failed and was fixed in git replaces the previous attempt's RBAC objects by name before creating fresh ones, rather than erroring on a conflict.

## Naming the Backup so a retried hook does not collide

**Question.** The ticket asks for a name like `<fullname>-final-<timestamp>` specifically "so a retried hook does not collide." The `Backup` object is created imperatively by the Job's own script (`kubectl apply`), not declared as a chart-rendered hook manifest, so `hook-delete-policy` (which only ever reaches resources ArgoCD itself created from the manifest) cannot dedupe or clean it up.

**Choice.** The Job's own name is stable (`<fullname>-final-backup`, matching the RBAC, so `BeforeHookCreation` on the Job also replaces a previous attempt's Job), but the `Backup` name is computed at run time inside the script, from a timestamp taken when the container actually starts (`date -u +%Y%m%d%H%M%S`), not from anything fixed at Helm render time. A retried deletion (after a fix in git, or after the failed Job and its logs were inspected and deleted by hand) gets a fresh Job, whose script computes a fresh timestamp, so its `Backup` never collides with a previous attempt's -- including one that is still sitting there because the deletion never got that far, or because a human wants to keep the evidence of a failed attempt next to a since-succeeded one.

## `iidp.itema.no/retain-until`, computed at run time, still just a record

The ticket asks the hook to carry "the same annotation `iidp.itema.no/retain-until` the current `render.Backup` writes, computed at run time as 30 days ahead." #17's notes ("Retention: no per-Backup field exists, so the annotation is only a record") already established that neither CloudNativePG nor the Barman Cloud Plugin read this annotation; nothing here changes that. The only change from #17's version is *when* the 30-days-ahead date is computed: previously at `iidp app delete` invocation time (Go's `time.Now()`, baked into the committed manifest); now inside the Job's shell script (`date -u -d '+30 days' +%Y-%m-%d`) when ArgoCD actually runs the hook. This matters more now than it did before: a `PreDelete` hook can, in principle, sit for a while before ArgoCD gets around to running it (contention on the repo server, a slow reconcile), and a retried hook after a failure could run much later still than the original deletion request. Computing at run time keeps the annotation honest about when the Backup was actually taken, which #17's design (computed once, in the CLI, before either commit was even pushed) did not guarantee either, but drifted less visibly since both commits landed close together.

## RBAC scope

The `Role` grants exactly `create`, `get`, `list`, `watch` on `backups.postgresql.cnpg.io` in the Environment's own namespace, per the acceptance criteria -- no `delete` (the hook never removes a `Backup`, including its own on a retry: leaving old ones around is harmless and arguably useful history) and no cluster-wide `ClusterRole`, since one Environment's hook has no business touching another's `Backup` objects. `get`/`list`/`watch` are all listed even though the script only ever does a single non-watching `kubectl get backup <name>` in a loop (polling, not `kubectl wait`'s own watch machinery, so progress can be logged each iteration): `list` costs nothing extra to grant and matches how `kubectl get` behaves when passed a single resource name behind the scenes on some client versions, and `watch` is included for forward compatibility with a future switch to `kubectl wait --for=jsonpath=...`, which does watch.

## `kubectl` image: `bitnami/kubectl`, not the distroless `registry.k8s.io/kubectl` -- and pinned by digest, not a version tag

**Choice.** `bitnami/kubectl`. `registry.k8s.io/kubectl` (mentioned in the ticket as the other option) ships `kubectl` alone on a distroless base with no shell, and the hook's script needs one: building the `Backup` manifest with interpolated values, running a polling loop with `if`/`case` and arithmetic, and GNU `date`'s `-d '+30 days'` extension (not available from BusyBox's `date`, which some minimal shells carry instead). `bitnami/kubectl` bundles `bash` and GNU coreutils for exactly this reason.

**Pinned by digest, found only by actually pulling it.** The original choice, `docker.io/bitnami/kubectl:1.36` (a guessed floating tag, matching the Kubernetes minor `bootstrap/versions.yaml`'s kind node image and `infra/platform/variables.tf`'s k3s pin both already use), failed in kind with `ImagePullBackOff`: "not found". Checking Docker Hub's tag-listing API for the repository (`hub.docker.com/v2/repositories/bitnami/kubectl/tags`) directly, rather than guessing another tag, showed why: as of 2026-09-22 it lists only `latest` plus content-addressed `sha256-*` attestation, signature and metadata tags -- no more per-version floating tags (`1.29`, `1.36`, or otherwise) at all, a wholesale change to Bitnami's free-tier distribution model that predates this ticket and is not documented anywhere the chart's other version pins were checked against. A version tag simply does not exist to pin. The `latest` tag's own manifest-list digest (`sha256:6e9c5284a0dac06e84de9f4d97852d2e6513442ee7ec3a66d35009eec86e1e62`, read from the same API response, its `media_type` confirming it is the multi-arch manifest list rather than one platform's image) is what the chart pins instead: `docker.io/bitnami/kubectl@sha256:...`, verified with a local `podman pull` (kubectl client v1.37.0). A digest pin is, if anything, a stronger promise than the version tag it replaces -- immutable rather than merely conventionally-stable -- at the cost of needing a deliberate edit here (not a version bump) whenever it is next updated; bumping the Platform's k3s minor no longer moves this pin automatically the way the original tag-matching design assumed, which is a real, if minor, decoupling worth knowing about the next time `bootstrap/versions.yaml`'s Kubernetes pin changes.

## `postgres.finalBackupTimeout`: exposed as a value

**Choice.** Exposed, default `1800` (30 minutes), the "generous but bounded" number the ticket itself suggests. A small Application's database backing up to a healthy bucket finishes in well under a minute; 30 minutes leaves headroom for a larger database or a slow bucket without leaving a stuck deletion hanging indefinitely (an operator can always raise it and retry, or fix the underlying problem and delete the failed hook by hand per ArgoCD's own documented recovery path). Not exposed as a CLI flag: `iidp app delete` no longer writes anything Postgres-specific at all (see below), so there is nowhere in the CLI's own flow to plumb a per-deletion override even if one were wanted; changing it is an edit to the Environment's `values.yaml` (a hand edit, tolerated per ADR's "the CLI must tolerate hand edits" convention) before running delete, or a chart-wide default change. `application.validate` (`_helpers.tpl`) refuses a non-numeric or non-positive value (`refuse-postgres-final-backup-timeout.yaml`) with a clear render-time message, rather than letting a typo reach the hook's shell script as a broken `TIMEOUT=` assignment.

## CLI: `iidp app delete` no longer writes anything Postgres-specific

`internal/render/final_backup.go` (`Backup`, `FinalBackupCluster`, `FinalBackupApplication` and their types) and the `final-backup-<environment>` writing path in `internal/platformrepo/delete.go` (`writeFinalBackup`, `finalBackupDirPrefix`, the two-commit split) are removed entirely, along with their tests (`internal/render/final_backup_example_test.go` and the corresponding cases in `internal/cli/app_delete_test.go`). `DeleteApplication` now removes each Environment's `application.yaml` in exactly one commit, `iidp app delete <name>`, whether or not Postgres was ever enabled -- there is nothing left for the CLI to decide based on `postgres.enabled` at delete time beyond whether to mention the hook in its own output (`DeleteResult.PostgresEnabled`, read back from each removed Environment's `values.yaml` before it is left behind -- `environmentHasPostgres` survives for exactly this, even though it no longer decides what gets written), since the chart already carries the actual logic and renders the hook (or not) from the same `values.yaml`. `platformrepo.FinalBackupRetentionDays` (30) is kept, unused for writing anything now, only for the confirmation prompt and the closing summary's wording -- both of which still need to say the number somewhere, and 30 is `docs/design.md`'s stated promise, not something the chart's own default (`postgres.backupRetention`, also 30 but independently configurable per Environment) should be read back from by the CLI (ADR-0002: the CLI does not read cluster or Environment-specific chart state at delete time beyond what it needs to find the directories to remove). A two-axis code review before opening the pull request caught one real regression here worth recording: an earlier version of `printDeleteResult` said "ArgoCD's PreDelete hook waits for that backup..." unconditionally, even for an Application where Postgres was never enabled on any Environment (no hook exists to wait for); fixed by threading `PostgresEnabled` through `DeleteResult` and covering both branches of the message in `TestAppDeleteIsOneCommitRemovingEveryEnvironment`.

## Why `iidp app delete` removes only `application.yaml`, not the whole Environment directory

**The gap, found only by actually running it.** The ticket's own wording, and this document's first draft, had `iidp app delete` remove `applications/<name>/prod/` and `.../staging/` -- the whole directory, `values.yaml` included -- in one commit. That is what `internal/platformrepo/delete.go` originally did, and every unit test agreed with it. It fails in a real cluster: `testDeleteEnvironment` (see below), run against kind, left `shop-staging`'s Application permanently stuck with a `DeletionError` condition:

```
error executing pre-delete hooks: failed to generate manifest for source 1 of 2: ... helm template ...
--values <path to cached source>/applications/shop/staging/values.yaml ... failed exit status 1:
Error: open <path to cached source>/applications/shop/staging/values.yaml: no such file or directory
```

**Root cause.** A `PreDelete` hook is not a resource ArgoCD already has tracked from a previous sync (unlike the Deployment, the Cluster, and everything else the resources-finalizer prunes from its own live-resource inventory, which needs no fresh git read at all). It has never been applied before; the only way ArgoCD can know it exists is to render the Application's manifest -- chart plus values -- at the moment deletion starts. Both of `shop-staging`'s Application sources track `targetRevision: main`, a moving branch, on purpose: that is what lets a `ci set-image` commit reach a running Environment without anyone re-pointing anything. The same floating reference is what breaks deletion: by the time ArgoCD renders for hook discovery, `main` is already at the commit that removed `values.yaml`, so the render fails, and it fails identically on every retry, forever -- there is no later state in which the missing file reappears. This is not a kind-only quirk or a bug in this test's harness: ArgoCD's own FAQ describes exactly this failure mode ("I've deleted/corrupted my repo and can't delete my app": "Argo CD cannot delete an application if it cannot generate manifests from the repository... delete the application using `--cascade=false`... and subsequently delete the resources manually"), confirmed with context7 alongside the PreDelete hook documentation itself.

**Options considered.**
1. **Pin every Application's values source to an exact commit SHA, updated by every writer (`app create`, `add-capability`, `ci set-image`, `secret set`) whenever it touches `values.yaml`.** Would make the very same commit still render correctly after deletion, since a pinned SHA's tree is immutable regardless of what `main` does later. Rejected: this is a cross-cutting change to the CI write-back path used on every single deploy (`internal/platformrepo/deploy.go`), well outside a ticket about the delete flow, and high-risk to get right under this ticket's own scope and testing budget.
2. **Inline the Environment's values into `application.yaml` itself (`spec.source.helm.valuesObject`), instead of a separate `values.yaml` file referenced via a second git source.** The live Application CR's `spec` is a Kubernetes object independent of git once synced, so an inline copy would survive `values.yaml`'s deletion. Rejected for the same reason as option 1: every writer of `values.yaml` would need to keep an inline copy in sync with it or deploys would silently stop taking effect -- a bigger redesign of the Platform repository's file contract than one ticket about a PreDelete hook should make.
3. **A separate, values-inlined ArgoCD Application dedicated to the backup hook** (structurally #17's old `final-backup-<environment>` Application, reimagined with a real PreDelete hook instead of a plain manifest). Rejected: `chart/application`'s shared `application.validate`/`application.labels`/`application.fullname` helpers, which every template (including the hook's own) calls unconditionally, already need most of the same values (`kind`, `platform.baseDomain`, `domains`, ...) that a dedicated, minimal Application would have to fabricate just to pass validation, and Helm renders a chart's templates together -- keeping a second Application from also rendering the Deployment, Service, Ingress, Cluster and ObjectStore would need new chart-level gating this ticket has no reason to add.
4. **Remove only `application.yaml`, leave `values.yaml` (and `sops/`) in place.** ArgoCD's render still needs `values.yaml`; leaving it where it already is means the render keeps succeeding, since neither the chart source nor the values file actually disappears from what `main` currently points at. This is the one commit `application.yaml`'s own removal is (`iidp app delete <name>`, unchanged), it needs no other writer touched, and it costs nothing while the Application is live (nothing reads a `values.yaml` with no matching `application.yaml`; `bootstrap/applications.yaml`'s own glob is `*/*/application.yaml`, not `*/*/`).

**Choice.** Option 4. Verified against the same kind cluster: with only `application.yaml` removed, `shop-staging`'s deletion proceeds, its final Backup reaches `completed` against the harness's MinIO, and the Application, its Cluster and its Deployment are all gone by the time `testDeleteEnvironment` checks.

**The cost this first introduced, and why leaving it stand was wrong.** `checkApplicationAbsent` (`internal/platformrepo/writer.go`) originally refused `iidp app create` on *any* existing directory under `applications/<name>/`, not only a live `application.yaml` -- a deliberate, pre-existing choice from an earlier ticket (#58's tolerance for hand edits: a human's own file left there for any reason must never be silently overwritten). A first attempt at this ticket narrowed that check to "a live `application.yaml`" specifically so a deleted-and-recreated Application would not be blocked by its own leftover `values.yaml`, then reverted it after `TestAppCreateRefusesAnExistingApplication` (which, at the time, hand-wrote only a `values.yaml`, no `application.yaml`, to represent "the Application exists") caught what looked like a regression: recreating an Application right after deleting it was refused until the leftover `values.yaml` was removed by hand. That framing does not survive contact with `docs/platform-repository.md`'s own rule that developers never edit the Platform repository by hand -- a leftover this ticket's own design choice creates is not an exception to that rule, and asking for a hand edit to work around it is not an acceptable trade-off, disclosed or not.

**The actual fix.** `checkApplicationAbsent` now refuses only a *live* Environment -- an `application.yaml` under `prod/` or `staging/`, the same signal `bootstrap/applications.yaml`'s own glob uses to decide an Environment exists. A directory with no `application.yaml` anywhere in it (leftover values.yaml, secrets, or both) is treated as available, and `attemptCreate` (`internal/platformrepo/writer.go`) clears it itself -- `git rm -r`, in the same commit as the new Environment's files -- printing one line naming what it found and removed. `PreviewApplication` and `CheckAvailable`, which must write nothing, still treat the leftover as available without touching it; only the real write clears it. `TestAppCreateRefusesAnExistingApplication` now hand-writes a real `application.yaml` (a live Environment is the only thing this check still refuses), and `TestAppCreateAfterDeleteReusesTheNameAndClearsTheLeftover` is the positive case: delete an Application with both Environments, recreate it under the same name with no flags of its own, and confirm the output names the leftover, `application.yaml` exists again, and the deleted Application's *other* Environment (not re-requested on the recreate) is gone too, not left behind as an orphan.

## Testing

Chart: `chart/application/final_backup_test.go`, the same fixture-and-`render()` pattern as `postgres_test.go` -- the `ServiceAccount`/`Role`/`RoleBinding`/Job present only with Postgres enabled (`TestFinalBackupHookRendersOnlyWithPostgres`, against `prod-small.yaml`), their `PreDelete`/`hook-delete-policy`/sync-wave annotations (`TestFinalBackupHookAnnotationsAndOrdering`), the `Role`'s exact rule and the `RoleBinding`'s `roleRef`/`subjects` (`TestFinalBackupRBACIsScopedToBackups`), the Job's pinned image, `backoffLimit`/`restartPolicy`, small resources, and its script's content -- the Barman Cloud Plugin shape, the retain-until annotation, the `completed`/`failed` phase checks, the configured timeout -- for both prod and staging (`TestFinalBackupJobShapeAndScript`, against `postgres-prod.yaml`/`postgres-staging.yaml`), and `postgres.finalBackupTimeout` reaching the script (`TestFinalBackupTimeoutIsConfigurable`, a new fixture `final-backup-timeout.yaml`). `chart_test.go`'s `render`/`helmTemplate` helpers gained an optional `extraArgs ...string` parameter so this file's tests can pass `--namespace <environment-namespace>` and assert on the script's `NAMESPACE=` line the way real ArgoCD rendering would set it (`.Release.Namespace` from the Application's destination namespace) -- every other test keeps using the unset default and is unaffected. `postgres_test.go`'s existing "absent without a command" migration-Job assertion was narrowed to Job names ending `-migrate`, since a `postgres.enabled` fixture without a migration command now legitimately renders one Job (the final-backup hook) where it previously rendered none. The existing `TestPostgresManifestsPassKubeconformWithTheCRDSchemas` (`postgres-prod.yaml`/`postgres-staging.yaml`) now also validates the new `ServiceAccount`/`Role`/`RoleBinding`/Job under kubeconform for free, since they are core and RBAC Kinds the default schema location already covers; the `Backup` the hook creates at run time is never itself rendered by the chart, so it needs no CRD schema here (kubeconform only ever sees what `helm template` produces).

CLI: `internal/cli/app_delete_test.go`'s Postgres-specific commit-count and file-content assertions were replaced by one table test, `TestAppDeleteIsOneCommitRemovingEveryEnvironment`, covering both with and without Postgres: exactly one `iidp app delete <name>` commit, no `final backup` commit ever, every Environment's `application.yaml` gone and its `values.yaml` still present, and the closing output naming the 30-day retention and that the Platform (not the CLI) takes the final backup only when Postgres was enabled (both branches of `printDeleteResult`'s message are asserted, catching the code-review regression above). `TestAppDeleteTwiceRefusesTheSecondAttemptClearly` covers deleting the same Application a second time (its own code-review finding, above). `TestAppCreateAfterDeleteReusesTheNameAndClearsTheLeftover` (`internal/cli/app_delete_test.go`) and the updated `TestAppCreateRefusesAnExistingApplication` (`internal/cli/app_create_test.go`) are the positive and negative sides of the leftover-directory story in `internal/platformrepo/writer.go`, described in full above.

## End-to-end: proving the hook for real, with MinIO

**The gap.** The ticket asks `TestBootstrap` to delete the fixture Application's staging Environment through the Platform repository and assert the `Backup` completed before the Cluster was gone. Two things the existing harness did not yet have: a way to push a *second* commit into a repository it had already served (the git server only ever served a repository's state as packed at harness start, `Cluster.ServeGitRepositories`/`buildRepository`), and a real Object Storage endpoint for a `Backup` to complete against -- every Environment's `platform.objectStorageEndpoint` in the fixture is `https://objectstorage.invalid` (RFC 2606, guaranteed to fail fast; #9's notes), deliberately unreachable, since nothing before this ticket needed a backup to actually succeed.

**Pushing a second commit.** `git-http-backend` refuses `receive-pack` (push) unless a repository's own config says otherwise; `buildRepository` now sets `git config --bool http.receivepack true` on each bare repository before it is packed into the ConfigMap tarball the server unpacks, so the setting is already there when the server starts and never needs a live change to the running Pod. `Cluster.PushToRepository` (`test/e2e/harness.go`) is the harness's equivalent of what `iidp app delete` itself does to the real Platform repository: it port-forwards to the git server (the same mechanism `checkRepository` already used, factored out into `withGitServerPortForward`), clones the named repository over that port-forward, lets a caller-supplied `mutate` function change the working tree and report whether it changed anything, and commits and pushes the result to `main` over plain HTTP. `withGitServerPortForward` also gained a short wait for the forwarded local port to actually accept connections before handing the URL to a caller (`waitForLocalPort`): `checkRepository`'s own retry loop already tolerated `kubectl port-forward`'s asynchronous startup, but `PushToRepository`'s single `git clone` does not get a retry loop of its own, and raced it (`connection refused`) in testing before this was added.

**Real Object Storage: MinIO, not the "assert only that it ran" fallback.** The ticket allows a lighter path -- assert only that the hook's Job ran and its `Backup` object was created, letting the Job fail after a short, fixture-set timeout, if a real object store is "too heavy for the 2-vCPU runner." It was not needed here. CloudNativePG's Barman Cloud Plugin documents MinIO as a first-class S3-compatible target with exactly the shape the chart already renders (`endpointURL: http://minio:9000`, `s3Credentials` from a Secret with `ACCESS_KEY_ID`/`ACCESS_SECRET_KEY` -- checked against the plugin's current documentation with context7, `/websites/cloudnative-pg_io_plugin-barman-cloud`, "ObjectStore endpointURL MinIO or generic S3-compatible endpoint"), so no chart change or special-casing was needed to point an Environment at one. `Cluster.InstallMinIO` (`test/e2e/harness.go`) deploys a single MinIO Pod and a small `mc` Job that creates the fixture's bucket (`iidp-backups`, matching `platform.backupsBucket`) once the server answers, in `GitServerNamespace` alongside the git server: a harness-only component, like the git server itself, that neither the chart nor a real bootstrap ever installs. Its resource requests (`10m`/`128Mi` for the server, `10m`/`32Mi`, no CPU limit, for the short-lived bucket-creation Job) are the same "small" spirit as everything else this harness adds on top of the nine Platform components and two Environments (#9's notes on the CI CPU ceiling) -- see "The CI CPU budget" below for why these were trimmed further after this ticket's own follow-up.

**`quay.io`, not `docker.io`: found only by actually running it.** The first local run pulled `docker.io/minio/minio` and `docker.io/minio/mc` and failed immediately with `requested access to the resource is denied` -- on every tag tried, including `latest`, confirmed with a plain `podman pull`. MinIO changed its Docker Hub distribution to require an authenticated (free) account to pull at all, some time after this repository's other version pins were last checked; nothing in the CloudNativePG or Barman Cloud Plugin documentation mentions it, since neither publishes MinIO itself. `quay.io/minio/minio` and `quay.io/minio/mc`, MinIO's own alternate registry, pull anonymously and were substituted, pinned to their newest plain (non-`-cpuv1`, non-hotfix) release tags at the time (`RELEASE.2025-09-07T16-13-09Z` and `RELEASE.2025-08-13T08-35-41Z` respectively, found via `quay.io`'s own public tag-listing API), both verified with a local `podman pull` before being written into the harness.

Only `shop-staging`'s `platform.objectStorageEndpoint` was pointed at MinIO (`http://minio.iidp-e2e.svc.cluster.local:9000`), with a `backups-credentials` Secret carrying MinIO's real root credentials (`Cluster.CreateMinIOBackupsCredentialsSecret`, mirroring the existing `CreateBackupsCredentialsSecret`'s dummy version) -- `shop-prod` is untouched, still pointed at `objectstorage.invalid` with dummy credentials nothing ever authenticates with, exactly as #9 left it: this ticket only deletes staging, so only staging's backup needs to be real, and changing less than the whole fixture keeps `testFixtureApplication`'s existing assertions (prod's Cluster reaching Healthy despite an unreachable `ObjectStore`) exercised unchanged. `postgres.finalBackupTimeout: 120` on staging is generous for a real, small, empty-database backup against an in-cluster MinIO (which finishes in well under a minute) while staying far short of the chart's own 1800s default, which this test's budget cannot afford to wait out even once.

**What `testDeleteEnvironment` asserts, and what it only logs.** `shop-staging` disappearing from `Cluster.Applications` is both "the Application was deleted" and, since ArgoCD's resources-finalizer only finishes removing an Application once every resource it owns is gone, indirect proof the Cluster, Deployment, Service, Ingress, ObjectStore and ScheduledBackup are all already gone by the time it happens -- the ticket's own suggestion that "the hook Job's completion suffices if the Cluster is gone by the time you look" taken directly: if the hook's `Backup` had not reached `completed` and the ArgoCD race below did not occur, the `PreDelete` hook would not reach Healthy, and the Application would still be there (or stuck in `DeletionError`) when the poll loop times out, loudly, with its own YAML. `Cluster.WaitForResourceGone` then checks the `Deployment/shop-staging` and `Cluster.postgresql.cnpg.io/shop-staging-db` directly, redundant with the Application-gone proof above but cheap and explicit about exactly what the acceptance criteria asks for. These are the test's hard assertions, and every run in testing reached them.

Whether a `Backup` object is still there afterward, in `shop-staging`, is logged but not asserted as a hard failure -- two distinct things observed in testing can make it absent even when the chart and the hook both worked exactly as designed, covered in the next two sections. The poll loop logs the hook Job's own `status` fields and `Cluster.BackupNames` on every one-second iteration, not only at the end, and tracks whether the Job was ever observed running at all (`jobEverObserved`): with a hook that can go from "just created" to "gone" (cleaned up by its own `HookSucceeded` policy) in well under even a one-second gap, a single before/after check cannot tell "the hook ran and finished" apart from "the hook never ran at all" -- the per-iteration log, and that flag, are what make the difference visible in the test's own output (see the pull request body for a real run's tail).

**The CI CPU budget: this harness's own additions were most of what tipped it over.** After the single-hook mitigation above landed (`db59a05`), `kind bootstrap` failed three CI runs in a row, all the same way: `after 10m0s these Applications had not reached Synced+Healthy: shop-prod` (or `shop-staging`), with `FailedScheduling` events reading `0/1 nodes are available: 1 Insufficient cpu` against shop-prod/shop-staging's own Deployment or migrate Job -- never against anything this ticket's chart template adds (the RBAC objects the mitigation made ordinary resources request no CPU at all; only Pods do). The previous commit on this same branch (`64c1295`) had passed the identical job cleanly in 12m5s with zero `Insufficient cpu` events anywhere in its log, so this was not pre-existing flakiness the reruns happened to hit; `kubectl describe node`'s "Allocated resources:" table from a failing run showed `cpu 1780m (89%)` requested against the runner's 2 vCPUs (2000m) allocatable -- a margin already thin enough that the mitigation's own extra objects (three ordinary RBAC resources per Postgres-enabled Environment, where before all four were PreDelete hooks deferred until deletion and so cost nothing at install time) were enough on their own to tip scheduling over the edge for the fixture's own workload.

Nothing in `test/e2e/harness.go` is the product under test, so everything in it was reviewed for CPU it did not need to request on a 2-vCPU runner, all in `test/e2e/harness.go`:

- **MinIO** (`minioManifest`): the server's CPU request dropped from `50m` to `10m` (its memory request, `128Mi`, is unchanged -- MinIO was never CPU-bound in this harness, only ever asked for more than it used). The `mc` bucket-creation Job's CPU request dropped from `25m` to `10m`, and its CPU *limit* (`100m`) was removed entirely: it runs once, for a few seconds, and only a Pod's request (not its limit) competes for the node's scheduling budget.
- **The git server** (`gitServerManifest`) already requested no CPU at all -- nothing to trim there.
- **Traefik** (`InstallTraefik`): the k3s chart's own default CPU request (`100m`) is sized for a real node sharing a real cluster's traffic, not a kind node routing a handful of test requests; `--set resources.requests.cpu=20m --set resources.requests.memory=64Mi` on the `helm upgrade --install traefik` call brings it down to what this harness actually needs.
- **kind's own components**, not Traefik's or this ticket's at all: after cluster creation, `kubectl -n kube-system set resources deployment/coredns --requests=cpu=10m` and `kubectl -n local-path-storage set resources deployment/local-path-provisioner --requests=cpu=10m` trim both to what a single-node, low-traffic test cluster needs, sized (like the existing CoreDNS replica-count reduction right above them in `Cluster.Create`) for a real cluster's node count rather than for sharing a hosted runner with the whole platform stack and two shop Environments. The static control-plane Pods (`kube-apiserver`, `etcd`, `kube-scheduler`, `kube-controller-manager`) are untouched -- they are not Deployments, `kubectl set resources` cannot reach them, and their requests reflect the control plane's own genuine needs, not something safe to shrink.

None of this touches anything the chart renders or `iidp app delete`/`iidp app create` write to the Platform repository -- every change is confined to the harness's own, test-only infrastructure.

**Visibility going forward.** `Cluster.WaitForApplications` now logs the node's `kubectl describe node` "Allocated resources:" table (`logNodeAllocatedResources`) after every successful wait, not only when `DumpDiagnostics` runs on a timeout -- so a green run's own log shows the CPU margin directly, and the next person adding a fixture Application, or moving another PreDelete hook object to an ordinary resource, has a number to check their own change against before CI tells them the hard way. `DumpDiagnostics`'s own node dump was widened from just "Allocated resources:" to starting at "Non-terminated Pods:", which includes the per-pod requests/limits table immediately before the totals -- a timed-out run now shows which pods are spending the budget, not only how full it is.

Two consecutive green `kind bootstrap` CI runs after this fix are recorded in the pull request body, with their durations and a green run's own "node allocated resources" log line.

## A real ArgoCD race, found only by watching it happen twice

**The first version hard-refreshed, and hit a race every time.** To avoid waiting out ArgoCD's default ~3-minute poll interval, the first working version of `testDeleteEnvironment` called a new harness method, `Cluster.RefreshApplication`, annotating the `applications` parent Application with `argocd.argoproj.io/refresh=hard` (the same thing `argocd app get --hard-refresh` does) right after the push. Two full runs against a real kind cluster both showed the same failure: `shop-staging`'s Application disappeared from `Cluster.Applications` within about ten seconds of the push -- far too fast for a Job's Pod to even pull an image, let alone run a backup -- and no `Backup` object the hook's script would have created was ever found afterward.

**What the controller's own log showed.** With the cluster kept (`IIDP_E2E_KEEP=1`) and `kubectl -n argocd logs statefulset/argocd-application-controller` read directly, the sequence was unambiguous: `applications`'s hard-refresh triggered an immediate sync that pruned `shop-staging`; the application controller correctly logged `Creating PreDelete hook resource` for all four of the chart's hook objects (`ServiceAccount`, `Role`, `RoleBinding`, `Job`) and `Created 4 PreDelete hooks` -- proving the chart's own contribution (the annotations, the RBAC, the Job) is correct and matches the documented API exactly. But in the same one-second window, a flood of `Requesting app refresh caused by object update` events (one per hook object just created) and repeated `Hook resource ... already exists, skipping` warnings showed several overlapping reconcile passes racing each other for the same Application; one of them logged `Deleting resources` / `Deleting application's resources with Foreground propagation policy` / `11 objects remaining for deletion` immediately after the hooks were created, without ever waiting for the Job to report `succeeded`. This reads as a genuine ArgoCD-level race in this chart version (10.9.2, appVersion v3.5.3) between "a burst of concurrent reconciles, each triggered by one of several hook objects' own creation events" and "the single code path that is supposed to gate resource deletion on PreDelete hook health" -- not a bug in the chart, and not something `application.validate` or the Job's own script could ever detect or work around, since by the time anything inside the cluster could react, the resources it might have blocked were already gone.

**Removing the hard-refresh reduced the race, but did not eliminate it.** The first suspect was the explicit hard-refresh itself, forcing everything to start at once. Removing it and letting ArgoCD's own, unhurried ~3-minute poll trigger the parent's prune produced a clean, correctly-gated deletion on the next run (cluster kept, `kubectl -n shop-staging get pods` watched directly: the `shop-staging-final-backup` Pod appeared, ran, and the Application stayed `Synced`/`Healthy`, not yet even `OutOfSync`, for the entire wait). A further run, still with no explicit refresh, raced anyway -- `shop-staging` went from `Synced`/`Healthy` straight to gone within about five seconds of ArgoCD's own natural poll, the same signature as the hard-refresh runs. So the explicit refresh was not the root cause, only one way (among others, apparently including ArgoCD's own ordinary poll) to arrive at the same storm of concurrent, hook-object-triggered reconciles this section already describes. Across four independent full runs the race occurred in two, did not occur in one (a stuck `ImagePullBackOff` run that never reached a terminal Job state either way, so inconclusive on the race specifically but still proof the hook correctly blocked deletion for its whole duration), and did not occur in a fourth where the Job genuinely ran to completion. `Cluster.RefreshApplication` was still removed from the harness (there is no remaining caller, and it did make the race easier to trigger on demand while diagnosing it), and `testDeleteEnvironment`'s own poll loop budget was widened to nine minutes and its interval tightened to one second, to give the test the best remaining chance of observing the hook's objects during whichever run does or does not hit the race, without pretending the race itself is fixed.

**Why this matters beyond kind.** This is not a kind-only artifact: the race is triggered by ArgoCD's own reconcile scheduling under concurrent refresh pressure -- multiple hook objects, each of whose own creation event asks for another refresh of the same Application, arriving close enough together that some pass through the deletion-processing code without correctly waiting on the Job's health. A real Platform's `iidp-platform` repository, relying on ArgoCD's own default polling (`bootstrap/applications.yaml` configures no webhook), is less likely to trigger it than this test's harness (which was, until this finding, actively forcing an immediate refresh at exactly the worst moment) but is not provably immune to it either, since the same multi-object-hook-creation event burst happens regardless of what triggered the surrounding sync. This is recorded here as a known, reproducible limitation of ArgoCD 10.9.2 / v3.5.3's PreDelete hook handling under concurrent reconciles, not a defect in this chart (which the controller's own logs confirm renders and creates the hook objects exactly as the ArgoCD documentation describes) or in `iidp app delete`.

**Confirmed: this is ArgoCD issue [#29100](https://github.com/argoproj/argo-cd/issues/29100), open, not fixed in any released version.** `gh search issues --repo argoproj/argo-cd "PreDelete hook"` turned it up directly: "PreDelete/PostDelete hook deleted before it executes," filed 2026-08-07, `bug/severity:critical` `bug/priority:high`. Its own root-cause analysis matches this investigation's independent findings almost line for line: `executeHooks` (`controller/hook.go`) builds `runningHooks` from a cluster-cache snapshot (`liveObjs`); deleting an Application generates a burst of finalization passes in quick succession; a pass that runs before the cache has observed a hook another pass just created re-attempts `CreateResource`, gets `AlreadyExists`, and `continue`s without adding the hook to `runningHooks` -- so the health check that follows sees zero running hooks and falls through to "phase complete," the finalizer is removed, and cascade deletion kills the hook resource before its Pod can run. The issue's own reproduction fingerprint -- an `already exists, skipping` warning immediately followed by the hook Pod being killed within the same second -- is exactly what this repository's own kept-cluster runs showed. Two fix PRs exist, [#29126](https://github.com/argoproj/argo-cd/pull/29126) and [#29687](https://github.com/argoproj/argo-cd/pull/29687) (both titled "do not complete a \[delete\] hook phase on AlreadyExists," both proposing the same fix the issue itself suggests: on `AlreadyExists`, requeue or fetch the live object instead of silently treating the hook as absent) -- neither is merged. Checked directly against the release history (`gh api repos/argoproj/argo-cd/releases`): v3.5.3, the version the bootstrap pins, published 2026-09-14, over five weeks after the bug was filed; v3.6.0-rc1, published 2026-09-16, the next release candidate. Neither release's changelog (`gh api repos/argoproj/argo-cd/releases/tags/<tag>`, `.body`) mentions #29100 or either fix PR. There is, as of this writing, no ArgoCD release this repository could pin to make the race stop happening; **the version is not bumped in this pull request** -- there is nothing to bump to yet. Revisit when either PR merges and ships in a release.

**Mitigation actually taken: one hook object, not four.** #29100's own root cause is a race against the informer cache after *a* create, not specifically about having several hook objects -- but each hook object's own creation is itself one of the "burst of finalization passes" the bug depends on (`Requesting app refresh caused by object update`, once per object, confirmed in this repository's own controller-log excerpt above), so four hook objects created together give the race four chances to trigger instead of one, and RBAC objects (no ArgoCD health check, "Healthy" the instant they exist) that were being raced through wave -1 added nothing but more of exactly that. `chart/application/templates/final-backup-job.yaml` now renders the `ServiceAccount`, `Role` and `RoleBinding` as ordinary resources -- no `argocd.argoproj.io/hook` annotation, no sync-wave -- present continuously whenever `postgres.enabled` and pruned with the rest of the Environment's resources through the normal resources-finalizer path, the same as the Cluster or the Deployment; only the Job keeps the `PreDelete` annotation. This does not fix #29100 (a single hook object's own create-then-immediately-raced-refresh is still possible, and this repository's own runs after the change, recorded below, confirm the race can still occur) but it does remove three of the four opportunities the previous design gave it, and removes the RBAC-before-Job ordering (`sync-wave: "-1"`) this design no longer needs at all, since the ServiceAccount the Job's Pod mounts already exists by the time deletion starts.

**Three runs after the single-hook mitigation: the race still occurs, one time in three.** With the RBAC no longer hooks, `go test -tags e2e -count=1 ./test/e2e/... -run TestBootstrap -v -timeout 30m` was run three separate times against a fresh `kind` cluster (`KIND_EXPERIMENTAL_PROVIDER=podman`), each a genuine independent execution (`-count=1`, to rule out Go's test-result cache -- an earlier attempt at a second run without it silently replayed a cached `ok` instead of re-executing). Per run, `testDeleteEnvironment`'s own one-second poll log is the source for both columns below:

| Run | Hook Job observed running | Application vanished before the hook finished | Final Backup recorded |
| --- | --- | --- | --- |
| 1 | Yes (`active=1`, then `succeeded`) | No -- Application stayed `Synced`/`Healthy` until the Job finished, only went `OutOfSync` after | No (the missing-Backup issue below, independent of the race) |
| 2 | Yes (`active=1` for ~20s) | No -- Application stayed `Synced`/`Healthy` through the Job's last `active=1` poll, only flipped `OutOfSync`/`Progressing` one poll after the Job was already gone | Yes -- `shop-staging-final-20260922131837` |
| 3 | Yes, but only for two one-second polls (`active=1` at both) | **Yes** -- the same poll that first showed the Job `active=1` already showed the Application `OutOfSync`/`Progressing`; one second later the Job was gone (`NotFound`) with `succeeded` never observed, and the ScheduledBackup's own pre-existing Backup (`shop-staging-db-20260922133109`), unrelated to the hook, vanished in the same one-second window -- the signature from the "controller's own log" finding above, reproduced with a single hook object | No |

The race is not eliminated by rendering the RBAC as ordinary resources: it reproduced in run 3, one of three, with the Application's cascade deletion already `OutOfSync`/`Progressing` in the same poll the Job first appeared, well before any `succeeded` state could be observed. This is consistent with #29100's own root cause -- the informer-cache race is against *a* hook object's own create event, not specifically against having several -- and with the mitigation's own stated limit above ("a single hook object's own create-then-immediately-raced-refresh is still possible"). Going from four hook objects to one did not need to drop the frequency to zero to be worth keeping: it removes three of the four opportunities the previous design gave the race per deletion, and this repository has no ArgoCD release yet to pin that fixes #29100 outright (see above). `testDeleteEnvironment` already logs this loudly on every run, whether or not this run hits it -- the full per-second Application/Job/Backup line (`bootstrap_test.go:151`), and on exit either `no Backup object found in shop-staging (hook Job observed running at some point: %v)` or `final Backup(s) recorded in shop-staging: %v` -- rather than asserting the Backup's presence as a hard failure, exactly because a run like #3 above is expected to keep occurring some fraction of the time until #29100 is fixed upstream. Nothing here is hidden or downgraded to a soft warning that should be a hard one: the test's own hard assertions (the Environment's other resources are actually gone, proving the hook was not simply skipped) still pass in all three runs, including run 3.

## The Backup can also go missing even when the hook is not raced

A separate, later run showed a third outcome: the hook's `ServiceAccount`/`Role`/`RoleBinding`/Job rendered and ran with no sign of the race (the Application stayed `Synced`/`Healthy` for the full ~3.75-minute wait for ArgoCD's natural poll, exactly as a correctly-gated deletion should), the Job reported `active` and then immediately cleared (consistent with a fast, successful backup against MinIO's empty database) and the Application's health returned to `Healthy` before deletion proceeded -- yet no `Backup` object was found in `shop-staging` afterward, whether or not the hook Job had been directly observed running. The leading, unconfirmed suspect is CloudNativePG's own controller: once the Cluster the Backup references is torn down (which happens immediately once the hook reports Healthy, by design), CloudNativePG's reconciler may treat a Backup whose Cluster no longer exists as orphaned and remove it, the same way the ScheduledBackup's own `Backup` (`shop-staging-db-<timestamp>`, owned by the ScheduledBackup via `backupOwnerReference: self`) is confirmed, separately, to cascade-delete once its ScheduledBackup is pruned -- though the final Backup this ticket's hook creates carries no ownerReference at all, so if this is what happens it would be CloudNativePG's own controller reconciling by Cluster reference, not Kubernetes' owner-reference garbage collection. This was not confirmed against CloudNativePG's source or documentation (out of this ticket's remaining time and scope to chase further, and it does not change anything the chart, the RBAC or the Job's script do); it is recorded here as the reason `testDeleteEnvironment` logs the Backup's presence rather than asserting it, alongside the ArgoCD race above, and as a concrete lead for whoever picks this up next. If confirmed, the practical implication for the design is unchanged either way: the "recoverable for 30 days" promise in `docs/design.md` was never resting on this specific Backup object's own survival (#17's notes already established that the continuous WAL archive and the daily `ScheduledBackup`, both already running against the same `ObjectStore` since the Environment was created, are what make the data recoverable) -- only the visible *record* of the final backup having been taken would be shorter-lived than intended.
