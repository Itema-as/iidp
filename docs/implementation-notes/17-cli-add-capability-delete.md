# #17 CLI: app add-capability and app delete

Questions that came up while building `iidp app add-capability` and `iidp app delete`, and the answer chosen for each. CloudNativePG and the Barman Cloud Plugin were checked with context7 on 2026-09-21 (`/websites/cloudnative-pg_io`, "on-demand Backup resource with plugin barman cloud"; `/websites/cloudnative-pg_io_plugin-barman-cloud`, "Backup annotations retention policy" and "Backup resource spec.method plugin"). PR #29 (`adriansberg/e2e-fixture-application`, merged before this one) supplied `bootstrap/applications.yaml`'s include glob, which the final-backup Application is built to match exactly.

## The final Backup's shape, confirmed against current CloudNativePG docs

The chart's `ScheduledBackup` (`chart/application/templates/postgres-scheduledbackup.yaml`) already uses the Barman Cloud Plugin: `spec.method: plugin`, `spec.pluginConfiguration.name: barman-cloud.cloudnative-pg.io`. Context7 confirms a one-off `Backup` resource takes the identical shape (`cloudnative-pg.io/plugin-barman-cloud/docs/usage`, "Create Backup via YAML Manifest"):

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Backup
metadata:
  name: backup-example
spec:
  cluster:
    name: cluster-example
  method: plugin
  pluginConfiguration:
    name: barman-cloud.cloudnative-pg.io
```

The deprecated in-tree shape (`spec.method: barmanObjectStore`, still shown on `cloudnative-pg.io/docs/1.30/backup`'s own top example) is not used, for the same reason #7 chose the plugin for the chart in the first place: it is marked deprecated and due for removal. `render.Backup` renders exactly this shape, targeting `<fullname>-db`, the same Cluster name `application.postgres.cluster` (`chart/application/templates/_helpers.tpl`) already gives every Environment's database.

## Retention: no per-Backup field exists, so the annotation is only a record

**Question.** The ticket asks for the `Backup` "annotated for 30-day retention... plus whatever the plugin documents for retention, if anything."

**Finding.** Neither CloudNativePG nor the Barman Cloud Plugin document a per-Backup retention field or annotation. Retention (`cloudnative-pg.io/plugin-barman-cloud/docs/retention`) is configured only on the `ObjectStore`'s `retentionPolicy` (a recovery-window string like `30d`), which `barman-cloud-backup-delete` reads to decide which *base backups* in that store to expire — it has no concept of "keep this one Backup object 30 days" at all. Object tagging (`cloudnative-pg.io/plugin-barman-cloud/docs/misc`) is the closest per-artifact knob, and it tags the *data* in the bucket, not the Kubernetes object.

**Consequence.** `iidp.itema.no/retain-until: <30 days ahead, YYYY-MM-DD>` is a plain annotation with no operational effect: nothing in CloudNativePG or the plugin reads it. It exists so a human (or a future cleanup tool) looking at `applications/<name>/final-backup-<environment>/backup.yaml` can see the Platform's stated retention promise (`docs/design.md`'s "final backup kept 30 days on delete") without cross-referencing this document. `iidp app delete`'s stdout says so explicitly (logged, per the ticket's instruction), and the point is moot in practice anyway: the Environment's `ObjectStore` (with its own real `retentionPolicy: 30d`, written by `app create`/`add-capability`) is deleted along with the Cluster in the second commit, so there is no `ObjectStore` left to enforce anything against this Backup specifically. What actually keeps the data recoverable for 30 days is not this annotation, or even this Backup succeeding — see the next section.

## The race is real, is logged, and is not fixed here

**Superseded.** #39 replaced this two-commit design with an ArgoCD `PreDelete` hook the chart itself renders: the race this section documents no longer exists, because ArgoCD, not commit ordering, now guarantees the final backup happens before the Environment's resources are deleted. See [`39-final-backup-predelete-hook.md`](39-final-backup-predelete-hook.md). The rest of this section is kept as history.

**The design.** Both commits (final Backup, then Environment removal) are pushed together in one push, as the ticket asks. ArgoCD reconciles `applications.yaml`'s two newly-visible children independently: the new `final-backup-<environment>` Application and the fact that `prod`/`staging`'s own Application is now gone. There is no ordering guarantee between "the Backup plugin finishes uploading a base backup" and "ArgoCD notices the Environment's Application was deleted and starts tearing down its Cluster." A slow bucket, a large database, or ArgoCD simply reconciling the deletion first can all mean the final Backup never completes.

**Why this is acceptable.** The Environment's Cluster has been running a `ScheduledBackup` (daily, `immediate: true`) and continuous WAL archiving to the same `ObjectStore` since Postgres was enabled (#7's notes). That data is already in Object Storage before `iidp app delete` ever runs, and deleting the `Cluster` and `ObjectStore` Kubernetes objects does not delete anything in the bucket — the plugin has no finalizer or hook that reaches into Object Storage on its own resources' deletion (confirmed by there being no such behaviour documented, and by design: the whole point of an external object store is that its lifecycle is independent of the cluster). So the Environment is recoverable from what was already archived, regardless of whether this specific final Backup wins the race. The retention promise (30 days) is real for that already-archived data; it is just not enforced by anything after the `ObjectStore` object is gone; there is no live retention policy for anyone to point at.

**What was not built.** A `--wait` flag that blocked until the final Backup's `.status.phase` reached `completed` was considered and rejected: `iidp` never talks to Kubernetes (ADR-0002), and there is no way to observe a `Backup`'s status without doing so. Recorded here as the ticket asks, as a Phase 2 idea *only if* a way to observe completion without cluster access ever exists (for example, if Grafana Cloud metrics from Alloy someday exposed backup completion) — not a gap to close with more `iidp` code today.

## Where the final-backup Application lives, and why it matches PR #29's glob exactly

`bootstrap/applications.yaml` (from PR #29, merged first) discovers `applications/*/*/application.yaml`. `applications/<name>/final-backup-<environment>/application.yaml` matches that glob like any other Environment's Application would — no change to the glob, and no second bootstrap Application needed. Its own source is deliberately narrow: a plain directory source on the Platform repository at `path: applications/<name>/final-backup-<environment>`, `directory.include: backup.yaml`, so it renders only the `Backup` manifest sitting next to it, not its own `application.yaml`. No resources finalizer (unlike every other Application this document describes): deleting this Application in some future cleanup must not delete the `Backup` object it recorded, which is the one thing meant to outlive it. `prune: false` for the same reason applied to the sync policy instead of the finalizer.

## `add-capability`'s already-present checks read prod only

Checking "is this Capability already present" reads `applications/<name>/prod/values.yaml` (`postgres.enabled`, `domains`, `size`) and, for `--staging`, `os.Stat`s `applications/<name>/staging/`. It does not separately check staging's `size` or `postgres.enabled`: every existing writer (`app create`'s `--staging`, and `add-capability` itself) keeps `size` and Postgres uniform across an Application's Environments by construction, so prod's state is staging's state whenever staging exists. If a hand edit ever desynchronised them (#58's tolerance for hand edits), `add-capability --size <same-as-prod>` would refuse based on prod even though staging might already differ; accepted as an edge case not worth a second read, since the fix is the same command with the Environments back in sync.

## `--staging` copies prod's values.yaml, not a fresh render

Building a fresh `render.Values` for the new staging Environment (the way `app create`'s `writeEnvironment` does) would require re-deriving every field `add-capability` never asked about (`env`, `probe.path`, `image.repository`, any hand-added key) from prod's current file — the read-modify-write path #13's notes deferred to this ticket. Chosen instead: `render.CopyValuesForStaging` takes prod's values.yaml (after this run's own edits, so `--staging --postgres` together give staging Postgres too) and produces staging's by editing four things in place — `environment: staging`, `image.tag` reset to `""` (nothing has deployed there yet, the same starting state `app create` gives a fresh Environment), `domains: []` (custom domains are prod-only), and no `secrets:` key. Everything else, including hand-added keys `add-capability` has no opinion about, survives untouched. `application.yaml` is still a fresh `render.ArgoCDApplication` render, the same as `app create`'s: it carries no developer-chosen content beyond the Environment name.

**Secrets are not copied, and the CLI cannot copy them if it wanted to.** Prod's `secrets:` list only names *which* SOPS documents exist; the values are age-encrypted, and only the cluster holds the private key (`docs/platform-repository.md`, "How the CLI writes"). Re-encrypting the same plaintext for staging would need the plaintext, which `iidp` never has once `secret set` has run. So the field is dropped and `add-capability` logs it plainly ("prod has secrets set; they are not copied..."), rather than silently leaving a `secrets:` list pointing at prod's `*.enc.yaml` files, which do not exist under staging's own `sops/` directory and would fail to render.

## `EnablePostgres`/`SetSize`/`AddDomain`/`CopyValuesForStaging`: new yaml.v3 node helpers, same shape as `secret set`'s

`internal/render/edit.go` already had `AddSecretName` and `AddKustomizeSource` (#16) for exactly this reason: editing a values.yaml or application.yaml in place, preserving comments, key order and unrelated content, without a full unmarshal-mutate-marshal round trip through Go structs (which would lose comments and any hand-added key). The four new functions follow the same pattern, plus one shared helper, `setNestedValue`, that walks or creates a dotted path of mapping nodes — `postgres.enabled`, `platform.backupsBucket`, `image.tag` are all one or two levels deep, so a single generic walker replaced what would otherwise be four near-identical hand-rolled traversals. One quirk it surfaced: a raw `yaml.Node` scalar with an empty `Value` and no `Style` re-encodes as YAML `null`, not `""`, because the encoder's implicit-tag resolution (unlike the struct-marshal path `render.Values` uses, which special-cases this) does not force quoting on a bare `Node`. `CopyValuesForStaging` sets `image.tag`'s node with `Style: DoubleQuotedStyle` explicitly to keep the `tag: ""` shape `render.Values` already produces for a fresh Environment.

## Refusal checks run after the clone, like Postgres/domain validation in #13

`add-capability`'s "at least one flag" and `--migration-command` requiring `--postgres` are flag-only and run before anything is cloned, matching `app create`'s `plan()`. Whether a Capability is already present needs the cloned Environment's own values.yaml, so those checks (and the bucket/endpoint requirement for `--postgres`) run inside `Writer.attemptAddCapabilities`, in the same place `attemptCreate` validates `chartVersion` and domains — the same trade-off #13 already documented: a failure here is reported after the token/clone step, with a clear message naming the Capability, and nothing is written.

## Delete's confirmation: a cheap TTY check, no new dependency

**Question.** "On a terminal (or `--interactive` for tests)... refuses on mismatch... `--force` skips... without a TTY and without `--force`, refuse."

**Choice.** `isTerminalReader` type-asserts `cmd.InOrStdin()` to `*os.File` and checks `os.ModeCharDevice`, rather than adding `golang.org/x/term` (or an `isatty` package) for a single call site. This is the same technique many small Go CLIs use for "is my stdin a pipe or a terminal" and needs no new module — relevant since `go.mod` otherwise only carries `cobra` and `yaml.v3`. It is not a full PTY detection (it would, for example, treat a `/dev/null` redirect the same as a pipe, both non-terminal — the correct answer for this command either way) but that is all `app delete` needs: tests always pass a `strings.Reader` or `bytes.Buffer`, never `*os.File`, so they exercise the same "non-interactive" branch a real script redirecting stdin would, and `--interactive` exists precisely so a test (or a script piping the typed name on purpose) can force the prompting branch without a real terminal. `--interactive` is a plain, visible flag rather than hidden like `--app-dir`/`--platform-repo`: unlike those, it is not purely an internal seam — a script that wants to pipe `echo shop | iidp app delete shop --interactive` deliberately, instead of using `--force`, is a legitimate (if unusual) choice, matching the ticket's own phrasing ("or `--interactive` for tests, mirroring how the other commands inject stdin").

## `runWithRetry` generalised to a free function

`platformrepo.Writer`'s clone-commit-push-retry-once pattern (`CreateApplication`, `SetSecrets`) was a method, `func (w *Writer) runWithRetry(...) (Result, error)`, tied to the one `Result` type. `AddCapabilities` reuses the identical `Result` type, but `DeleteApplication` needs its own (`DeleteResult`: which directories were removed, which final Backups were recorded). Go does not allow a method to carry its own type parameter, so `runWithRetry` became a package-level generic function, `runWithRetry[T any](ctx, attempt func(ctx, retry bool) (T, error)) (T, error)`, and every caller (`CreateApplication`, `SetSecrets`, `AddCapabilities`, `DeleteApplication`) now calls it as `runWithRetry(ctx, func(...) (SomeResult, error) { return w.attemptX(...) })`. No behaviour changed; this only removes what would otherwise have been a fourth near-identical retry loop.

## Commit messages

`add-capability`: `iidp app add-capability <name> <capabilities>`, where `<capabilities>` is a fixed, space-separated ordering (`postgres`, `staging`, `domain`, `size`) of whichever flags were given — `domain` appears once regardless of how many `--domain` flags were passed, naming the Capability rather than every host (the values.yaml diff already shows which hosts). `delete`: `iidp app delete <name>: final backup` for the first commit (only made when at least one Environment has Postgres) and `iidp app delete <name>` for the second, matching the ticket's exact wording for both.

## Code review: one fix taken, one duplication accepted

A two-axis review (Standards, Spec) against `origin/main` before opening the pull request found no hard violations and no missing or wrong requirements. Two items came up:

- **Fixed.** `runAppAddCapability`'s "at least one flag" gate originally checked `cmd.Flags().Changed(...)`, which is true for `--staging=false` even though nothing was actually asked for; a caller passing an explicit `false` would have reached `AddCapabilities` with an all-zero `Capabilities` and no file to commit. Changed to check the effective values (`opts.postgres`, `opts.staging`, `len(opts.domains)`, `opts.size`) instead, with a regression test (`TestAppAddCapabilityExplicitFalseFlagStillRequiresACapability`).
- **Accepted as is.** `detectAddCapabilityMigrationCommand` (`internal/cli/app_add_capability.go`) duplicates most of `app.go`'s pre-existing `detectMigrationCommand`: the same `--app-dir`-or-cwd-with-package.json selection, the same `migrate.Detect` call, the same progress messages. A shared helper would remove it, but extracting one means editing `internal/cli/app.go` beyond command registration, which this ticket's own git rules rule out (issue #14's wizard is restructuring `app.go`'s flow in parallel; conflicts there are explicitly this ticket's to avoid, not to create). Left duplicated; a natural cleanup once #14 lands and `app.go` settles.

## Testing

Both commands are driven through `cli.Run`/`cli.RunWith` against a bare Platform repository, the seam #10 onward established (`internal/cli/app_add_capability_test.go`, `internal/cli/app_delete_test.go`): every Capability added to an Application seeded by `iidp app create` first, the refusal for each already-present Capability (naming it), prod's secrets and header comment surviving a Postgres/size/domain edit, `--staging` copying prod and logging that secrets are not copied, delete with Postgres (two commits, `backup.yaml` and the final-backup `application.yaml` parsed and asserted field by field, Environment directories gone, `final-backup-*` directories present) and without (one commit, no `final-backup-*` directory at all), the typed-back confirmation matching and mismatching through injected stdin, `--force`, and the non-TTY refusal naming `--force`. `internal/render`'s new functions (`EnablePostgres`, `SetSize`, `AddDomain`, `CopyValuesForStaging`, `Backup`, `FinalBackupApplication`, `FinalBackupCluster`) also get direct table/`Example` tests in `internal/render`, the same layout `edit_test.go`/`example_test.go` already used for `AddSecretName`/`AddKustomizeSource` and `ArgoCDApplication`/`Values` — this package, unlike `internal/migrate` or the domain logic in `internal/platformrepo` (#13's notes), has carried its own direct tests since #10, and the new node-editing logic (in particular the empty-string-vs-null quirk above) is exactly the kind of thing worth pinning down at the unit level in addition to the CLI seam.
