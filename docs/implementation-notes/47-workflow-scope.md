# #47 (item 12) CLI: `app create` needs the `workflow` scope

Questions that came up while making `iidp app create --path create` and `--path adopt` check the developer's token for the `workflow` OAuth scope, the options considered, and the answer chosen for each. GitHub's behaviour was checked against the real API on 2026-09-24 (`gh api -i /`, `/rate_limit` and `/user` all carry `X-OAuth-Scopes` for a `gh auth login` token); the gh CLI's scope behaviour against its manual (Context7, `/websites/cli_github_manual`, `gh auth refresh`).

## The failure being prevented

GitHub refuses any HTTPS push that creates or changes a file under `.github/workflows/` when the OAuth token lacks the `workflow` scope ("refusing to allow an OAuth App to create or update workflow `.github/workflows/deploy.yaml` without `workflow` scope"). Create pushes `deploy.yaml` in its first commit, *after* `POST /orgs/{org}/repos` has made the repository, so the push failing left a half-provisioned Application: an empty repository, nothing in the Platform repository, and a re-run refused because the repository already exists. `gh auth login`'s minimum scopes are `repo`, `read:org` and `gist`; `workflow` is not among them, so a developer cannot be assumed to have it. It worked on the admin's machine only because a global git `url.<ssh>.insteadOf` rewrote the push to SSH, where OAuth scopes do not apply.

## Which commands write workflow files

Only two: Create (`apprepo.Creator.Create`, every framework's rendered template including `other` gets `templates.DeployWorkflowPath`) and Adopt (`apprepo.Adopter.Adopt`, when the repository has no `deploy.yaml` yet). Every other push in the CLI (`app create` without `--path`, `app add-capability`, `app delete`, `secret set`, `ci set-image`) goes to the Platform repository under `applications/`, never `.github/workflows/`, and `ci set-image` uses a GitHub App installation token rather than the gh login anyway. So only those two paths check; the legacy bare `app create` does not even make the extra API call (`TestAppCreateWithoutPathNeverChecksTheWorkflowScope` asserts the fake GitHub is never called).

## The push uses the same token that is checked

`runAppCreate` takes one token from `gh auth token` and hands it both to `github.Client` (the scope check, repository creation, the pull request) and, as `git.Auth`, to every clone and push. `internal/git` runs each git command with `-c credential.helper=` (dropping any helper the developer configured, gh's own included) followed by a helper that answers `x-access-token` and that token from `IIDP_GIT_TOKEN`, and the remote is the API's HTTPS `clone_url`. So over HTTPS the push authenticates with exactly the token whose scopes were read. The one way it does not is the one that hid this bug: a developer's own `insteadOf` (or `pushInsteadOf`) rewriting `https://github.com/` to SSH, where git never asks the credential helper at all.

## How the scopes are read: `X-OAuth-Scopes` on `GET /`

`github.Client.TokenScopes` requests the API root and reads the `X-OAuth-Scopes` header, which GitHub sends on every authenticated response to a classic OAuth token or classic personal access token; `gh auth status` reads the same header the same way. The root was chosen over `GET /user` because it answers any token (an installation token gets 403 from `/user`) and has no side effects. `do` became a thin wrapper over a new `send` that also returns the response headers, so there is still one request path. Header presence is what matters, not its value: a classic token with no scopes at all gets the header with an empty value, which is `Known: true` with no scopes, and is refused; `TestAppCreatePathRefusesALoginWithoutTheWorkflowScope` has a case for it.

## Fine-grained and GitHub App tokens: skip, don't refuse

Fine-grained personal access tokens and GitHub App (user-to-server or installation) tokens have permissions, not scopes, and GitHub sends no `X-OAuth-Scopes` header for them. Whether such a token may push workflows (the fine-grained "Workflows: write" repository permission) cannot be read up front without trying a write. Chosen: `TokenScopes{Known: false}`, and `apprepo.CheckWorkflowScope` lets it through. Refusing would lock out every developer who authenticates `gh` with a fine-grained token through `GH_TOKEN`, including ones whose token is perfectly able to push; the check exists to catch the common case (a `gh auth login` OAuth token, always classic), and that case always reports its scopes. The README says a fine-grained token needs the Workflows permission, since nothing checks it. `TestAppCreatePathProceedsWhenGitHubReportsNoScopes` covers the skip.

## A developer whose git rewrites GitHub to SSH is refused anyway

For that developer the scope does not matter for the push, so a refusal is, strictly, a false one. Chosen: refuse regardless, for three reasons. First, the cost is asymmetric: a false refusal costs one `gh auth refresh -s workflow` browser round trip, once per machine, and nothing is created before it; a false pass costs a half-provisioned Application and manual cleanup. Second, the rewrite is not something iidp sets up or supports: the design is "authentication is the gh login", and `internal/git` deliberately replaces the developer's credential helpers with the gh token. Detecting it reliably would mean re-implementing git's URL rewriting (`insteadOf`, `pushInsteadOf`, longest-match rules, includes), or probing with `git ls-remote --get-url`, which does not apply `pushInsteadOf` at all, and a wrong guess there is exactly the failure this check exists to prevent. Third, it keeps the behaviour the same on every machine, so "it worked for the admin" cannot hide the problem again, which is how this bug survived until the first real developer run. The `workflow` scope adds nothing beyond `repo` except the right to change workflow files in repositories the developer can already push to, so asking for it is a small grant.

## Where the check runs: Create up front, Adopt after detection

Create always pushes the workflow, so `runAppCreate` reads the scopes right after taking the token and refuses before anything else: before the wizard's summary, before `CheckAvailable` clones the Platform repository, before `GET /user` for `--owner user`, and before `Creator.Create`'s existence check or `POST .../repos`. The tests assert no creation request and no Platform-repository commit, and that the interactive summary is never shown.

Adopt adds the workflow only when the repository has none (`Detection.HasDeployWorkflow`, `docs/implementation-notes/15-cli-adopt-path.md`), and that is known only once the repository is cloned. Refusing Adopt before the clone would falsely refuse a repository that already has `deploy.yaml` and only needs a Dockerfile, which needs no scope beyond `repo`. So the scopes are read up front, but the refusal runs where the Postgres/Static-site refusal already runs: in the interactive path, in `checkAdoptPreview` (after `Adopter.Preview`'s throwaway clone, before the summary); in the flag-driven path, inside `Adopter.Adopt` right after detection (`AdoptRequest.Scopes`), before any file is written, branch created, commit made or push attempted. Cloning into a temporary directory is a read, so this is still "before anything is created or written". The zero value of `AdoptRequest.Scopes` is "unknown", which never refuses, so a caller that does not read scopes keeps the old behaviour. `TestAppAdoptNeedsNoWorkflowScopeWhenTheRepositoryAlreadyHasTheWorkflow` covers the case that must not be refused.

## The message

`apprepo.CheckWorkflowScope` wraps `ErrMissingWorkflowScope` and says why (GitHub refuses a push that adds `.github/workflows/deploy.yaml` without it), that nothing was created, and the exact command on a line of its own: `gh auth refresh -s workflow`. `gh auth refresh -s` adds to the existing scopes rather than replacing them, so the developer loses nothing by running it.

## Testing

Through the CLI seam, as everywhere else in the CLI. `fakeGitHub` (`internal/cli/app_create_create_test.go`) gains a `GET /` handler and middleware that stamps `X-OAuth-Scopes` on every response. The default is `gh auth login`'s minimum scopes plus `workflow`, so every existing Create and Adopt test now also runs through the passing branch of the check. `setScopes` changes the header and `reportNoScopes` drops it. `internal/cli/app_create_workflow_scope_test.go` covers: Create refused (minimum scopes, and a token with no scopes at all), including `--owner user` and the wizard before its summary; Create proceeding when no scopes are reported; the legacy path never calling GitHub; Adopt refused with no branch pushed, no pull request and no Platform commit, flag-driven and through the wizard; and Adopt proceeding without the scope when the repository already has the workflow. Each refusal test was checked to fail with the check disabled.
