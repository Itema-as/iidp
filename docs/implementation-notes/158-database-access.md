# #158 Database access: per-Environment levels, the roles and their passwords

This note records the decisions taken while adding `postgres.access`, the setting that says who among an Application's developers may reach an Environment's database ([#158](https://github.com/Itema-as/iidp/issues/158), designed in [#147](https://github.com/Itema-as/iidp/issues/147)). It covers the levels, the `<app>_read` and `<app>_write` roles they open, the password Secrets the CLI writes for them, `iidp app db access`, and what `iidp app status` and Argus show. The database tunnel that will log in as these roles is #159; nothing outside the cluster reaches the database yet. For each question the note gives the options considered and the answer chosen, and what was checked against the pinned CloudNativePG. The setting's contract is in [`chart/application/README.md`](../../chart/application/README.md) ("Database access"), [`docs/platform-repository.md`](../platform-repository.md) and the README ("Database access").

## What was checked, and where

Sources, checked on 2026-10-06. `bootstrap/versions.yaml` pins the `cloudnative-pg` chart 0.29.0, whose `Chart.yaml` (`helm show chart cloudnative-pg --repo https://cloudnative-pg.github.io/charts --version 0.29.0`) has `appVersion: 1.30.0`. Everything below is from `cloudnative-pg/cloudnative-pg` at the tag `v1.30.0`:

- **The PostgreSQL version.** `pkg/versions/versions.go`: `DefaultImageName = "ghcr.io/cloudnative-pg/postgresql:18.4-system-trixie"`. The chart sets no `imageName`, so every Environment runs PostgreSQL 18.4. The predefined roles `pg_read_all_data` and `pg_write_all_data` exist from PostgreSQL 14 on. The kind e2e checks `server_version_num` is at least 140000, logged in as `shop_read`.
- **Managed roles.** `api/v1/cluster_types.go`, `RoleConfiguration`: `inRoles` ("existing roles to which this role will be immediately added as a new member", applied with `GRANT` and `REVOKE` on later changes too), `connectionLimit` (default `-1`), `passwordSecret` ("must follow the `kubernetes.io/basic-auth` format and contain both a `username` and a `password` field"), `inherit` (default `true`), and `superuser`, `createdb`, `createrole`, `replication` and `bypassrls`, all `false` by default. `internal/management/controller/roles/postgres.go`: `CREATE ROLE` writes every attribute explicitly (`NOSUPERUSER`, `NOCREATEDB`, ..., `CONNECTION LIMIT <n>`) and quotes the name with `pgx.Identifier.Sanitize`, so an Application name with dashes makes a valid role name. `internal/webhook/v1/cluster_webhook.go`, `validateManagedRoles`: a role name must not be duplicated or reserved (`postgres`, `streaming_replica` and the like), and `connectionLimit` must be `-1` or positive.
- **The password Secret.** `internal/management/controller/roles/runnable.go`, `getPassword`, and `internal/management/utils/secrets.go`, `GetUserPasswordFromSecret`: the operator reads the Secret's `username` and `password` keys, and refuses one whose `username` is not the role's name ("the username in secret %q does not match role %q"). It does not itself check the Secret's type; the API reference asks for `kubernetes.io/basic-auth`, which is what the CLI writes. `docs/src/declarative_role_management.md`: a Secret labelled `cnpg.io/reload: "true"` has a changed password applied at once, an unlabelled one only at a later reconciliation, so the CLI labels it.
- **A role whose Secret does not exist.** `runnable.go`, `applyRoleCreateUpdate`: the password is read before `CREATE ROLE`, so a missing Secret means the role is not created. The error is recorded per role in `status.managedRolesStatus.cannotReconcile` and does not stop the other roles. The role is created at a later reconciliation once the Secret exists. The chart renders a role only when its Secret is named, and the CLI writes the Secret in the same commit as the name, so this only happens while ArgoCD applies the two.
- **A role removed from `spec.managed.roles`.** `declarative_role_management.md`, "Removing a role": a role leaves the operator's management when its entry is removed, and is dropped only with `ensure: absent`. See "Closing a level" below.
- **`ensure: absent`.** `internal/management/controller/roles/roles.go`, `evaluateNextRoleActions`: a role in the database whose spec entry is `absent` is put on the delete list; one that is not in the database is counted as reconciled and nothing is done, so an absent entry for a role that never existed is a no-op. `postgres.go`, `Delete`, runs `DROP ROLE IF EXISTS`. A failed drop goes through `parseRoleError` (`postgres_errors.go`), which knows `2BP01` (dependent objects still exist), and is recorded in `cannotReconcile` like any other per-role error, to be tried again at the next reconciliation.
- **A drop with a session open.** Neither CloudNativePG nor PostgreSQL's documentation says, so it was tried on a throwaway PostgreSQL 18.6 cluster (Homebrew's `postgresql@18`, `initdb` in a temporary directory). `DROP ROLE IF EXISTS` of a role with an open session succeeds; that session's next statement fails with "invalid role OID", and a new login as the role fails ("role does not exist"). A session that has created a temporary table makes the drop fail: "role cannot be dropped because some objects depend on it", "owner of table pg_temp_2.t", the `2BP01` above. Once that session ends, the drop succeeds. `DROP ROLE IF EXISTS` of a role that never existed only notices that it does not exist.
- **The superuser.** `cluster_types.go`: `enableSuperuserAccess` defaults to `false`, and the chart does not set it. `pkg/postgres/configuration.go`: the default `pg_hba.conf` ends with `host all all all <DefaultAuthenticationMethod>` (`scram-sha-256`), so the roles log in over TCP with their password, as the e2e does.

From the PostgreSQL documentation (postgresql.org, checked the same day):

- **The predefined roles.** The PostgreSQL 14.0 release notes add `pg_read_all_data` and `pg_write_all_data`. "Predefined Roles" (version 18): `pg_read_all_data` reads all data "as if having `SELECT` rights on those objects and `USAGE` rights on all schemas", and `pg_write_all_data` writes it "as if having `INSERT`, `UPDATE`, and `DELETE` rights". Neither bypasses row-level security.
- **No DDL.** "Schemas" (version 18): from PostgreSQL 15 on, the `public` schema does not grant `CREATE` to `PUBLIC`. "Privileges", table 5.2: a database grants `PUBLIC` only `CONNECT` and `TEMPORARY`, not `CREATE`.

Checked in kind, in the e2e (`test/e2e/database_access_test.go`, run locally on 2026-10-06 with kind 0.33.0 on podman; `TestBootstrap` passed in 567 s): `server_version_num` is 180004; the operator reconciles both roles; `shop_write` writes a row and `shop_read` reads it; `INSERT` as `shop_read` and `CREATE TABLE` as either role are refused ("permission denied"); and the database tunnel's ServiceAccount may `get` exactly the two password Secrets. A rerun at the final commits also closes read-only and sees `shop_read` dropped (below). Not checked anywhere: how long the operator takes to retry a role whose Secret arrived late. The e2e only shows it gets there within three minutes.

## The values: `postgres.access` and two password Secret names

The brief fixes `postgres.access.readWrite` and `postgres.access.readOnly`. The names of the password Secrets follow `platform.backupsCredentialsSecret`, the other Platform secret the chart names by key: `postgres.readWritePasswordSecret` and `postgres.readOnlyPasswordSecret`. They sit beside `access`, not inside it, so that an Environment with no `access` block (one written before the setting) can still name passwords, which is the case the brief's first rendering criterion describes. They are not in the `secrets:` list, which would put the passwords into the Application's environment.

An unset level takes the Environment's default in the chart, not in the values file, so an existing Environment needs no migration commit. The CLI does write both levels explicitly whenever it opens an Environment (`app create`, `add-capability --postgres` and `--staging`, `app db access`), the way it writes `backupRetention`: the values file then reads as a complete description. A Preview Environment renders from staging's values file, so it gets staging's explicit levels, or with none, the chart's default for `pr-<number>`, which is staging's. The ApplicationSet needed no change.

## One check, in the chart and in the CLI, with one message

`application.postgres.access` in `_helpers.tpl` resolves and checks the levels, and `application.validate` calls it, so an unreleased Environment is refused too. `internal/render.ResolveDatabaseAccess` does the same for the CLI. The two cannot share code, so `TestTheCLIRefusesTheSameDatabaseAccessWithTheSameMessage` (in the chart's tests) feeds each refusal fixture to both and compares the messages exactly. The Go errors are a small type whose `Error()` is the chart's message alone and which `errors.Is` matches to `ErrInvalidDatabaseAccess`; wrapping with `%w` would have prefixed the sentinel's text.

The order is: an unknown level, then a level other than `none` without Postgres, then `readOnly` stricter than `readWrite`. Only an explicit level can be refused for missing Postgres: a staging Environment without Postgres has a default `readWrite` of `push`, which opens nothing and must not be refused. The strictness check runs on the resolved levels, so `readOnly: admin` on staging is refused against the default `readWrite: push`.

## The roles

`<app>_write` and `<app>_read` are named after the Application, not the Environment, as the brief says: each Environment has a database of its own, and the name a developer types stays the same in each. Every attribute is written out (`login: true`, `inherit: true`, the five others `false`) although they are CloudNativePG's defaults: `inherit` is what makes the predefined roles' privileges apply, and the rest make the manifest say what the role cannot do.

`pg_write_all_data` grants `INSERT`, `UPDATE` and `DELETE` on every table and `USAGE` on every schema, and nothing that creates objects. On PostgreSQL 15 and later the `public` schema no longer grants `CREATE` to everyone, and the database's `CREATE` privilege is its owner's, so `CREATE TABLE` and `CREATE SCHEMA` are refused for both roles; the e2e checks the first. A role can still create temporary tables, which `PUBLIC` may by default. They last only for the session and change no schema, so they were left alone.

## The tunnel's `Role`

`<fullname>-db-tunnel` grants `get` on `secrets` with `resourceNames` listing exactly the rendered roles' Secrets, bound to `platform.databaseTunnel.serviceAccount` in `platform.databaseTunnel.namespace`, both `iidp-db-tunnel` by default, the names #159 deploys the tunnel under. It renders only with at least one open role and lists only open roles' Secrets, so a closed Environment grants nothing, and it lives in the Environment's namespace, so ArgoCD prunes it with the Environment. It is in the default sync wave: nothing in the Environment waits for it.

## Closing a level

#147's decision is that a role exists only when its level is not `none` and the values file names its password Secret. Leaving a closed role out of `spec.managed.roles` does not do that: CloudNativePG stops managing a role whose entry is removed but leaves it in the database, with `LOGIN` and its last password. So the chart renders both roles always, an open one as `ensure: present` with its attributes and password Secret, and every other one as `ensure: absent` with its name alone. That covers a level of `none` and a level whose password is not named. A role that was open is dropped when it closes, and an absent entry for a role that never existed costs nothing (above).

Closing a level with `iidp app db access --read-only none` removes the password Secret and its name, and the next sync drops the role. A developer still connected as it is cut off at their next statement. One holding a temporary table keeps the role until their session ends: CloudNativePG records the failed drop in `status.managedRolesStatus.cannotReconcile` and drops the role at a later reconciliation. The database tunnel will refuse new sessions straight away anyway, since it reads the level from the `Cluster`'s annotation.

## Passwords and their files

The CLI generates a password with `crypto/rand.Text()` (26 base32 characters, 130 bits) and writes it as a `kubernetes.io/basic-auth` Secret, `render.PasswordSecretDocument`, a variant of `render.SecretDocument` sharing its labels and annotations, plus `cnpg.io/reload: "true"`. It is SOPS-encrypted like `iidp secret set`'s, into `sops/db-write.enc.yaml` or `sops/db-read.enc.yaml`, as the Secret `<fullname>-db-write` or `<fullname>-db-read`. A password already there is kept, so running `iidp app db access` again does not change a working password. A preview uses staging's names, which staging's `sops/` source applies in the preview's namespace.

`iidp secret set` writes `<KEY lowercased, _ to ->.enc.yaml` and `<fullname>-<that>`, so a `KEY` of `DB_WRITE` would have replaced the role's password with an Opaque Secret of the same name. `ValidateSecretKey` now refuses `DB_WRITE` and `DB_READ`, naming `iidp app db access`. Names the slug rule cannot produce (with a dot, say) were the alternative, but they would read unlike every other file in the directory.

`app create --postgres`, and `add-capability --postgres` and `--staging` on an Application with Postgres, need an `agePublicKey` in `platform.yaml` to write a password, which until now only `secret set` needed. Without one they still succeed, write the levels only, and print which Environment stays closed and the `iidp app db access` command that opens it once the key is there; refusing would have broken creating an Application on a Platform without the key, which `platform.yaml`'s documentation allows. They also need `sops` on `PATH` now. With `--path create` or `--path adopt` and `--staging`, a missing `sops` is refused before the Application repository is created or the pull request opened (`checkPasswordEncryption`); without `--path`, and for `add-capability`, the Writer fails before it commits. The CLI's tests use a fake encryptor (`Dependencies.Encryptor`), so they run without `sops`; one test encrypts with the real binary and decrypts with the fixture key.

`add-capability --staging` copies prod's values, but not prod's levels or passwords: `render.CopyValuesForStaging` drops `postgres.access` and both names, and the new staging is opened at its own defaults. Prod's passwords could not be copied anyway, as the CLI cannot decrypt them.

## `iidp app db access`

`--env` takes `prod` or `staging` (`platformrepo.ValidateEnvironmentName`), and is required: the brief names no default, and guessing an Environment for a command that opens a database seemed wrong. A level not given keeps its current value, defaults included, so the flagless form writes exactly the passwords the current levels need. An Environment without Postgres is refused, after the chart's own checks, naming `iidp app add-capability --postgres`. A run that changes nothing prints "Nothing to change" and commits nothing. The commit message spells out the resulting levels (`iidp app db access shop --env staging --read-write push --read-only none`), so the Platform repository's log says what each Environment was set to.

## `iidp app status` and Argus

`platformstate.Environment` gains `databaseAccess`, `{"readWrite": ..., "readOnly": ..., "readWriteSetUp": ..., "readOnlySetUp": ...}`, absent without Postgres. The Deploy gate's status endpoint fills it from the clone of the Platform repository it already reads, staging's values file for a Preview Environment, so it needs no new access in the cluster. Argus fills it from the `Cluster`, which `platformstate.EnvironmentOf` reads from the `Cluster`s it is handed: the levels from its annotations, which Argus's transform already keeps (`pruneAnnotations` keeps `iidp.itema.no/*`), and each role's name and `ensure` from `spec.managed.roles`, which `platformstate.PostgresCluster` now decodes and so the transform keeps. So `iidp app status` shows what the Platform repository says and Argus what is deployed; they differ only between a commit and its sync.

A level is set up when it is `none`, or when its role is open: for `iidp app status`, its password Secret is named in the values file; for Argus, its role is present among the `Cluster`'s managed roles. A level that is not set up is open on paper but lets nobody in yet, which is the state of every existing Environment until the Platform admin runs `iidp app db access` at rollout. The JSON has a boolean per level, `readWriteSetUp` and `readOnlySetUp`, rather than one field for both, so a script can tell which level is missing; for a level of `none` it is `true`, since there is nothing to set up. Both texts print the command that sets it up, with `--env staging` for a Preview Environment, since its levels and passwords are staging's: `iidp app status` as "Database: read-write push (not set up: run iidp app db access shop --env staging) · read-only none", and the detail card as "Developer access" with the same words.

## The kind e2e

The fixture's `shop-prod` opens read-write for `admin` and read-only for `pull`, with both passwords encrypted for the fixture's age key. `testDatabaseAccess` runs right after the fixture Application is healthy, before `shop-staging` is deleted. It waits for both roles in `status.managedRolesStatus.byStatus.reconciled`, then runs `psql` in the database Pod, over TCP to `shop-db-rw`, with each role's password read from its Secret. The table it writes to is created as the owner, `SET ROLE shop`, the way a migration would make it. It then closes read-only by pushing to the fixture Platform repository the edit `iidp app db access shop --env prod --read-only none` makes (the level, the removed reference and the removed password file, with `internal/render`'s own editors), refreshes `shop-prod`, waits up to three minutes for `shop_read` to be gone from `pg_roles`, and checks that `shop_write` still works and that the tunnel's ServiceAccount may no longer get `shop-db-read`.
