# #159 The Database tunnel and `iidp app db connect`

This note records the decisions taken while adding the Database tunnel, the Platform component through which a developer reaches an Environment's database from their own machine ([#159](https://github.com/Itema-as/iidp/issues/159), designed in [#147](https://github.com/Itema-as/iidp/issues/147)), and `iidp app db connect`, the CLI command that uses it. It builds on the levels, roles and passwords of [#158](158-database-access.md). For each question the note gives the options considered and the answer chosen, and what was checked against Traefik, pgx and Grafana Cloud. Why there is a tunnel at all, and why it is a component of its own, is [ADR-0009](../adr/0009-developers-reach-an-environments-database-through-a-database-tunnel.md). The command's contract is in the [README](../../README.md) ("`app db connect`"), and the component's in [`bootstrap/README.md`](../../bootstrap/README.md) ("The Database tunnel").

## What was checked, and where

Sources, checked on 2026-10-06.

**WebSockets through Traefik.** `bootstrap/versions.yaml` pins k3s's Traefik chart `40.1.4+up40.1.0` with the image `3.7.8`. In `traefik/traefik` at the tag `v3.7.8`:

- `pkg/config/static/static_config.go`: `DefaultReadTimeout = 60 * time.Second`, `DefaultIdleTimeout = 180 * time.Second`; the write timeout defaults to none. Traefik's documentation (doc.traefik.io, "EntryPoints", `transport.respondingTimeouts`) gives the same defaults: `readTimeout` is "the maximum duration for reading the entire request, including the body", `idleTimeout` the time "an idle (keep-alive) connection will remain idle". It says nothing about upgraded connections.
- `pkg/server/server_entrypoint_tcp.go`: the entry point sets `readTimeout` as a read deadline on each accepted connection, and gives it to its `http.Server` as `ReadTimeout`, `WriteTimeout` and `IdleTimeout`. A 60-second deadline on a session's connection would cut every session after a minute.
- Go's `net/http` (`server.go`, `(*conn).hijackLocked`, in the Go this repository builds with, 1.27) calls `rwc.SetDeadline(time.Time{})` when a handler hijacks the connection. That clears both the server's deadlines and the one Traefik set at accept, since a TLS connection's deadline is its underlying connection's.
- `cmd/traefik/traefik.go`: the proxy is `pkg/proxy/httputil`, Go's `httputil.ReverseProxy`, unless `experimental.fastProxy` is set, which the chart leaves off (`experimental.fastProxy.enabled: false` in its values). `ReverseProxy` handles a `101 Switching Protocols` by hijacking the client's connection and copying both ways, with no deadline of its own. `pkg/proxy/httputil/proxy.go` only restores the `Sec-WebSocket-*` headers' case for servers that need it, and `proxy_websocket_test.go` tests upgrades, ping and pong, and closing through it. The backend side's `serversTransport` has a dial timeout and an idle timeout for pooled connections, and neither applies to an upgraded one.
- Neither the k3s `HelmChartConfig` the bootstrap writes nor the kind harness sets `respondingTimeouts`.

So a WebSocket upgrade passes through an Ingress with no extra configuration, and once upgraded has no timeout of Traefik's, shorter than 30 minutes or otherwise. Neither the Ingress nor the tunnel sets anything for it, and nothing sends keepalives: both ends' TCP keepalive (Go's default of 15 seconds) keeps the connection alive in any NAT between them. The kind e2e checks the part that matters: a session through Traefik sits idle for 65 seconds, past the 60-second `readTimeout`, and then runs another query.

**SCRAM.** The tunnel logs in with `github.com/jackc/pgx/v5`'s `pgconn` at v5.11.0, the newest release. Its documentation (the `pgconn` API reference and `configuration.md` at v5.11.0, through context7) lists SCRAM-SHA-256 among the authentication methods, with channel binding (`SCRAM-SHA-256-PLUS`) preferred over TLS (`channel_binding` defaults to `prefer`), and `require_auth`, which aborts a login whose server asks for any method not listed. `pgconn.PgConn.Hijack` hands over the raw connection, the backend's process id and secret key, its parameter statuses and its transaction status, once the connection is idle; the documentation names proxies as what it is for, and exempts it from semantic versioning, so a pgx upgrade has to be checked against it. `max_protocol_version` defaults to `3.0`, which the tunnel sets anyway, so the secret key it forwards is the four bytes a protocol 3.0 client expects. CloudNativePG's default `pg_hba.conf` ends with `host all all all scram-sha-256` ([#158](158-database-access.md)). The unit tests log in against an in-process Postgres that runs the server's side of SCRAM-SHA-256 (RFC 5802 and RFC 7677) itself, and the kind e2e against CloudNativePG's PostgreSQL 18.

**Retention.** `docs/design.md` puts the Platform's logs and metrics on Grafana Cloud's free tier. Grafana's pricing page and "What's included in Grafana Cloud Free" (grafana.com/products/cloud/free-tier) give the free tier 14 days of log retention, and paid plans 30 days by default ("Understand your Grafana Cloud Logs, Traces, and Profiles invoices", grafana.com/docs). So the tunnel's log lines, the record that lasts, are kept 14 days, against an hour for the Events. **Not confirmed:** which plan Itema's stack is on today; only the design document says free. Longer retention needs a paid plan or Grafana Cloud's logs export.

Checked in kind, in the e2e (`test/e2e/database_tunnel_test.go`, run locally on 2026-10-06 with kind 0.33.0 on podman, where `TestBootstrap` passed): the `db-tunnel` Application is Healthy in a namespace enforcing Pod Security `restricted`; `iidp app db connect shop`, through Traefik's websecure entry point, prints a connection string for `shop_write` on staging, and `psql` through it inserts a row, sits idle for 65 seconds and runs another query on the same session; `--read-only` connects as `shop_read`, which reads the row and is refused an `INSERT` ("permission denied"); prod is refused before anything listens, at the levels #158's test leaves it at and again once its values file is back at the defaults, both `none`; `--pr 7` reaches `notes`'s Preview Environment as `notes_write`, with staging's password Secret; and the Events in `argocd` are a start and an end for each staging session and a refusal for each prod attempt, all naming the developer's login. The scenario logs the connection strings, the roles and the exit codes, and no query results. The tunnel logged in to CloudNativePG's PostgreSQL 18 with `require_auth=scram-sha-256` and `sslmode=require`, so the SCRAM exchange, over TLS, is the one the default `pg_hba.conf` asks for. Not checked anywhere: a session reaching the 30-minute or 8-hour limit through Traefik, which only the fake clock covers, and Ctrl-C through a real `psql`, which only the unit test's own `CancelRequest` covers.

## One component, three packages

The tunnel is `cmd/iidp-db-tunnel`, its own image `ghcr.io/itema-as/iidp-db-tunnel`, released with the gate's and Argus's (`.goreleaser.yaml`, `IIDP_PUBLISH_DB_TUNNEL`), and the bootstrap component `db-tunnel` in the namespace `iidp-db-tunnel`. The code is in three places:

- `internal/dbtunnel`: the server, the check, the Postgres handling, the limits and the audit. It is the only package that imports pgx; `TestOnlyTheTunnelLinksThePostgresDriver` keeps the CLI, the gate and Argus from linking it, and `TestOnlyArgusLinksClientGo` now covers the tunnel too.
- `internal/dbtunnel/api`: the two calls, their answers and a client. It is apart from the server so that the CLI does not link the driver.
- What the tunnel shares with the gate moved out of `internal/deploygate`, rather than being copied: `internal/repoaccess`, the repository permission check of the status endpoint, and `internal/kubeevent`, the Event recording of the Deploy Events. `platformrepo.LiveEnvironments` replaces the status endpoint's own list of Environments, and `platformstate.Kube` gained `Get`. The status endpoint's behaviour is unchanged, and its tests are as they were.

The Application is `db-tunnel`, after `deploy-gate`, and the ServiceAccount and namespace are #158's `iidp-db-tunnel`. `TestTheApplicationChartsTunnelIsTheComponentsServiceAccount` keeps the application chart's `platform.databaseTunnel` defaults equal to them. `db` joins the reserved Application names, next to `deploy` and `auth`: an Application called `db` would have the tunnel's address, and could receive the tokens developers send it.

## The protocol: a check, then one WebSocket per connection

The brief asks for a preflight that refuses at once and learns the role, and for one WebSocket per Postgres connection. The tunnel has two calls on the same path shape, `GET /v1/check/<app>/<environment>` and `GET /v1/connect/<app>/<environment>`, each with `?readOnly=true` when asked and the token as `Authorization: Bearer`. The check answers JSON, a `Grant` (`login`, `application`, `environment`, `access`, `role`, `database`) or an `ErrorResponse`, so the CLI can print the tunnel's refusal as it is. A single path whose plain `GET` is the check was considered, and rejected as harder to read in a log.

`<environment>` is `prod`, `staging`, `pr-<number>` or `auto`. The brief's default, staging when the Application has one, is decided by the tunnel, which clones the Platform repository anyway, and the check answers the Environment it chose; the CLI then connects to that one. The CLI would otherwise have needed a second clone just for it. `auto` is the word the Deploy gate's call already uses for its own default.

Connect upgrades first, and runs the check on the Postgres client's startup. Only a call with no token at all is refused before the upgrade. A refusal after it reaches the client as a `FATAL` `ErrorResponse` with the tunnel's message (SQLSTATE `28000`, invalid authorization, for a permission refusal, `08004` otherwise), so `psql` prints the reason itself. Checking before the upgrade would have answered an HTTP status that the CLI could only turn into a closed connection, or into an `ErrorResponse` of its own, which would have meant speaking the Postgres protocol in the CLI too.

## The Postgres startup

- **Toward the client.** The tunnel reads each startup packet to its length and no further, so nothing the client sends after it is lost to a buffer. It answers an `SSLRequest`, and a `GSSENCRequest`, with `N`: the WebSocket is already TLS. It never asks the client for a password, and ignores the user and the database it sends. It forwards only `application_name`, `client_encoding`, `DateStyle`, `TimeZone`, `IntervalStyle`, `extra_float_digits` and `search_path` from the client's parameters; `options` and `replication` could ask for more than a plain session, and are dropped with the rest. A client that asks for protocol 3.2 gets a `NegotiateProtocolVersion` down to 3.0, as from a server that does not speak it.
- **Toward the database.** `pgconn` connects to `<cluster>-rw.<namespace>.svc:5432` as the role, to the Application's database, with `sslmode=require` (encrypted, without checking the operator's own CA, whose Secret the tunnel may not read), `require_auth=scram-sha-256` and `max_protocol_version=3.0`. Once logged in, the tunnel hijacks the connection and tells the client `AuthenticationOk`, then the database's own `ParameterStatus` messages, its `BackendKeyData` and `ReadyForQuery`, and from then on copies bytes both ways untouched. Nothing is buffered across the hijack: Postgres sends nothing after `ReadyForQuery` until the client's first query.
- **A Postgres error at startup** reaches the client as Postgres's own `ErrorResponse`, its code, message, detail and hint, such as `53300` "too many connections for role" when the role's three connections are taken. Any other failure to log in is a `FATAL` `08006` that names the Environment, and the cause goes to the log only.
- **The role and its password come from the `Cluster`.** The role is the managed role named `<app>_write` or `<app>_read` that is `ensure: present`, and its password is in the Secret its `passwordSecret` names, which for a Preview Environment is staging's. The Secret must be `kubernetes.io/basic-auth` for that role; one whose `username` is another role's is treated as missing.

## Ctrl-C: the cancel request works for the developer's own session

`psql` sends Ctrl-C's `CancelRequest` on a new connection, with the process id and secret key from `BackendKeyData`. The CLI carries it over a WebSocket of its own like any other connection, and the tunnel runs the whole check on it too. The tunnel keeps its open sessions by their key, and passes a cancel on to the database only when the key is a session of the same GitHub login on the same Environment; any other is dropped, and the connection closed, the way Postgres answers a cancel with nothing either way. Dropping every cancel was the alternative the brief allowed, but it would have left `psql`'s Ctrl-C doing nothing during a long query. The keys are the database's own, which the tunnel forwards unchanged, so it can send the cancel straight to the `-rw` Service. `iidp app db connect --psql` catches Ctrl-C itself while `psql` runs, so that it reaches `psql` and does not stop the tunnel under it.

## The check

In order, for every check call and every WebSocket:

1. The developer's GitHub login, from `GET /user` with their token. It is the name every Event and log line carries, and a token GitHub rejects is refused here.
2. The Environment, `auto` resolved: `repoaccess.Clone` makes a shallow clone of the Platform repository with the token (the status endpoint keeps its full clone, which it needs for deploy times), and prod or staging must have a live `application.yaml` in it (`platformrepo.LiveEnvironments`). This comes before the permission, which the brief lists first, so that a developer refused for their permission is recorded on the Environment they asked for (below). It tells them nothing new: the clone has already shown them the Platform repository.
3. Their permission: `repoaccess.Check` reads the binding, checks the owner is the org and asks `GET /repositories/<id>`. `github.ReadableRepository` now decodes `push`, `maintain` and `admin` beside `pull` from the same answer, and `Permission()` is the highest of them, as the levels' own words (`render.AccessPush` and the rest); `triage` is not kept, since GitHub only gives it with `pull`.
4. The `Cluster`: a Preview Environment must have one in `<app>-pr-<number>`. Without one, prod or staging is refused as having no database, or one ArgoCD has not created yet, by its values file.
5. The levels, from the `Cluster`'s annotations, and the role, from `ChooseRole`: read-write when the developer qualifies for it and did not ask for read-only, else read-only when they qualify for that. Whoever qualifies for read-write qualifies for read-only too, since `readOnly` never needs more, so `--read-only` only steps read-write down. `render.Qualifies` holds the comparison, next to the levels it compares.
6. The role and its password, as above.

The refusals are worded in the status endpoint's style, and name the Application, the repository or the Environment, and what is missing. The two the brief words: a developer below both levels gets "refused: your permission on Itema-as/shop is pull, and shop staging's database admits read-write for push and read-only for nobody (none). iidp app db access shop --env staging changes who may connect" (or, with `--read-only` and a read-only level of `none`, that "shop staging's database has no read-only access", with the same permission and repository), and a level whose role or password is not there yet "no database access set up for staging yet, run `iidp app db access shop --env staging`". A Preview Environment's refusals name `--env staging`, since its levels and passwords are staging's.

## Limits

`Relay` copies the bytes and ends the session after `IdleLimit` (30 minutes) with no traffic in either direction, and after `MaxSession` (8 hours) in any case. Both are constants, not settings, and a fake clock tests both. The idle limit counts reads on either side, so a long query whose answer is still coming is not idle. The roles' `connectionLimit: 3` caps a developer's concurrent connections, and its refusal reaches the client as Postgres's own error. When the tunnel stops, it ends every open session and records each end before it exits.

## Audit

Each session's start and end, and each refusal, is an `events.k8s.io/v1` Event in `argocd` regarding the Environment's ArgoCD Application, reported by `iidp.itema.no/database-tunnel` with the action `Connect` and the reasons `DatabaseSessionStarted`, `DatabaseSessionEnded` and `DatabaseSessionRefused`. The annotations are `iidp.itema.no/application`, `/environment`, `/login`, `/role` once one was chosen, and at the end `/duration`, `/bytes-from-client` and `/bytes-to-client`. The note says the same in words. Each moment is also one JSON log line with the same fields, plus the reason a session ended, and the check calls log a line of their own. Nothing logs or records SQL, query results, passwords or tokens, and the audit tests look for each in the log and the Events.

A refusal is recorded as an Event only once the developer's login and the Environment are known: for prod and staging, once the Platform repository has it, so a developer who cannot read the repository, or an Application bound to none or outside the org, is recorded on `<app>-<environment>`; for a Preview Environment, only once its `Cluster` is found. A refusal before that, such as no token, a token GitHub rejects or a pull request with no Preview Environment, has nobody to name or no ArgoCD Application to record on, and would let anyone on the internet fill `argocd` with Events; it is logged only. That follows the Deploy gate, which records a refused Deploy only once it knows the caller and the Environment.

Argus shows the tunnel's Events as notes in the Environment's activity, in the tunnel's own words: quiet, and a session's end feed-only, since it reports something finished. They are seeded when Argus starts, like the Deploy gate's, and a refusal is not also shown as a Warning Event. Argus's informers already read every Event in `argocd`, so it needs no new access.

## The WebSocket library

`golang.org/x/net/websocket`, already in `go.mod` as an indirect dependency of client-go, now a direct one. It carries binary frames as a `net.Conn` and answers pings, which is all a byte pipe needs. Its own documentation points to more actively maintained packages, and `github.com/coder/websocket` was the alternative; it would have added a module for no feature the tunnel uses. The only other new modules are pgx's: `github.com/jackc/pgx/v5`, `jackc/pgpassfile` and `jackc/pgservicefile`. The client does its own TCP and TLS, so the kind e2e can dial Traefik's host port while asking for `db.app.example.test`. It does not go through an HTTPS proxy, and the README says so.

## The CLI

`iidp app db connect` reads `platform.yaml` for the address, as `iidp app status` does for the gate's. When it cannot, it says so on stderr and asks `platform.DefaultDatabaseTunnelURL`, `https://db.app.itma.no`, next to `DefaultDeployGateURL`; the tunnel then refuses for itself whoever may not connect.

While it runs, its local port is open to any process on the developer's machine, with no password, as `kubectl port-forward`'s is, and every connection to it is checked and recorded as the developer. That is the price of letting any Postgres client connect; the README says so, and to stop the command when done. Only `127.0.0.1` listens. `cli.Dependencies` gained `DatabaseTunnel`, which the tests replace with a fake tunnel, and `Context`, which the tests cancel where a developer presses Ctrl-C. `RunWith` now runs commands in that context, and returns the exit status of a program a command ran, `psql`'s, without printing anything of its own.

## The kind e2e

The harness builds the tunnel's image from the working tree, as it does the gate's, and the fixture's `platform.yaml` points `dbTunnel.image` at it. The fake GitHub answers `push` (with `triage` and `pull`) for the developer's token on `shop` and `notes`, and `GET /user` with the login `e2e-developer`. The fixture's `shop-staging` opens read-write for `push` and read-only for `pull`, and `notes-staging` names a read-write password, both encrypted for the fixture's age key with the CLI's own `render.PasswordSecretDocument` and `sops`. `testDatabaseTunnel` runs `iidp app db connect` in-process, through Traefik's host port, and the host's `psql` against the connection string it prints, after `testDatabaseAccess` and before `shop-staging` is deleted. `testPreviewEnvironments` connects to `notes`'s pull request 7 the same way. The CI runner's image, Ubuntu 24.04, has PostgreSQL 16's `psql` (`actions/runner-images`, `images/ubuntu/Ubuntu2404-Readme.md`, "Databases"); the test fails without one, rather than skipping.

The brief's "prod, closed by default" needed a fixture prod with a database and its default levels, and there is none: `notes` and `later` have no image on prod, so no `Cluster`, and #158's test opens `shop`'s prod (read-write for `admin`, read-only for `pull`, then read-only closed). So the scenario first refuses that prod with its levels ("admits read-write for admin and read-only for nobody (none)"), then takes `postgres.access` and both password names out of `shop`'s prod values file, waits for the `Cluster`'s annotations to say `none` for both, and is refused again ("admits read-write for nobody (none) and read-only for nobody (none)"). Nothing after it depends on `shop`'s prod database access.
