# iidp

Itema's Internal Developer Platform. It lets an Itema developer describe an application once and have everything it needs to run provisioned for them.

## Language

**Platform**:
The shared Kubernetes cluster and the services on it that every Application runs on. There is one Platform.
_Avoid_: infra, the cluster (when meaning the whole thing)

**Application**:
A deployable unit that an Itema developer owns, with its own git repository, its own Environments, and its own resources on the Platform.
_Avoid_: app (in docs), service, project

**Environment**:
One running instance of an Application with its own data and its own address. Every Application has a `prod` Environment. An Application may also have a `staging` Environment.
_Avoid_: stage, deployment target, tier

**Application repository**:
The git repository holding an Application's source code. Owned by the Application's developers.
_Avoid_: app repo, source repo

**Platform repository**:
The git repository holding the desired state of every Application on the Platform. The CLI writes to it; the Platform reconciles from it. Developers do not edit it by hand.
_Avoid_: config repo, gitops repo, manifests repo

**CLI**:
The `iidp` command developers run to create and change Applications. It is the only intended interface to the Platform.
_Avoid_: tool, wizard (the wizard is one flow inside the CLI)

**Capability**:
Something an Application can request from the Platform and have provisioned for it, such as a Postgres database, a custom domain, or a `staging` Environment. Capabilities are chosen in the wizard and can be added later.
_Avoid_: feature, add-on, resource, service

**Kind**:
What an Application fundamentally is, chosen once at creation. The Kinds are Static site (built files served as-is) and Web service (a container listening on a port).
_Avoid_: type, shape, template

**Create**:
Making a new Application together with a new Application repository generated by the CLI.
_Avoid_: new, scaffold, init

**Adopt**:
Making a new Application from an Application repository that already exists. The CLI proposes its changes to that repository as a pull request.
_Avoid_: import, migrate, onboard, connect

**Deploy**:
Setting an Environment to run a newly built image of its Application. A push to `main` deploys to `staging`, or to `prod` when there is no `staging`.
_Avoid_: release, ship, roll out

**Promote**:
Deploying to `prod` the image `staging` already runs, triggered by a `v*` tag on the Application repository. Nothing is rebuilt.
_Avoid_: release, publish

**Deploy gate**:
The part of the Platform through which an Application repository's CI deploys and promotes. It checks that the caller is that Application's own repository and may deploy that Environment, then records the new image in the Platform repository. It is the only way an Application repository's CI can change the Platform.
_Avoid_: deploy service, deploy API, write-back

**Argus**:
The live, read-only view of the Platform: every Application and its Environments drawn as a map that developers can explore, where new, deploying and unhealthy Environments show up as they happen. It can only look; changes go through the CLI.
_Avoid_: dashboard, Platform map
